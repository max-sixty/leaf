What needs you: asks and to-dos

Each side has a list: Questions, what waits on you, and Tasks, what the agent owes you. Either side can put items on the other's. A to-do is explicit work on either list, and it stays open until it is ended, so a reply, a Resolve or the end of a session can no longer settle work nobody did. An ask, a request for your input, is a record of its own that its answer ends. This page tracks the plan, how the model works so far, and what is still open.

Step 5: should an Ask be a task on you?

Today an ask is its own record, and a to-do is not an ask. Step 5 made every item on your side a task, as this tab records. Two later changes took it apart again: #2240 gave every request for your input, from a widget, a thread or a version's sign-off, one ask record with its typed answer, which the lists select directly and never turn into a to-do, and #2506 named the record left for explicit work a to-do. What B added still stands: a to-do on you about anything, its id, and its Done.

Your direction then: a task is what sits on a queue, on either side. An Ask stops being a primitive of its own and becomes a task on you that a widget answers. It can carry as much context as it needs, but the queue, the a key, the banner and the panel see only tasks. The three shapes below differ in where a task on you comes from and how it ends. You picked B, and it landed (B, as built).

Before step 5, an Ask came from the page's markup: a widget whose registry entry declares x-awaits says when its state counts as answered, and an lf-ask frames it with a heading and evidence. A question in a thread came from a reply with --awaits. A task came from the log, through leaf task open, and only the agent held one. The queues read all three, under the kinds ask, question and task.

A. Asks read as tasks

Nothing about authoring changes. Leaf reads every open Ask and every thread question as a task on you, beside the agent's tasks, in one tasks reading with an owner.

  • The pick: an lf-ask around the options, as today. Its widget reaching its answered state ends the task done; a version that removes it ends it dropped.
  • The open request: a thread on § Rollback whose reply asks with --awaits. Your reply ends it.
  • The agent's work: leaf task open, as today.

What changes: the queues, the banner, the panel and page state read one tasks list, and the ask, question and answer kinds go. x-awaits keeps its job.

Cost: a task on you can only come from a widget or a thread question. The task is a reading rather than a record, so it has no id of its own and nothing to link a later task to.

B. One task record, with how it ends

A task names its owner, you or the agent, and how it ends. An Ask is a task on you that ends when its widget is answered. The agent can put a task on you on any subject, with or without a widget.

  • The pick: an lf-ask around the options. Stamping the version opens it as a task on you, ended by the widget's answered state.
  • The open request: leaf task open PAGE rollback "Is the rollback plan enough?" --on user. It ends at your Done press on the task.
  • The agent's work: leaf task open, owned by the agent, as today.

What changes: the task event gains owner and an ending, either a widget, a reply or an explicit end. Asks and thread questions become tasks with an id in the log. x-awaits becomes the way a widget declares that it can end a task. A task on you with no widget gets a Done control.

Cost: a version that adds an lf-ask now writes a task event, so markup and log must agree on which widget it is. That is the same rule a widget task already follows. The Done control is new.

C. A task element in the page

lf-task replaces lf-ask. It is a framed region with a heading, any content, and optionally an answering widget. The agent's tasks also show in the page as task cards where the work is, drawn from the log.

  • The pick: <lf-task for="user"> around the options.
  • The open request: <lf-task for="user"> in § Rollback, with the question and a Done control.
  • The agent's work: a card in the chart's section reading "Rebuild the download chart · Working · 3m", and its outcome once it ends.

What changes: B's record, plus the element and the cards. lf-ask is renamed everywhere: the registry, the references, the examples and the corpus.

Cost: the largest change. The page also shows log state in its body, not only in the chrome, which every layout has to make room for.

A start lasts until its item ends: the reply or stamped version that answers your update, or the to-do's end. It holds the item only for the turn that wrote it. Hierarchy, and who says a to-do is done

Two questions about the shape of a to-do: whether one to-do can belong to another, which is in TODO.md to think about, and who decides that a to-do is finished, which you've settled.

Can one to-do belong to another?

Today, no. A Leaf to-do has exactly one link: its subject, the thread, widget, element or page it is about. Nothing points from one to-do to another, or from a to-do to the message that asked for it.

Pi's tasks form a tree. A task that spawns subtasks owns them, and it can wait on them until they finish. Leaf has no equivalent yet.

Two Leaf cases could want a link like that:

  • Work that answers your message. Say you comment "make the table wider". This needs no to-do: Working names your comment itself, so the thread reads Working until the agent's reply settles it. Only work that outlasts the turn, such as a CI run or a build, gets a to-do, and that to-do names the thread your comment is in rather than the comment. That is enough to show the work beside the right thread. It can't say which of several comments in one thread the work answers; if that ever matters, the fix is one field naming the comment, not a tree.
  • Work handed to another session. Say the agent here dispatches a separate session to fix a bug, as this session has done several times this week. The work now belongs to a session this page knows nothing about, so the page can't show it as under way or learn when it ends. Fixing that needs the dispatched session's to-do to point back at the to-do that dispatched it, which is a parent link. That belongs in step 7, Items outlive their session, which already deals with work that moves between sessions: it is also where a to-do whose session ended without an outcome is handed to the next session.

Why not a general tree now: a tree brings rules nothing here needs yet. Does a parent end when its children do? Whose list shows a child? Can a child outlive its parent? The two cases above need at most one link each, so the tree can wait until a case needs more.

The broader question, for later: most work forms a fuzzy hierarchy, since much of planning is breaking a goal into pieces. That breakdown also changes as the work goes on, so a fixed tree is too brittle. It's in TODO.md as "Model how work breaks into pieces".

Who decides the agent's to-do is done?

Decided: the agent ends its own to-dos. It ends each one itself, with leaf task end as done, failed or dropped and a note saying where the result is, or with a version stamped --completes. A to-do on you ends at your Done, and an ask at its answer (how each item ends).

When it needs your sign-off, it asks first. The agent judges whether a result needs it. A passing test or a merged PR doesn't. A design, a rewrite or a choice of wording might. It asks the way it asks anything:

  • A widget ask when there are options to pick, such as "Ship this layout, or try the other?"
  • A prose ask in the thread (a reply with --ask) when the answer is open, such as "Does this read right to you?"

Either goes on Questions, so q reaches it. The to-do stays open on Tasks while it waits, and the agent ends it once you answer. So there is no separate "to review" item, and no rule about whether reading something accepts it. What's left is the agent's instructions, which should say when to ask before ending.

The agent picks the banner line

Today the banner shows the line of the latest start. Later, the line is a field the agent sees and sets: Leaf fills it from the item in hand when the agent is answering something quickly, and the agent can replace it, for example with one line covering five threads it is answering at once.

How Pi Durable models the same ground

The two work at different levels. In Pi, every model turn, tool call and tool result is a message in the user–assistant conversation, and each is a task. In Leaf, a message is your comment or the agent's reply, and one reply is the outcome of a whole run of those: dozens of model and tool steps work towards answering you.

Pi Durable Leaf
A message Every model turn, tool call and tool result Your comment, or the agent's reply to it
A task One step: a model request, a tool call, a compaction, a subagent One thing owed between you and the agent: an answer to your comment, a rebuild, a review
How long it runs Usually seconds; a subagent or reminder longer A turn, or hours to days across sessions
What the record is for Resuming exactly where a crash left off Knowing what is owed, by whom, and whether it was done

So a Leaf item is not one of Pi's tasks but one high in the tree: in Pi's terms, a task the conversation owns, whose children are the steps that work towards it. Leaf sees those steps only as the banner's Working line.

At its own level, Pi Durable works like this:

  • A message is input, not a task. Sent while the agent is busy, it either steers (“joins the running work after the current tool calls”) or queues as a follow-up. A requestId makes the submission exactly-once. Nothing like “picked up” is recorded on it.
  • Work is tasks, and a task's stages are its own. A task type declares named phases, and its state holds a checkpoint naming the current one. Its status is running, waiting on named tasks, or terminal with an outcome (completed, failed or aborted). Code registers one with tx.createTask(Type, input, {ownership}), owned by a task or a conversation.
  • Asking you is not a record. An approval hook asks, and stores your answer with api.memo(), so that “after a restart, the hook finds the stored answer instead of asking again”. The question is the agent's running work, paused on you.

Your model fits Pi's. A Pi task has an owner and waits on whatever it needs, so an ask is the agent's work waiting on you, and Questions is everything waiting on you. Pi differs in two places, neither a conflict. A message is input that starts or steers the agent's work rather than an item of its own, so putting an item on the agent's queue is your message creating work there. And Pi records nothing about delivery, so Leaf's stages from sent to replying belong to the message, not to the task.

How Working became a task

Before step 4, leaf status working --on SUBJECT "…" wrote a claim into the page's status file, outside the log, while a task was a separate record in the log. Both said the agent had taken the subject on. Pi Durable splits that fact by lifetime rather than by record: a foreground task belongs to the current turn, and a background task outlives it.

The first proposal made each claim a task that lasted the turn. What was built goes one step further: your moves are already items on the agent's queue, so a start names your move directly, and only work the agent takes on itself needs a task. The claims left the status file for the log, every reader of claims (workflows, the activity fold, the Stop hook, the banner, the margin and Page Map labels, neighbour rows, the stamp guards) now reads starts, and the instructions tell the agent to start an item.
