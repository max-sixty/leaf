How it works

How Leaf works

An agent builds a page around the work. The user comments, explores, and makes choices. The agent responds by revising the same page.

Leaf supplies the interface and the record of that exchange: comments attached to passages, interactive widgets, decisions, and versions. The agent supplies the content and does the work, using its existing tools in Claude Code, Codex, or Pi.

The agent, Leaf, and the browser

Leaf connects an agent session to a browser page. The harness is the application running the agent, such as Codex. Leaf’s integration brings page updates into that session; the agent answers through Leaf commands and edits to the page’s files.

Leaf’s Python code serves the page, records actions, and computes shared state. Its JavaScript runtime draws the interface in the browser. A user’s own choice or message appears immediately; the server’s reading supplies facts that depend on the whole conversation, such as whose turn it is to answer.

The exchange

Suppose an agent is helping choose a queue policy for an importer. It puts the alternatives and their consequences on a page. The user can choose a policy, or select a sentence and ask about its assumptions. Both reach the agent with the context of the part they concern.

Choose a policy, then open Show activity below it to see the recorded choice. Open the page’s leaf menu and choose Undo; press Activity changed in the feed to see the choice marked undone. This example uses the page’s activity log and Undo; its queue policy is fictional.

Importer queue policy

The importer receives bursts of records faster than it can process them. Its queue has room for 1,000 records.

When the queue fills, what should happen?

Pause the producer Keep every queued record; wait for space before accepting more. Drop the oldest record Accept the newest record immediately; discard the oldest queued one.

Recorded actions
  1. The agent prepares the page. It writes HTML, adds widgets, checks the result, and opens a link for the user.
  2. The user responds on the work. A choice records which option was picked. A comment records the words and the passage or object it points at. Once the server accepts the update, Leaf saves it and makes it available for delivery to the agent.
  3. The agent answers and revises. It can inspect code, run an experiment, or research the question with its normal tools. It replies in the thread and updates the page to reflect the result.

The same link now shows the revised proposal. The discussion stays attached to the work, and the user can continue from there.

Author, hand over, and respond

The harness supplies the agent’s tools and runs its turns. This example follows a queue-policy review from the first page to the answer. Command inventory lists the available operations; Harness connections explains delivery and receipt.

Publish a page

The agent reads Leaf’s skill and the reference for each step: page authoring before writing, and its harness contract before handoff. These instructions set goals for the user’s experience and leave wording and presentation to the agent.

The agent creates a page directory and writes index.html with ordinary HTML and Leaf components. Here, ./review names that directory, relative to the commands’ working directory.

leaf page init installs the page’s runtime and selected packages. The agent then authors its content using the HTML and components described in Pages.

leaf server start starts the page’s HTTP server and claims the page for the current agent session: that session receives its updates. The command returns a URL with an access key. The agent hands over the URL and ends its turn; the harness integration continues watching. 

leaf page init --package diagram ./review
# Write ./review/index.html with the harness's file tools.
leaf page check ./review --render
leaf page stamp ./review --text "Queue policy ready for review"
leaf status ./review waiting "Which queue policy fits the importer?"
leaf server start ./review

This example is a record meant to be revisited, so the agent reviews and stamps it before handoff. A quick page needs only leaf page check. Revisions defines valid saves, stamps and version addresses; Checks before a revision goes live describes validation.

Package instructions, evals, and an existing page

Each package adds instructions for its components, written for an audience such as the page's author. leaf page instructions ./review prints the packages' shared instructions as JSON, keyed by audience; leaf page instructions ./review --use lf-diagram | jq -er '.author' prints how to author a diagram.

The repository scores each change to these instructions with evals: cases a headless agent completes in Claude Code and Codex, run on the old and the new instructions.

To resume an existing page, the agent reads its active HTML and leaf page state ./review, which returns current state as JSON. leaf page claim ./review registers the current session as the recipient of the page's updates without starting its server. Starting the server also makes that claim.

Answer updates

A reaction records brief feedback on a passage or agent reply without opening a thread. The default reactions request keeping, changing, clarifying, shortening, supporting, or prioritizing content. Packages can declare additional reactions.

A browser comment or choice sends an HTTP request. Leaf validates it, appends it to the event log, and delivers it to the agent with thread context and instructions assembled from the registry. The harness supplies this JSON batch or an id to open with leaf delivery read.

For a comment requesting a policy change, the agent follows the delivery’s receipt instructions and first posts a progress message naming the work. This also starts the event, so the user sees which update it is handling. It then reads the current page and thread, revises the policy, and replies. This example posts replies through the CLI; harness routes describes when Leaf captures a turn’s messages instead. 

leaf response reply <answer.ref> --ephemeral --text "Checking the importer's queue policy."
leaf page state ./review
leaf page state ./review <thread-id>
# Revise ./review/index.html.
leaf response reply <answer.ref> --done --text "The importer policy is updated."
leaf status ./review waiting "Does the revised policy match the workload?"

A comment needs a thread reply. A decision widget creates an obligation on the user’s On me list, with a prompt, typed answer, and lifecycle; an optional lf-ask supplies its heading as the prompt. The widget owns the value, and the agent records the decision in a stamped revision. The browser fetches the revised HTML and state.

Example: answer a page choice

The page asks which queue policy to use with lf-options id="queue-policy" choose. When the user chooses Drop the oldest record, Leaf delivers that choice to the agent. The agent starts the choice event, reads the current choice, and revises the HTML to show the selected option: 

<lf-options id="queue-policy" choose>
  <lf-option id="drop-oldest" chosen>Drop the oldest record</lf-option>
  <lf-option id="block-producer">Pause the producer</lf-option>
</lf-options>

After checking and reviewing the result, the agent stamps the revision to record the decision. The stamped markup answers the choice event and ends its start: 

leaf task start ./review <event-id> "Recording the chosen queue policy"
leaf page state ./review
# Add chosen to the picked option in ./review/index.html; check and review.
leaf page stamp ./review --text "Queue policy: drop the oldest record"
Delivery fields and answer semantics

In a delivery requiring a thread reply, answer.parent is the message it threads under. The event's id identifies the update to start, and answer.responds identifies the update the reply answers. The example batch uses 9d41b20f for all three because the comment opens a new thread. A later message has its own event id within that thread.

A user comment requires a reply in its thread. A decision on a page widget requires a stamped revision. If the obligation's component declares a record form, the revised HTML uses it to show the decision, such as the chosen option. An obligation embedded in a thread message receives a thread reply, because that message's HTML is fixed. Resolving a thread or moving a card can require no answer; the agent still receives the event. A multi-select obligation submits the choice when the user presses Done.

A delivery is one JSON document, whose format field names its version. Its envelope contains one or more page batches, preserving the captured event order, thread context, and handling instructions. A delivery id supplied by the harness names this whole envelope; an event’s id names one recorded event. Harness connections and receipt describes how to read and confirm a delivery pointer. Data structures lists every field.

Reading Meaning for the agent
acknowledge The instruction for confirming receipt, or null when the harness confirms it.
page, through_seq The batch's page and captured log position.
subject, threads, says The affected page, thread or widget, its discussion context, and authored words for named gesture targets.
answer The response owed at capture, with its address and ref: a thread reply, whose writer is the agent or the turn’s final message, or a stamped markup revision.
Event handling Ordered clause ids to read in the batch's handling object.

The registry is Leaf's machine-readable definition of components and events. It declares event instructions under $events.handling and response instructions under $events.answering. Leaf combines the applicable clauses in the batch's handling object. The agent follows those clauses and reads current state before answering: a newer update may already have settled the response the captured batch requested. 

{
  "handling": {
    "h1": "Read the thread context before answering.",
    "h2": "Write the answer with leaf response reply using its answer.ref."
  },
  "events": [
    {
      "id": "9d41b20f",
      "kind": "comment",
      "handling": ["h1", "h2"],
      "answer": {
        "kind": "reply",
        "parent": "9d41b20f",
        "responds": "9d41b20f",
        "ref": "6ba31df0:0:9d41b20f",
        "writer": "agent"
      }
    }
  ]
}

The event's list selects h1 and then h2 from this batch. These ids belong only to that batch. The event id identifies the update being answered.

Change the live page

The agent can save HTML, replace a component’s data source, or report a component state change while the user reads. The browser fetches the revised document and state when the server reports a change (Freshness checks and state reads). 

leaf data set ./review queue-metrics --file ./metrics.json

Here, the declared source queue-metrics receives the complete value in metrics.json. For a component state change, leaf page report records its declared operation and fields. Saving HTML changes the live document; stamping adds a version address and changelog entry.

These changes preserve the user's recorded choices. If an edit changes what a decision was about, the author marks the component restated to invalidate that decision. The Revisions view explains how decisions survive page edits.

Threads explains anchors and how they survive revisions, drawings, titles, summaries, and the Threads list.

Source errors

A source error can leave the file on disk newer than the live page (Checks before a revision goes live). Read leaf page state alongside the active HTML to check which revision the user sees.

Wait for updates or finish

leaf status ./review waiting says the agent needs more from the user. The harness integration keeps watching after the turn ends and sends later updates back to the same session.

leaf status ./review idle marks the page finished and stops watching it. Leaf refuses it while an update awaits receipt or an answer, or an agent to-do is open. If the agent ends a turn with a delivered update unanswered, the Stop hook tells it so (Stop hook checks).

Background work and durable to-dos

Work longer than a few minutes runs in background workers, whose results start another agent turn.

leaf task start names the update or to-do the agent is handling in this turn, and a reply or stamped decision answers the update. Work that outlasts the turn, or that no update asked for, gets a to-do, which stays open across replies, revisions and sessions until the agent ends it. The agent opens it on a thread, a widget that takes to-dos, or the whole page, and starts it with the id leaf task open prints: 

leaf task open ./review page "Check the importer policy"
leaf task start ./review <todo-id> "Checking the importer under load"
# Run the check and put its result on the page.
leaf task end ./review <todo-id> done "The load check is recorded on the page"

A to-do ends as done, failed, or dropped, with a note saying where its result is or why there is none. A stamp with --completes <widget-id> ends every open to-do on that widget as done. Until then the to-do stays on the agent's list, On Claude.

Stop hook checks

When the agent ends a turn, Leaf’s Stop hook checks its pages for unanswered updates and delivery between turns. Claude Code shows a reminder as context, not an error. A new update normally opens a turn of its own after this one ends, preserving this turn’s final message as its answer. Where nothing watches afterward, as with Claude Code’s plain --print or a Codex task waiting with leaf wait, or where the next turn would open on a message in the user’s name, as with Codex’s codex queue, an update needing an answer enters the current turn instead. An update needing no answer waits for the next turn.

  • An update started in this turn lets the turn end. Long work runs in background workers whose results start a later turn, so the Stop hook doesn't hold a turn open for an update the agent started in it. The update reads Working, with the agent's line beside it, until the next turn answers it or starts it again; otherwise it soon reads Update stale.
  • Between turns, a page needs a watcher: Claude Code's or Pi's watch hook, a leaf wait, or Codex's adapter. Without one, the user's next update waits in the event log until the agent's next turn, which in Claude Code Leaf starts by messaging the session. A closed page or a developer's preview needs no watcher.

Harness connections and receipt

Claude Code’s background Stop hook watches between turns and wakes the agent; its prompt hook puts the update into the new turn. Codex’s adapter queues the update as the next message, or starts a turn when Leaf is an App Server client. Pi’s experimental extension runs inside Pi. Each route supplies the same delivery format and says who confirms receipt.

  1. Confirm receipt separately from transport. Leaf counts an update as received only when the agent or harness confirms it. A harness discards output from a timed-out hook, so the hook confirms well before its deadline and passes a complete delivery into the turn only after confirmation.
  2. Use a pointer when the whole delivery cannot fit or be confirmed. A delivery too large for the turn’s context, or one the hook could not confirm in time, arrives as an id. leaf delivery read <delivery-id> confirms nothing; the agent follows every next command, then runs leaf delivery ack <delivery-id> as the envelope’s acknowledge field directs.
  3. A direct wait confirms on its next call. A Codex task running its own wait uses leaf wait --ack <delivery-id>. Until then, the events remain available to the next wait, in case output was lost or cut off. Stages of an update names the evidence for Delivered on each route.
Harness / route Updates and answers
Claude Code Hooks supply updates when a turn starts or ends, and wake the session between turns. The hook confirms a delivery it passes whole.
Pi (experimental) Leaf's extension checks the session's pages as each run settles and puts the delivery in a new run, or in the current run after its tool calls. The extension confirms a delivery it passes whole.
Codex queue Leaf’s adapter queues a delivery pointer for the next turn. During work, hooks pass complete inline input or a pointer. The delivery’s acknowledgement instruction distinguishes transport confirmation from complete receipt.
Codex App Server Leaf starts an agent turn with the updates and confirms receipt. When a reply’s answer.writer is turn, its opening posts as progress and its final message becomes the thread reply. A reply whose writer is agent uses the reply command.
Direct wait Without a hook integration, leaf wait prints the delivery in the current turn, and the next leaf wait --ack confirms it and waits again.

On every route the agent can answer with leaf response reply <answer.ref>. One task can receive updates by several routes, and each delivery says how to confirm it and how to answer.

Claude Code integration

leaf hook handles Claude Code's prompt and Stop hooks, and leaf session-end releases the session's pages. A background Stop hook runs leaf hook --watch and wakes the session when an update arrives.

Leaf reads Claude Code's session registry to tell whether a session is busy, waiting or idle. If nothing is watching the page, Leaf can message the session through its socket, or resume a retired background session with claude --bg --resume. The socket accepting a message doesn't show that the agent read it.

Codex entry points and the public website

leaf server start connects the page to the current Codex task. leaf codex start ./review connects delivery when claiming a page without serving it. The desktop app uses the queue route, even though it runs an App Server internally.

leaf codex launch starts a terminal client with a private App Server and sets LEAF_CODEX_APP_SERVER for the task. Leaf can connect to that endpoint; this terminal route is experimental.

On leaf.page, the website host starts a Codex task over App Server for each page a visitor changes. The hosted agent answers deliveries on that page rather than starting a new one. The website describes how the site serves pages.

Owning contracts

The delivered event batches reference owns the envelope and handling lookup. Conversation loop owns to-dos, starts, statuses, and the response loop.

Harness routes are specified in Claude Code, Codex, and Pi. Session lifetime owns the hooks, adapters, and App Server protocol behind them. Page storage owns revisions and browser replacement.

Parts of a page

The agent writes an HTML document containing the page's title, description, content, and layout. When the server delivers it, Leaf adds the page identity, visual theme, browser JavaScript, and canonical URL. The browser runtime supplies the commenting and collaboration interface. Authors build the content with these tools, starting with ordinary HTML:

  1. Ordinary HTML. Leaf styles headings, paragraphs, tables, code, and details without requiring CSS classes. These elements provide most of a page's content.
  2. Theme classes. Leaf supplies classes for common presentation patterns, including .eyebrow, .lede, .callout, aside.sidenote for a margin note, and ol.steps for a numbered sequence like this list.
  3. Widgets. Leaf widgets are custom HTML elements, such as <lf-options> for choices and <lf-board> for cards in columns. Other lf-* elements provide structure, such as <lf-pane> for a pane. The registry declares each element’s attributes and behavior using JSON Schema. The browser, validator, and agent instructions read those same declarations.
  4. Page-specific presentation. A local <style> and inline SVG can define arrangements and drawings specific to the page. They use the theme's shared color and type tokens to stay consistent with the rest of Leaf. The Layout tab's drawings use this approach.

Interactive components load their JavaScript modules when the page uses them. Behavior specific to one page can use inline module scripts or local modules under page/. Reusable behavior belongs in a package, a directory containing components and their supporting files. The page-behavior reference defines module and dependency rules.

Runtime and packages

Each page directory contains its own copy of Leaf's runtime and selected packages. This validated composition is called its layer. page init builds it. Each revision captures the layer it uses. Updating the installed plugin does not rewrite those captured bytes; serving a captured revision still requires a compatible page protocol. The package contract defines how packages are combined and replaced.

Leaf's core, called the kernel, supplies the browser runtime, shared controls, and collaboration protocol. Packages supply reusable elements, JavaScript modules, styles, and authoring instructions. The default package provides common components; optional packages add capabilities such as diagrams and diffs. Project packages use the same format and can replace or extend the page's selected layer. The extension guide lists the bundled packages and demonstrates a small custom package.

Widgets

These examples are interactive parts of this page. Their choices, card moves, and comments share its event log, Undo, and On me. Each activity feed shows the same page history, including actions in other examples.

The component catalog also includes diagrams, charts, diffs with collapsible files, annotated code, editable drafts, playgrounds, and recorded browser traces. The examples gallery opens complete pages using them.

Styles and overrides

A page’s <style> changes that page; a theme package shares styles across pages. Theme packages declare no widgets. Their ordinary rules override Leaf’s defaults and Layouts, and the page’s rules override the theme. Generated controls require the explicit access below; shadow trees have their own tiers.

To change Write
Leaf's colors :root { --accent: teal; }
A Layout's width :root { --col: 46rem; }
A widget lf-card { padding: 8px; }
Controls Leaf or a widget builds <style data-controls>lf-board .lf-grip { color: teal; }</style>

A Layout reads tokens such as --col, --sidebar and --page-pad-start, and any other rule changes it too, such as main { padding-top: 28px; }.

A bare button or input rule styles the page’s own controls. To reach controls Leaf or a widget builds, a page marks its stylesheet data-controls; a theme package puts those rules in controls.css. Widget packages already style their own controls through theme.css. Leaf’s panel and thread cards also inherit theme inputs such as --accent and --sans from :root.

Which rule wins

Leaf sorts CSS into tiers by who wrote it. The tiers are CSS cascade layers (@layer), and a rule in a higher tier wins. Each switch below puts the rule beside it into the tier its page or package writes into, for the same card, so the card shows what the browser decides.

A lower tier's rule loses however specific its selector is, as the widget package's :scope.featured shows. Within a tier, the more specific selector wins; between equally specific selectors, a widget package's rule, scoped to its widget, beats an unscoped one; after that, the later rule wins. !important reverses the order of the tiers, so a page's !important loses to Leaf's own; an ordinary rule is all an override needs.

Writing a package's styles

A widget package styles its own widgets in its theme.css, where :scope names the widget itself and ordinary selectors name what it contains, and reaches nothing outside them. Its shadow.css reaches the private parts inside each widget's shadow tree. A theme package's shadow.css reaches the same parts from the tier above. The package reference lists the supported tokens.

Layouts

Leaf supplies page layouts and a layout for blocks within a page. A column, sidebar, or workspace sets the page’s shape; tiles arrange a block’s children and can be used within any of them. The table and drawings below show the same classes in the same order.

Class Arrangement
layout-columnPage layout Text in a centred 720px column; figures, boards and tables may extend past it. Suits plans, reviews and explanations, including this page.
layout-sidebarPage layout A body beside a narrower side column, with the header across both, as wide as the window up to 1600px. A board and its status, a release dashboard, or a review with its verdict beside the diff.
layout-workspacePage layout Task regions kept together: a queue beside its selected item, or controls beside a preview. In a large window, the workspace fills the height and its panes scroll separately.
layout-tilesBlock layout Equal cells, as many to a row as fit. A row of metrics or status tiles.

Leaf's Layout classes are ordinary CSS, applied beneath the page's own stylesheet in the cascade. A page can adjust them with CSS rules, for example to change a column's share of the width or a gap. It can also use its own grid when the supplied layouts do not fit.

The reading column

On a layout-column page, headings, paragraphs, lists, and code occupy a centred column up to 720px wide. On a sidebar page too, the theme limits paragraphs, list items, and headings to that reading width. A workspace sets no reading width, and none of the widths below: every block fills the pane it stands in.

A diagram, board, or wide table can extend into the margins beyond the reading column. The text above and below it keeps its width and position. These width settings control the block:

  • column is the text measure. In a wider region, such as a sidebar page's body, a column component starts at the same left edge as the text.
  • wide extends up to 1080px. Wide blocks share this width so they align with one another.
  • available uses the window's width after subtracting the outer page margins and space for margin notes and controls.

The registry, which declares each component's behavior, also gives it a default width. For example, lf-options uses column, lf-board uses wide, and lf-diagram uses available. A data-width attribute asks for wide or available on any block, overriding the default. If the margins have unequal space, the block extends farther into the wider margin. A table given a width takes its columns' natural width up to that room rather than spreading across it.

A log, feed, or long listing with data-bound scrolls within a limited height and opens at its newest entry. Its growing content therefore does not make the whole page longer.

Margins

A sufficiently wide window places these controls and notes beside the reading column:

  • The rail, on the right, where Leaf places a marker beside each commented or decided passage. It needs a window about 960px wide, or about 1010px on a touch screen.
  • A sidebar, the page's first aside.sidebar, on the left. It holds a table of contents, a legend or reference facts, and stays in view at the window's top as the page scrolls. It needs about 1130px.
  • Sidenotes, each an aside.sidenote, on the right, level with the block they annotate. They need about 1150px.

The column shifts sideways to make room for a sidebar or sidenotes. In a narrow window, those notes appear within the column at their original positions in the HTML.

Sidebar pages

layout-sidebar on main places the header across the top, with a body and a narrower side column below it. The page fills the window up to 1600px, with an outer margin that grows from 24px to 64px, and uses a larger title than a column page. Its blocks and title share a left edge, while paragraphs still wrap at 720px.

The side column is an aside; placing it before or after the body in the HTML puts it on the left or right. The regions stack in HTML order below about 870px, or when the body's content needs the full width, such as a board with many columns.

A side column made by layout-sidebar is part of that layout's content area. An aside.sidebar instead places a note in the margin of a column page. A section.panel groups a region by its compact heading and spacing, without a surrounding card. 

<main class="layout-sidebar">
  <header><h1>Release 4.2 rollout</h1></header>
  <div>…</div>      <!-- body: the work in progress -->
  <aside>…</aside>  <!-- side column: status, counts, contents -->
</main>

Examples: Live progress, Triage board, Command hub.

Workspace

layout-workspace fits the page to the window above Leaf's panel. A single-row header holds the title and status tags. The body takes the remaining height and contains an lf-pane, a component that arranges its own panes, or a grid of panes defined by the page's CSS. Each pane scrolls its content beneath its own header. A pane's footer stays visible, keeping its actions within reach.

An lf-tabs list="side" in the workspace body displays a list of tabs as a queue, such as tickets or findings. The selected item's content appears beside that list.

The workspace fills the window's height when the window is at least 720px wide and 480px tall. In a smaller window, panes expand to fit their content and the whole page scrolls. 

<main class="layout-workspace density-working">
  <header><h1>Payments alerts</h1></header>
  <div id="regions">
    <lf-pane label="Queue">…</lf-pane>
    <lf-pane label="Alert">…</lf-pane>
  </div>
</main>

<style>
  #regions { display: grid; grid-template-columns: 1fr 2fr; }
  @media (width < 720px) { #regions { grid-template-columns: 1fr; } }
</style>

density-working reduces type size and spacing for a compact working surface. It is independent of the Layout: a workspace can use ordinary reading sizes, and a pane or table on another page can use working density.

Examples: Notification playground, Merge a worktree, Alert review.

Tiles

layout-tiles arranges an element's children in equal cells at least 9rem wide, placing as many cells in each row as fit. Cells in the same row have equal heights. A page can set its own columns when it needs a particular grouping, such as four tiles in two rows of two. A row of headline numbers can use a layout-tiles block of native dl elements with labels in dt and values in dd.

Tabs and parts

An lf-tabs at the top of a page creates tabs like the ones on this page. Their tab strip stays at the window's top while the page scrolls, and one tab's content is visible at a time. All tabs share the page's width, Layout, threads, and version history.

When different parts of the work need different layouts, lf-parts holds an lf-part for each. Each part contains its own layout container; main itself carries no Layout. For example, one part can hold an interactive workspace and another a proposal read in a column. Parts share the page’s history, threads, and On me list. The page-layout reference gives the markup.

Panel, rail and thread cards

Leaf adds controls around the authored HTML. This interface is called chrome: the Leaf panel floating at the window's foot, comment and decision markers, and thread cards. At rest the panel is one row: the leaf, coloured by the agent's state; the comment field, which shows the agent's status while it is empty; and marks counting On me and Threads. The leaf opens a small menu of the page's other controls, and a mark opens its list as a view above the row. Folded, the panel is the leaf alone in the window's corner.

The On view shows one list at a time, under a tab named for its actor, with completed items under Done. On me and the agent’s list defines their membership. Opening a view preserves the page’s text wrapping and reading position.

The page leaves room at its foot for the panel's row, so its last lines scroll clear of it. A view opens above the row and covers the page beneath it without moving it; Escape or a press on the page puts it away. Phones and touch screens describes the panel on a touch screen.

The rail is the strip to the right of main where Leaf places comment and decision markers. It appears when the window has enough space: about 960px on a column page or about 1920px on a sidebar page. data-rail="right" keeps it visible above 640px, except on a workspace, whose panes scroll on their own. Where no rail fits, and inside a scrolling pane, a small pin appears beside the target on the page. Leaf places it clear of text and controls when space permits. The o shortcut hides pins and passage highlights.

A thread card opens beside its marker in the margin. If the margin is narrower than the card, it overlaps the text's edge. Threads, a thread opened from it, the On view and All pages open as views above the panel's row, one at a time.

Narrow windows

In a narrow window, page regions stack vertically in HTML order. Margin notes move into the reading column, a side column appears above or below its body, and workspace panes expand to fit their content. Tiles can still fit two per row on a 390px phone.

Current state

The active revision's HTML supplies initial values. Leaf applies recorded actions to those values on each read, keyed by [widget, unit, verb]: the widget, the part of its state being changed, and the operation. The latest action still in effect wins each key. leaf page state reports the result; the browser adds pending browser updates.

Every event enters the log through the same validation. Leaf checks widget actions against the registry and records their meaning at admission, so later readers need no surviving widget to interpret them. Undo appends an event identifying the action withdrawn. The event log reference follows a choice and undo through this computation.

External data

External values, such as benchmarks or build status, use one JSON publication per named source. leaf data set validates the value against the page’s declaration, records the contract beside the value in the source file, and replaces the publication atomically. Any process can call it. Leaf validates the value against the recorded contract on read and displays a source error for a mismatch.

A source replacement updates the open page without creating a revision; each publication holds its latest value. A later page revision may bind the source to another contract, which its next write takes. An lf-num instead freezes a number into authored text. It retains that number when the source changes, and leaf page check reports when its source has changed.

Revisions

When Leaf reads changed, valid page source or dependencies, it captures an immutable revision and makes it live. Identical captured inputs reuse a revision. leaf page stamp adds a changelog entry, a version number and a stable address such as /versions/v2.html. The live URL follows revisions; a tab displaying v1 stays on v1.

An open tab installs a live revision while preserving reading position and active controls, waiting where it would interrupt the user (Live revisions). A comment follows its passage, or its surviving section if the passage disappears. If neither can be identified, the thread detaches rather than choosing unrelated text.

An lf-approval widget requests permission for the action its heading and prose describe. Its approve action answers an ordinary widget obligation on On me; Undo approval reopens it. Each request is independent of other unanswered widgets and page stamps. Approval persists with the widget's id across unrelated edits. When the action or evidence changes enough to invalidate that permission, the author explains the change and marks the widget restated. A request that depends on another decision is presented after that decision, once the action to authorize is concrete.

Try Approve, then Undo approval. The request changes immediately, and the activity feed records the action and its withdrawal.

Checks before a revision goes live

Before making a revision live or stamping a version, Leaf validates the HTML structure, component declarations, dependencies, and recorded user decisions. An invalid save keeps the last valid revision live and reports the error. leaf page check --render additionally opens the page in Chrome in both color schemes to check for console errors, invisible components, and horizontal overflow.

Decisions across revisions

A pick or drag records a structured action, shown immediately and delivered alongside comments. Once accepted into the log, it survives reloads, other tabs, and later revisions. The event log reference shows how actions and undo determine current state.

An edit preserves recorded choices unless it explicitly changes their basis. The agent marks an affected element restated and explains why in the version note. Otherwise the choice still applies. Wording, labels, placement and vocabulary can change; the log keeps each action's original meaning.

z withdraws the user's latest action, saying what it takes and how long ago it was made. Where that action is out of view, or the agent has already picked it up, the first press shows it and the second takes it back. Each undo appends an event naming its target, so the recomputed result survives reloads.

Progress on an update and the page

Leaf distinguishes progress on one update from the page’s status. A busy agent has not necessarily started every comment. Its progress message or leaf task start names the update or to-do it is handling and the work it is doing. That line appears beside the relevant thread or widget and in the panel; replies carry the results.

A session is the agent conversation attached to the page; a turn is one run within it. A watcher receives updates between turns. The illustrative sequence below follows a request to shorten a lede; its times are examples, not delivery guarantees.

  1. 0s observation Sending → Sent The comment appears immediately as Sending. It reads Sent once the server accepts and records it.
  2. 1s observation Delivered The hook puts the comment into the agent’s turn, and the turn's next hook confirms the agent read it. Until the agent names its work, the page reads Claude working — has the comment.
  3. 5s intervention Working The agent posts leaf response reply <answer.ref> --ephemeral --text "Cutting the lede to two sentences.". The comment reads Working, and the same sentence becomes the page’s status.
  4. 1m intervention Each new phase gets a new line When the work moves from editing to checking, the agent starts the same update again: Claude working — checking the page at phone width.
  5. 2m observation Answered The revision goes live, the agent's reply reports it, and a waiting status names what the agent wants back: Claude awaits — does the shorter lede keep enough?

Status readings

The server combines the agent’s latest start or status with observed session, turn, and watcher activity. Browser tabs and leaf page state read that same result. All pages uses each serving page’s published activity summary.

  • The turn. The harness integration records when a turn starts and ends. Leaf treats it as active while its opening, a start, a status declaration, or a reported step is less than 15 minutes old. Claude Code also reports the session's activity directly, including permission dialogs and interrupted turns. An interruption can therefore mark the turn ended as soon as the user presses Escape.
  • The watcher. Claude Code's watch hook, leaf wait, or Codex's adapter registers with Leaf while watching for updates. Leaf treats the agent as available for updates while a watcher runs. A running Claude Code turn can also receive updates through its hooks.
  • The start. A start stops counting as active once it is 15 minutes old, or two minutes after the turn that wrote it ends, if that occurs sooner. This delay lets an immediately resumed agent renew its start before Leaf reports that the work stopped.

Leaf shows work as active when a start is still current, when the harness reports a step in an active turn, or when that turn has received input requiring an answer. The freshness rules above determine when a start or turn stops counting as active. Input is stalled if it remains Sent for two minutes, or if the turn that received it ends without answering. After about a minute, the status also shows the working reading's age, for example Claude working · 5m ago — running the browser suite.

Where the agent's messages appear

The agent writes progress messages, statuses, replies, and version notes. Leaf adds observations about delivery and activity. These commands reach different surfaces; starting work places its line both in the panel and beside the update or to-do.

Written by the agent

  • leaf response reply <answer.ref> --ephemeral Names the upcoming work in the user’s thread before reads or edits. It sets the page’s status and the comment’s Working label, then folds behind Show 1 progress message when the answer arrives.
  • leaf task start … <id> "…" Names the current operation for an update or to-do, such as Claude working — running the browser suite. Its line remains beside the thread or widget until answered or ended. The panel’s leaf and tab icon take the status’s colour; All pages repeats its line.
  • leaf status … waiting "…" Names the input wanted, such as Claude awaits — pick a layout, while a watcher or turn runs. It clears starts but keeps to-dos; it creates no item-level Working label. Without text it reads Claude awaits — select text to comment.
  • leaf status … idle The agent has finished with the page, and the status reads Page closed (Wait for updates or finish says when Leaf refuses it).
  • leaf response reply <answer.ref> Answers the user’s comment and clears its label. --done delivers the result; an lf-ask asks the user back; --todo promises work that stays on On Claude until ended.
  • leaf thread reply … <thread> A later message in a thread already answered, such as the result of work the first reply promised.
  • leaf response reply … --markup '<lf-ask>…' Opens a question on On me and makes the thread read My turn to answer. A reply or settling reaction answers it. The agent can end it with leaf task end as answered elsewhere or withdrawn.
  • leaf task open … --on user Puts a task such as trying a build on On me. m reaches it; its Done button, or x, ends it and tells the agent. A thread question has no Done button: the user’s reply answers it.
  • leaf thread open, leaf thread edit, leaf thread resolve A thread the agent opens on a passage, a message it corrects, marked edited, or a thread it closes (✓ Resolved by Claude).
  • leaf page stamp --text "…" Names a version and its note in Versions. The live page updates and the panel says Updated to v4. A tab on an earlier version stays there; its version notice offers Latest.

leaf page report records a component state change. A component supplied by an optional package can use these reports to show a background worker's progress.

When the agent says what it is doing

  • When an update arrives. The agent names the requested work before starting it, or answers immediately when no work is needed. Each delivery repeats this instruction beside the applicable events.
  • When the work changes. A new subject or phase—reading, editing, testing, or waiting on a result—gets a new line by starting the item again. Every start names its operation.
  • During long work. Background workers keep the agent free for the user’s next comment. The start names the running work beside its update; the agent renews it when a worker reports (Stop hook checks).
  • When it is the user’s turn. A waiting status names the answer or decision wanted.

The conversation loop reference is the agent's copy of these rules.

The work plan

For work with several steps, the agent can publish an outline in the On view’s Plan tab. It shows the goal, the current step, and later steps, including those waiting on the user. A step can name an existing to-do or obligation and follow its title, owner, and state, or carry a title and state the agent maintains.

Plan commands and lifetime

leaf task plan reads the complete outline from stdin. Depth 0 is the goal; each nested step is one level deeper. A plain step’s state is open, working, done, or dropped. 

leaf task plan ./review <<'EOF'
[{"depth": 0, "title": "Review the queue policy", "state": "working"},
 {"depth": 1, "item": "<todo-id>"},
 {"depth": 1, "item": "widget:queue-policy"}]
EOF

Rewriting the plan replaces its arrangement; an empty list clears it. Removing a to-do or obligation from the outline ends nothing. Work that must stay owed after the turn belongs in a to-do or obligation, which the plan references; a plain step creates no such obligation.

c, compose, send A reply leaves focus on its card or title; a page comment leaves it in the panel’s field. Escape keeps an unfinished draft.
Undo a resolution The thread reopens. If the panel has returned to Threads and the reopened row is shown, focus returns to it. If another thread is now open, that view stays put. An embedded thread retains its place.

Panels and Escape

Escape's next step depends on focus

A comment composer returns to its element; a reply box returns to its thread. In Threads, Escape clears a search before leaving it. Page-side selections, targets and margin cards can unwind while a desktop panel stays open. A covering panel must close before the page behind it is accessible.

m, c, Escape returns to the obligation and its option keys; another Escape lets it go. Commenting from an option or aiming at that obligation has the same return. A visual comment returns to its current response proxy. A whole-page comment stays in the panel’s field; closing a comment on selected words clears the selection.

Opening All pages or On me replaces the panel’s current view. Escape closes the new view rather than restoring the old one. Pointer and keyboard entry give the view the same Escape parent.

Back and Forward

A successful trip to a destination that is not fully readable adds a return stop. Consecutive trips share it while part of the preceding landing remains visible and the user has not clicked or Tabbed onto another passage. Back returns to the journey’s start. A fully readable destination adds no stop.

Which actions create a history entry?
Action History behavior
t, m, a marker, or Page Map reaches a hidden or clipped destination A successful trip pushes an entry, or replaces the current journey's entry. Changing focus alone adds none.
Click or Tab onto a different passage, then take another trip The reading choice ends the journey; the next offscreen trip saves that passage. Controls and runtime focus handoffs do not end it.
Scroll completely away from the last landing, then take another trip The new trip adds a separate return stop.
Follow a #fragment link The browser supplies a history entry. Leaf reveals the destination's enclosing tab or disclosure and lands on the named element.
Select a root page tab The switch saves the outgoing reading position and adds an entry; Back / Forward returns between views. Embedded tabs add no entry.
Scroll, search page text, align with g then z, open a panel, Escape, or resolve These actions add no reading-history entry themselves. Back neither undoes a resolution nor unwinds a panel.
Back / Forward returns Leaf restores the view and restores focus or selection where the saved nodes survive and remain visible. A newly hidden destination is revealed again. A newer gesture cancels a delayed return.

Enhanced return handling uses the browser’s Navigation API. Other browsers retain native traversal and fragment landing.

Phones and touch screens

Touch users can read, comment and operate widgets. Leaf’s page commands have direct gestures or visible controls; authored widgets supply their own routes. Narrow windows describes how page regions stack.

The panel and its menu

The panel fits a narrow window with space at its edges. Its row holds the leaf, a comment field showing agent status, and On me and Threads counts beside their icons. A temporary notice replaces the status words.

The leaf’s menu includes Search page and Page Map under Navigate, Undo, and Select element, Draw mode, Design mode and Hide annotations under Annotations. Approval requests appear in On me and in their widgets. An active mode or search names itself in the panel and provides a ✕ exit. Search arrows stand beside the match count; tapping the marked match selects it.

Comments, threads and widgets

Select words to quote them in the panel’s field; tap the field to open a comment below the block. For a whole table, figure or other element, use Select element.

Where the margin cannot hold a rail, markers appear as pins on their blocks. Tapping a pin highlights its passage and opens its thread card. Threads opens above the panel’s row. Hide annotations hides the pins.

On a touch screen, a board at most 640px wide shows a Move to row on each card, reaching offscreen columns without dragging.

Touch coverage and testing

  • Whole elements. Open the leaf’s menu → Annotations → Select element, then tap the target. This opens its comment composer without activating the target’s controls.
  • Commands. Menu commands and direct controls provide touch routes; the panel and reply fields suppress keyboard hints for a coarse pointer.
  • Exits. The panel’s ✕ leaves an active mode, search or target picker. Within the picker it first removes a typed hint prefix.
  • Hover detail. Authored hover explanations need a touch-accessible alternative; keyboard and hover behavior alone do not establish a touch route.
  • Layout. Page-authored controls and diagrams still need review at narrow widths for target size, legibility and reachable content.
  • Device coverage. Automated touch journeys use browser emulation; they do not establish real-device behavior.

Browser runtime

The browser runtime upgrades components, draws threads and shared controls, sends updates, and keeps the page current. Its inputs meet in one read-only state.

The server supplies actions in effect for the displayed revision, threads, obligations and activity (Current state). The browser applies them to authored values and adds only what pending gestures decide by themselves.

Loading the runtime

Startup prepares a stable page before enabling its controls. Page loading distinguishes usable controls from the arrival of saved state.

  1. Before first paint

    Small scripts reserve component geometry and panel space, capture early key presses, and provide a startup-failure notice. Late-arriving controls do not shift the page.

  2. Initialize and upgrade

    Start the state request, restore control arrangements and load the registry. Capture each component’s authored values before its module changes the DOM, then import modules for the tags the page uses.

Page loading

These stages describe the document, interface and saved state. JavaScript initialization and the state request overlap. Agent availability is independent; Progress describes whether the agent has received or started work.

  1. HTML and styles arrive

    Text, links and scrolling work. The panel appears when JavaScript starts.

  2. JavaScript initializes the interface

    Components and comment controls are being prepared.

    Panel: Loading…
  3. Comment controls are ready

    New comments and drawings appear immediately and remain Sending until accepted. Choices that change saved state wait for the server’s current reading.

    Panel: Loading saved state…
  4. Saved state arrives

    Saved threads and choices join the page, preserving new comments and drafts. Saved choices can now change.

    Panel: normal status; each comment keeps its delivery status

A pending state request remains Loading saved state; a failed read shows Offline. Connection failures describes retry behavior.

Pending browser updates

A pick, drag or comment enters an ordered pending list. Its result appears in the sending task, before the next frame: the option is selected, the card moves, or the comment appears as Sending (Stages of an update). Sent words leave the input but remain in the draft store until accepted.

Condition Browser behavior
Server unreachable Updates send one at a time, in gesture order. The local result stays drawn while the panel reports retrying, every two seconds. Keep the tab open: pending widget actions are not a durable queue.
Accepted or refused An accepted response carries the recorded event and current state. The entry leaves after every renderer showing it has drawn the server’s version. Refusal immediately removes the local result, explains why in the panel, and returns refused comment text to its input.
Which obligation changes appear immediately?

The server computes obligation completion from the whole log. A user’s answer changes the widget and its answer in the On view immediately; the obligation leaves the list when server state arrives. Replies to thread questions take effect locally at once. Thread turns also come from the server, with local adjustments for a comment being sent or refused.

Freshness checks and state reads

When What happens
Visible tab Freshness checks run roughly four times a second. The token covers page-file stamps, session and watcher presence, and neighboring pages in All pages. The request also records that someone is viewing the page. Hidden tabs pause checks and catch up when shown.
A read is running One state request runs at a time; changes queue one follow-up. Event responses also supply state. Log position and capture time let the tab discard older, late responses. A two-second clock refreshes displayed ages, retries failed reads and requests state when the server says activity is due to change.
Connection fails A failed first read leaves authored content and local comments available; state-dependent decisions wait. Later failures retain the last reading. The panel reports the loss and retries; a successful read applies normally. A request still pending remains Loading rather than Offline.

Drawing current state

Computing state and drawing it are separate. Components, threads, the obligation view, panel and page marks register as renderers. Each state has an epoch number. Renderers report when they have presented it; those reports stay outside state, so a slow or failed paint cannot change the facts.

A renderer may defer paint during an active drag or edit. These operations wait for presentation, not merely computed state:

Operation Presentation requirement
Apply server state Count it as applied and announce changes after every part has drawn it. A paint failure is reported; accepted state stays, and the next state triggers another attempt.
Release pending entry Every part drawing the update must show the server’s version first, so old state never flashes between the local result and server state.
Render check leaf page check --render waits the same way to judge the page the user sees.

Browser-owned state

Focus, scroll, selection, open disclosures, unsent text and active drags live outside shared state and the log. DOM nodes hold them; Data lifetime names browser stores preserving some across reloads.

Change Continuity
Node replaced The renderer’s existing identity matches its replacement. Threads keep reply text and caret; surviving component children keep focus.
Composer open Only a user action—Send, Cancel, Escape or a press elsewhere—or removal of its passage closes it. Scroll, resize, panel closure and server news leave it open.

Live revisions

A revision’s executable identity is its registry, loaded JavaScript modules and inline module scripts. Each install pairs the revision with its corresponding state.

Identity unchanged

Patch the document

Keep unchanged nodes; changed components recapture authored values. Prose, styles and media can update this way.

Identity changed

Load a fresh document

The new executable graph starts with the new document and its state.

What both paths preserve

Replaced elements with matching authored ids inherit local values differing from authored defaults: typed values, checked state, disclosures, inner scroll, focus and caret. Unidentified replacements carry nothing. Reading position follows a passage, not a pixel offset. Fresh documents use a one-time tab handoff that later reloads and Back do not replay; drafts and control arrangements use separate browser stores.

Installation waits during comment or reply writing, passage selection, card dragging, a pending update’s server response, or an open version menu. Latest in the version notice installs the waiting revision immediately.

Server lifetime

The HTTP server exposes the page directory to browsers. A session-started server stops when no live session claims the page; a claim names the recipient of its updates. A server started from a bare shell or with --persistent runs until leaf server stop.

On leaf.page, a private browser session gets a hosted agent environment using the same page and event machinery (How leaf.page works).

Addresses and access

A local session binds to loopback; an SSH session uses its SSH destination. A local server's URL includes an access key shared by every Leaf page on that machine. The browser keeps it in a cookie. Anyone with the key and network access can read and act on those pages.

For an unreachable address, restart with leaf server start PAGE --host NAME, naming a host the browser can reach. Leaf uses existing networks and creates no public tunnel. The serving reference covers addresses, authentication and lifetime.

Offline exports

leaf page export PAGE -o FILE captures a stamped version, its resources and recorded state in one HTML file. Reading controls and page-owned code work offline; new Leaf choices, comments, Undo and thread interactions need the served page. An agent need not be running to record a choice on a live server. Pages containing live samples cannot export.
