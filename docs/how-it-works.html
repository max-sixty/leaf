How leaf works

Leaf is an intermediary between your browser and the agent's harness. The harness is the software running the agent, such as Claude Code or Codex.

Typical flows

An agent writes a page that a user reads and responds to in a browser. Leaf stores the page and records comments and choices in its event log. It sends that feedback to the agent, which answers by revising the page or replying in a thread.

  Agent["Agent + harness"]
  Leaf["Leaf"]
  Browser["Browser"]
  Agent -- "files + CLI" --> Leaf
  Leaf -- "page + state" --> Browser
  Browser -- "feedback" --> Leaf
  Leaf -- "delivery" --> Agent

The harness is the application running the agent, such as Claude Code or Codex. It supplies tools and runs agent turns. Leaf connects a page to an agent session in that harness. The examples below follow an agent asking a user to choose a queue policy for an importer.

Publish a page

The agent creates a page directory and writes index.html: ordinary HTML for the page's content and layout. It can include Leaf components for choices, tabs, diagrams, and other interactions. In the commands below, ./review is that directory, relative to where the commands run.

leaf page init copies Leaf's browser JavaScript, styles, and selected component packages into the directory. When the server delivers the HTML, it adds the browser runtime. That runtime supplies comments attached to passages, drawing, thread panels, keyboard controls, and live updates. The Pages view shows how authored HTML and Leaf components fit together.

leaf server start starts an HTTP server for the page directory and registers the current agent session as the recipient of feedback. This registration is called a page claim. The command returns a URL containing the page's access key. The agent hands that URL to the user and ends its turn; the harness integration continues watching for feedback. 

leaf page init --package diagram ./review
# Write ./review/index.html with the harness's file tools.
leaf page check ./review --render
leaf page stamp ./review --text "Queue policy ready for review"
leaf status ./review waiting "Which queue policy fits the importer?"
leaf server start ./review

leaf page check --render checks the source and renders it for review. Once the server is running, saving valid HTML updates the open page. A stamp records a changelog entry and gives the current revision a version address such as /versions/v1.html. The agent reviews the rendered result before handing it over.

Packages and an existing page

A package contains components and their instructions. Initialization copies the selected packages into the page directory. leaf page instructions ./review lists the available instruction audiences; leaf page instructions ./review author --widget lf-diagram returns instructions for authoring a diagram.

To resume an existing page, the agent reads its active HTML and leaf page state ./review, which returns current state as JSON. leaf page claim ./review registers the current session as the page's feedback recipient without starting its server. Starting the server also makes that claim and connects feedback.

Answer feedback

A comment or choice in the browser sends an HTTP request to Leaf. Leaf validates the input, appends it to the event log, and sends the agent a delivery: a JSON batch of feedback with thread context and instructions for answering. The harness supplies either the batch itself or an id that the agent opens with leaf delivery read.

For a comment requesting a policy change, the agent reads the delivery and follows its receipt instructions. It then marks that thread as Working, so the user can see which input it is handling. The agent reads the current page and thread, revises the policy, and answers in the thread. This example uses a CLI command to post the reply; the harness routes below explain when Leaf captures a turn's messages instead. 

leaf status ./review working "Checking the importer's queue policy" --on <thread-id>
leaf page state ./review
leaf page state ./review <thread-id>
# Revise ./review/index.html; check and review the result.
leaf page check ./review --render
leaf page stamp ./review --text "Importer now drops the oldest queued job"
leaf thread reply ./review --for <event-id> --text "The importer policy is updated."
leaf status ./review waiting "Does the revised policy match the workload?"

A comment receives a thread reply. A page can also contain an Ask: a component requesting a user decision, such as a choice between queue policies. The agent records that decision in a stamped revision. The browser fetches the updated HTML and current state, so the user sees the result on the same page.

Example: answer a page choice

The page asks which queue policy to use with lf-options id="queue-policy" choose. When the user chooses Drop oldest, Leaf delivers that choice to the agent. The agent marks queue-policy Working, reads the current choice, and revises the HTML to show the selected option: 

<lf-options id="queue-policy" choose>
  <lf-option id="drop-oldest" chosen>Drop oldest</lf-option>
  <lf-option id="block-producer">Block the producer</lf-option>
</lf-options>

After checking and reviewing the result, the agent stamps the revision to record the decision. --completes queue-policy ends the work claim on that component: 

leaf status ./review working "Recording the chosen queue policy" --on queue-policy
leaf page state ./review
# Add chosen to the picked option in ./review/index.html; check and review.
leaf page stamp ./review --text "Queue policy: drop oldest" --completes queue-policy
Delivery fields and answer semantics

In a delivery requiring a thread reply, answer.to is the thread id used to read the conversation and mark its work as Working. answer.for is the event id used to answer the specific input. The example batch uses 9d41b20f for both because the comment opens a new thread. A later message has its own event id within that thread.

A user comment requires a reply in its thread. A decision on a page Ask requires a stamped revision. If the Ask's component declares a record form, the revised HTML uses it to show the decision, such as the chosen option. An Ask embedded in a thread message receives a thread reply, because that message's HTML is fixed. Resolving a thread or moving a card can require no answer; the agent still receives the event. A multi-select Ask submits the choice when the user presses Done.

A delivery uses the leaf-delivery-v3 JSON format. Its envelope contains one or more page batches, preserving the captured event order, thread context, and handling instructions. A delivery id supplied by the harness names this whole envelope; an event's id names one recorded input. The agent opens a delivery pointer with leaf delivery read <delivery-id>.

Reading Meaning for the agent
carrier, acknowledge The receipt and reply contract, and who confirms receipt.
page, through_seq The batch's page and captured log position.
subject, threads, says The affected page, thread or widget, its discussion context, and authored words for named gesture targets.
answer The response owed at capture: reply, turn, or markup, with its address.
Event handling Ordered clause ids to read in the batch's handling object.

The registry is Leaf's machine-readable definition of components and events. It declares event instructions under $events.handling and response instructions under $events.answering. Leaf combines the applicable clauses in the batch's handling object. The agent follows those clauses and reads current state before answering: newer feedback may already have settled the response the captured batch requested. 

{
  "handling": {
    "c1": "Read the thread context before answering.",
    "c2": "Write the answer in the thread with leaf thread reply."
  },
  "events": [
    {
      "id": "9d41b20f",
      "kind": "comment",
      "handling": ["c1", "c2"],
      "answer": {
        "kind": "reply",
        "to": "9d41b20f",
        "for": "9d41b20f"
      }
    }
  ]
}

The event's list selects c1 and then c2 from this batch. These ids belong only to that batch. The event id identifies the input being answered.

Publish updates

The agent can update the page while the user reads it. It can save valid HTML, replace a data source that components read, or use a Leaf command to change a component's state. The browser polls the server for changes and fetches the updated document and state. 

leaf data set ./review queue-metrics --file ./metrics.json

Here, queue-metrics is a data source declared by the page, and metrics.json supplies its complete new value. For a component state change, leaf page report records an event using that component's declared operation and fields. An HTML save updates the live document; leaf page stamp adds a version address and changelog entry.

Updates preserve the user's recorded choices. If an edit changes what a decision was about, the author marks the component restated to invalidate that decision. The Revisions view explains how decisions survive page edits.

Threads explains passage anchors, replies beside the page, and the Threads panel, with a practice exchange.

Document replacement and source errors

When only HTML and styles change, the browser updates the open page in place. Changes to the component registry or JavaScript replace the document and restore supported reading and editing state. Leaf waits for text composition, dragging, and pending user actions to finish before applying an update.

If an HTML edit is invalid, Leaf keeps the last valid revision live and reports the error to the agent and browser. The file on disk can therefore differ from the page the user sees. The agent reads leaf page state alongside the active HTML to check that distinction.

Wait for feedback or finish

The agent uses leaf status ./review waiting when it needs more feedback. The harness integration keeps watching after the agent's turn ends and sends later input back to the same session. For longer work, a background worker can produce results while that session stays available to receive feedback.

leaf status ./review idle marks the page finished and stops its feedback watch. Leaf refuses this command while input still needs receipt confirmation or an answer. A page marked Waiting keeps watching for new input.

Background work and completing a claim

Work longer than a few minutes runs in background workers, whose results wake another agent turn. A developer can also open a claimless preview: a page that records practice interactions without sending them to an agent session.

Marking a thread or component Working creates a work claim, which associates the work with that input. A reply in the thread completes its claim. A component's claim continues through unrelated revisions; the stamp that completes its work names it with --completes. 

leaf page stamp ./review --text "Queue policy recorded" --completes <widget-id>

Harness differences

The page and feedback model stays the same across harnesses. The integration determines when feedback enters an agent turn, who confirms its receipt, and how the reply reaches the page. Starting the page server normally selects and connects the appropriate integration automatically.

Harness / route Feedback and answers
Claude Code Harness hooks supply feedback when a turn starts or ends and wake the session between turns. After reading the delivery, the agent confirms receipt with leaf delivery ack and answers with leaf thread reply.
Codex queue Leaf's adapter queues a delivery id for the next turn; a tool hook can supply one during work. The adapter confirms queued receipt. For a tool-hook delivery, reading the id confirms receipt. The agent posts its answer with leaf thread reply.
Codex App Server Leaf starts an agent turn with the feedback and confirms receipt. That turn's opening and final messages become the thread reply. Feedback from a tool hook uses leaf thread reply.
Direct wait Without a hook integration, leaf wait prints the delivery in the current turn. The next leaf wait --ack confirms receipt and waits again; the agent uses leaf thread reply.

One task can receive feedback through several routes. Each delivery states how to confirm receipt and how to answer, so the agent follows those instructions for the input it has received.

Claude Code integration

A hook is code the harness invokes at a lifecycle boundary. leaf hook handles prompt and Stop events; leaf session-end releases session ownership. The background Stop wrapper runs leaf hook --watch and wakes the session when feedback arrives.

Leaf reads Claude Code's session-registry JSON for busy, waiting, and idle observations. If the background watch has stopped, it can send an authenticated message through the session socket or resume a retired background worker with claude --bg --resume. Socket acceptance does not prove the agent read the input.

Leaf checks the pages the session holds when a turn ends. In Claude Code, the Stop hook can deliver new input owed an answer into that turn or remind the agent of an unanswered input or missing watcher. It reminds once for the same obligation; if the turn ends again, the next turn receives the outstanding input. A claim made in this turn lets the turn end while its work continues.

Codex entry points and the public website

leaf server start connects the page to the current Codex task. leaf codex start ./review connects delivery explicitly when claiming a page without serving it. The desktop app uses the durable queue route even though it runs an App Server internally.

leaf codex launch starts a terminal client with a private App Server and sets LEAF_CODEX_APP_SERVER for the task. Leaf can connect to that endpoint; this terminal route is experimental.

On leaf.page, the site initially serves a published page at the edge. Interaction activates a private page served by Leaf's Python server, and the website host starts its Codex task over App Server. The hosted agent inherits the page and handoff; it responds to deliveries rather than initializing another page.

Transport details and automatic calls

The envelope's acknowledge and each event's answer.kind determine the operations for that delivery. An App Server task can still receive a queued delivery with a plain reply answer. A direct wait is refused while an adapter holds the task's watch. An open page proves the server is reachable; the label beside each move reports whether the agent picked it up. Unconfirmed input remains available for a later delivery.

For a turn answer, Leaf streams the agent's first user-facing message into the addressed thread, then commits that opening together with the final message. On the Claude Code and Codex queue routes, chat messages stay in the host; the agent writes the page answer with leaf thread reply.

The integration runs the hook commands above automatically. Its private child commands are leaf codex run for the detached adapter and leaf server _serve for the page server. The agent uses the public start commands to launch them.

The harness invokes leaf hook for prompt and Stop events, plus Codex's tool and interrupt events; leaf session-end releases session ownership. Claude Code's background wrapper runs leaf hook --watch and returns an async wake when input arrives. 

codex queue --thread <task-id> --message <delivery-pointer>
claude --bg --resume <session-id> <wake-message>
# The experimental terminal launcher starts:
codex app-server --listen <endpoint>
codex --remote <endpoint>
# Leaf starts private children with a readiness handshake:
python -m leaf codex run --codex-path <path> --handshake <fd>
python -m leaf server _serve <page> --handshake <fd>

These are internal invocation shapes. The parent supplies the private handshake descriptor and any route-specific flags.

The App Server channel carries JSON requests, responses, and notifications over a local WebSocket. Connection setup uses initialize and initialized. The adapter resumes the task with thread/resume, reads recovery history with thread/turns/list, and starts feedback with turn/start. The website host also uses thread/start and turn/interrupt. Feedback enters turn/start as a tool output, with these parameters: 

{
  "threadId": "<task-id>",
  "clientUserMessageId": "<delivery-id>",
  "input": [],
  "toolOutput": {"name": "leaf_delivery", "output": "<envelope JSON>"},
  "turnTrigger": "leaf"
}

Incoming turn/started, turn/completed, thread/status/changed, plan and item updates, message deltas, and tool progress provide activity and reply evidence. Approval and user-input requests tell Leaf the turn is waiting; the harness owns those dialogs. The private child handshake above proves process readiness, not receipt of a user's feedback.

Thread naming makes a separate model request: claude -p with Haiku, or config/read, thread/start, and turn/start for an ephemeral App Server thread. It receives the opening comment and passage, returns a title, and runs beside the answering turn.

Owning contracts

The delivered event batches reference owns the envelope and handling lookup. Conversation handoff owns statuses and the response loop.

Harness routes are specified in Claude Code, Codex queue delivery, and Codex App Server. Page storage owns revisions and browser replacement.

The agent says what it is doing before it does it

The agent writes a status before starting each step, naming the work and its subject. The banner at the top of the page shows that status. A status attached to a thread or component also appears beside it. The agent's replies carry the discussion and results.

An agent session is the conversation attached to the page in a harness such as Claude Code or Codex. A turn is one run of the agent within that session. A watcher is the background integration that receives feedback between turns.

Sent You comment on the lede. The page shows your comment at once, marked Sent. Picked up The agent reads your comment in its turn and confirms receipt. Your comment reads Picked up, and until the agent writes its own words the banner reads Claude working — on your update. The work is named Before doing the work, the agent writes leaf status … working "cutting the lede to two sentences" --on <thread>, which puts that line beside the thread and in the banner, and your comment reads Working. Each new phase gets a new line When the work moves from editing to checking, the agent writes the status again: Claude working — checking the page at phone width. Answered The revision goes live, the agent's reply reports it, and a waiting status names what the agent wants back: Claude awaits — does the shorter lede keep enough?

Written by the agent

  • leaf status … working "…" What it is doing, in the banner: Claude working — running the browser suite. With --on, the same line stands beside that thread or widget until the agent answers there. The tab icon takes the banner's colour, and the page's row in the Leaves drawer repeats the line.
  • leaf status … waiting "…" What it wants from you, as in Claude awaits — pick one of the two layouts, shown while a watcher runs or the agent's turn does. With no sentence the banner invites a comment: Claude awaits — select text to comment.
  • leaf status … idle The agent has finished with the page, and the banner reads Leaf closed. Leaf refuses it while input of yours has not been picked up or a picked-up move still has no answer.
  • leaf thread reply --for … An answer in your thread, which clears the label beside your comment.
  • leaf thread reply … <thread> A later message in a thread already answered, such as the result of work the first reply promised.
  • leaf thread reply … --awaits A question for you. The thread reads On you to answer, and the question joins the Asks drawer.
  • leaf thread open, leaf thread edit, leaf thread resolve A thread the agent opens on a passage, a message it corrects, marked edited, or a thread it closes (✓ Resolved by Claude).
  • leaf page stamp --text "…" A named version and its change note. The page updates in place, the status line says Updated to v4, and the text joins the versions menu as that revision's note. While you read an earlier revision, a chip offers the new one: New page available → open v4.

leaf page report records a component state change. A component supplied by an optional package can use these reports to show a background worker's progress.

Written by Leaf beside your input

A label beside each comment, choice, or drag reports its delivery and response status. It clears when the agent answers with a reply or revision.

When the agent writes one

  • When your input arrives. Your comment comes before the work in hand: the agent names the work it asks for before starting it, or answers at once when it asks for none. Each delivery repeats these steps to the agent beside the events they apply to.
  • When the work changes. A new subject, or a new phase such as reading, editing, testing, or waiting on a result, gets a new line. leaf status refuses working with no sentence, since the banner already says that the agent is working.
  • During long work. Work longer than a few minutes goes to background workers, so the agent stays free to answer your next comment. Its status names what is still running, beside the move the work answers, and it writes it again when a worker reports (when the agent's turn can end).
  • When it is your move. A waiting status names the answer or decision the agent wants, rather than saying that it is waiting.

The conversation loop reference is the agent's copy of these rules.

How Leaf decides what the banner says

The banner combines the agent's last status with observed activity: whether the session is running, whether a turn is active, and whether an integration is watching for feedback. The server computes this activity, so browser tabs and leaf page state report the same result. The Leaves drawer lists other pages using the activity summaries their servers publish.

  • The turn. The harness integration records when a turn starts and ends. Leaf treats it as active while its opening, a status update, or a reported step is less than 15 minutes old. Claude Code also reports the session's activity directly, including permission dialogs and interrupted turns. An interruption can therefore mark the turn ended as soon as the user presses Escape.
  • The watcher. Claude Code's watch hook, leaf wait, or Codex's adapter registers with Leaf while watching for feedback. Leaf treats the agent as available for input while a watcher runs. A running Claude Code turn can also receive feedback through its hooks.
  • The status. A working status and each --on line stop counting as active after 15 minutes without an update. They also stop two minutes after the turn that wrote them ends, if that occurs sooner. This delay lets an immediately resumed agent renew its status before Leaf reports that the work stopped.

Leaf shows work as active when a working status is still current, when the harness reports a step in an active turn, or when that turn has received input requiring an answer. The freshness rules above determine when a status or turn stops counting as active. Input is stalled if it remains Sent for two minutes, or if the turn that received it ends without answering. After about a minute, the banner also shows the status's age, for example Claude working · 5m ago — running the browser suite.

Every valid save is a revision

Every changed, valid save of index.html creates an immutable revision containing the HTML and its local dependencies. That revision becomes live immediately. leaf page stamp gives a revision a version number and a stable address, such as /versions/v2.html. The live URL follows new revisions; a browser tab displaying v1 stays on v1.

Leaf preserves the reading position when it updates an open page. It waits while the user is composing text, dragging, or undoing, while a user action is awaiting the server's response, or while the version menu is open.

A page requesting approval includes <meta name="lf-review" content="sign-off">. A stamped version with this declaration offers an approval control in the banner. The control becomes available after the user has answered every Ask, the components requesting decisions on that page.

Checked before it goes live

Before making a revision live or stamping a version, Leaf validates the HTML structure, component declarations, dependencies, and recorded user decisions. An invalid save keeps the last valid revision live and reports the error. leaf page check --render additionally opens the page in Chrome in both color schemes to check for console errors, invisible components, and horizontal overflow.

Your choices survive revisions

Dragging a card or choosing an option records a structured action in the event log. The browser shows the action immediately, and the agent receives it alongside comments. The recorded choice survives reloads, other browser tabs, and later revisions. The event log reference shows a choice and its undo, and how Leaf computes their result.

An edit normally preserves recorded choices. If the edit invalidates a decision, the agent marks the affected element restated and explains the change in the version note. Without that declaration, the recorded choice still applies. Leaf rejects a revision that contradicts it.

The z shortcut withdraws the user's last undoable action. Repeating it withdraws earlier actions. Each undo appends an event naming the action being withdrawn; the browser recomputes the result without that action. Reloading the page therefore preserves the undo.

A reaction records brief feedback on a passage or agent reply without opening a thread. The default reactions request keeping, changing, clarifying, shortening, supporting, or prioritizing content. Packages can declare additional reactions.

What a page is made of

The agent writes an HTML document containing the page's title, description, content, and layout. When the server delivers it, Leaf adds the page identity, visual theme, browser JavaScript, and canonical URL. The browser runtime supplies the commenting and collaboration interface. Authors build the content with these tools, starting with ordinary HTML:

  1. Ordinary HTML. Leaf styles headings, paragraphs, tables, code, and details without requiring CSS classes. These elements provide most of a page's content.
  2. Theme classes. Leaf supplies classes for common presentation patterns, including .eyebrow, .lede, .callout, aside.sidenote for a margin note, and ol.steps for a numbered sequence like this list.
  3. lf-* components. Custom HTML elements add interaction, such as <lf-options> for choices and <lf-board> for cards in columns. The registry declares their attributes and behavior using JSON Schema. The browser, validator, and agent instructions read those same declarations.
  4. Page-specific presentation. A local <style> and inline SVG can define arrangements and drawings specific to the page. They use the theme's shared color and type tokens to stay consistent with the rest of Leaf. The Layout tab's drawings use this approach.

Interactive components load their JavaScript modules when the page uses them. Behavior specific to one page can use inline module scripts or local modules under page/. Reusable behavior belongs in a package, a directory containing components and their supporting files. The page-authoring reference defines module and dependency rules.

Widgets you can operate

This page uses Leaf's own theme and components. Each example is wrapped in lf-sample, which marks it as an illustration. An example choice is therefore distinct from a decision the page is asking the user to make.

The component catalog also includes diagrams, diffs with collapsible files, annotated code walkthroughs, file trees, timelines, metric rows, milestone plans, and command interfaces. The examples gallery opens complete pages using them.

Runtime and packages

Each page directory contains its own copy of Leaf's runtime and selected packages. This validated composition is called its layer. page init builds it. Each revision captures the layer it uses, so an installed plugin update cannot change a version already approved. The package contract defines how packages are combined and replaced.

Leaf's core, called the kernel, supplies the browser runtime, shared controls, and collaboration protocol. Packages supply reusable elements, JavaScript modules, styles, and authoring instructions. The default package provides common components; optional packages add capabilities such as diagrams and diffs. Project packages use the same format and can replace or extend the page's selected layer. The extension guide lists the bundled packages and demonstrates a small custom package.

Layouts

A Layout is a CSS class that arranges the element carrying it. On main, it can give the page a reading column, a wide content area, or a workspace. A workspace contains panes: regions with optional headers and footers and, in a full-height workspace, their own scrolling. Sidebar and tile layouts arrange an element's children and can be used on main or on a block within the page.

Class Arrangement
layout-column Text in a centred 720px column, which figures and boards can extend past. A plan, review, report or explanation read top to bottom, as most pages are, this one included.
layout-wide A single vertical sequence of content as wide as the window, up to 1600px. A code comparison or a data explorer.
layout-workspace The window's full height, divided into panes that scroll separately. A queue beside the item it opens, or a playground's controls beside its preview.
layout-sidebar A body beside a narrower side column; on main, a wide page with its header across both. A board and its status, a release dashboard, or a review with its verdict beside the diff.
layout-tiles Equal cells, as many to a row as fit. A row of metrics or status tiles.

Leaf's Layout classes are ordinary CSS, applied beneath the page's own stylesheet in the cascade. A page can adjust them with CSS rules, for example to change a column's share of the width or a gap. It can also use its own grid when the supplied layouts do not fit.

The reading column

On a layout-column page, headings, paragraphs, lists, and code occupy a centred column up to 720px wide. In every Layout, the theme limits paragraphs, list items, and headings to that reading width.

A diagram, board, or wide table can extend into the margins beyond the reading column. The text above and below it keeps its width and position. These width settings control the block:

  • column uses the reading column's width.
  • wide extends up to 1080px. Wide blocks share this width so they align with one another.
  • available uses the window's width after subtracting the outer page margins and space for margin notes and controls.

The registry, which declares each component's behavior, also gives it a default width. For example, lf-board uses wide, and lf-diagram uses available. A data-width attribute on a block sets its width or overrides the default. If the margins have unequal space, the block extends farther into the wider margin.

A log, feed, or long listing with data-bound scrolls within a limited height and opens at its newest entry. Its growing content therefore does not make the whole page longer.

Margins

A sufficiently wide window places these controls and notes beside the reading column:

  • The rail, on the right, where Leaf places a marker beside each commented or decided passage. It needs a window about 960px wide, or about 1010px on a touch screen.
  • A sidebar, the page's first aside.sidebar, on the left. It holds a table of contents, a legend or reference facts, and stays in view under the banner as the page scrolls. It needs about 1130px.
  • Sidenotes, each an aside.sidenote, on the right, level with the block they annotate. They need about 1150px.

The column shifts sideways to make room for a sidebar or sidenotes. In a narrow window, those notes appear within the column at their original positions in the HTML.

Wide pages

Applying a Layout other than layout-column to main makes a wide page. It fills the window up to 1600px, with an outer margin that grows from 24px to 64px. Its blocks and title share a left edge, while paragraphs still wrap at 720px. Wide pages use larger titles than column pages. A workspace uses a smaller title to keep its header on one row.

layout-wide arranges content vertically in a single wide area. layout-sidebar places the header across the top, with a body and a narrower side column below it. The side column is an aside; placing it before or after the body in the HTML puts it on the left or right. The regions stack in HTML order below about 870px, or when the body's content needs the full width, such as a board with many columns. On an element within a page, layout-sidebar makes the same arrangement without widening the whole page.

A side column made by layout-sidebar is part of that layout's content area. An aside.sidebar instead places a note in the margin of a column page. A section.panel draws a bordered card with a short heading to distinguish one region from another. 

<main class="layout-sidebar">
  <header><h1>Release 4.2 rollout</h1></header>
  <div>…</div>      <!-- body: the work in progress -->
  <aside>…</aside>  <!-- side column: status, counts, contents -->
</main>

Examples with a side column: Live progress, Triage board, Command hub. Examples with a single wide flow: Code comparison, Data explorer.

Workspace

layout-workspace fits the page between Leaf's top banner and bottom bar. A single-row header holds the title and status tags. The body takes the remaining height and contains an lf-pane, a component that arranges its own panes, or a grid of panes defined by the page's CSS. Each pane scrolls its content beneath its own header. A pane's footer stays visible, keeping its actions within reach.

An lf-tabs list="side" in the workspace body displays a list of tabs as a queue, such as tickets or findings. The selected item's content appears beside that list.

The workspace fills the window's height when the window is at least 720px wide and 480px tall. In a smaller window, panes expand to fit their content and the whole page scrolls. 

<main class="layout-workspace">
  <header><h1>Payments alerts</h1></header>
  <div id="regions">
    <lf-pane label="Queue">…</lf-pane>
    <lf-pane label="Alert">…</lf-pane>
  </div>
</main>

<style>
  #regions { display: grid; grid-template-columns: 1fr 2fr; gap: var(--sp-4); }
  @media (width < 720px) { #regions { grid-template-columns: 1fr; } }
</style>

Examples: Notification playground, Merge a worktree, Alert review.

Tiles

layout-tiles arranges an element's children in equal cells at least 9rem wide, placing as many cells in each row as fit. Cells in the same row have equal heights. A page can set its own columns when it needs a particular grouping, such as four tiles in two rows of two. A row of headline numbers can use a layout-tiles block of lf-metric elements.

Page tabs

An lf-tabs at the top of a page creates tabs like the ones on this page. Their tab strip stays below the banner while the page scrolls, and one tab's content is visible at a time. All tabs share the page's width, Layout, threads, and version history.

Banner, rail and panels

Leaf adds controls around the authored HTML. This interface is called chrome: the top banner, bottom bar, comment and decision markers, thread panels, and Asks drawer. An Ask requests a user decision; the drawer collects those requests. Opening these controls preserves the page's text wrapping and reading position.

The banner and bottom bar have fixed heights, and the page scrolls between them. The bottom bar shows keyboard hints and status messages. Touch screens omit that bar because they have no keyboard shortcuts to show.

The rail is the strip to the right of main where Leaf places comment and decision markers. It appears when the window has enough space: about 960px on a column page or about 1920px on a wide page. data-rail="right" keeps it visible above 640px. Where no rail fits, and inside a scrolling pane, a small pin appears beside the target on the page. Leaf places it clear of text and controls when space permits. The o shortcut hides pins and passage highlights; on a touch screen, Hide annotations in the banner's More menu provides the same action.

A thread card opens beside its marker in the margin. If the margin is narrower than the card, it overlaps the text's edge. The Threads panel and Asks drawer open over the page's edges, one at a time.

Narrow windows

At phone widths, page regions stack vertically in HTML order. Margin notes move into the reading column, a side column appears above or below its body, and workspace panes expand to fit their content. Tiles can still fit two per row on a 390px phone.

Page files and history

A page directory stores its HTML, revision history, event log, and external data. Copying it preserves the page and its recorded decisions. Leaf derives the visible content and state from immutable document revisions, an append-only event log, and JSON files containing the latest external values.

Current state is computed on every read

The active revision's HTML supplies each component's initial state. Leaf computes current state by applying recorded actions to that starting point whenever it reads the page. An action is keyed by [widget, unit, verb]: the component, the part of its state being changed, and the operation. For each key, the latest action still in effect determines the result. leaf page state reports that result. The browser also shows local actions while waiting for the server to confirm them.

Every event passes through the same validation step before Leaf appends it to the log. Leaf checks the operation against the page's component declarations and records what the action meant when it was taken. Later readers use that meaning even if the original component is gone. Undo appends a new event identifying the action being withdrawn; it does not remove the original event. The event log reference follows a choice and its undo through this computation.

External values are replaced, not logged

External values, such as benchmark results or build status, use one JSON file per data source. The page declares the format each source must provide; its first write records that contract in data.json for the page's lifetime. Any process can replace the source file. Leaf validates its value on each read and displays a source error if it does not meet the contract.

Replacing a source file updates the open page without creating a document revision. Each file holds only its latest value. An lf-num freezes a number into the authored text, so it keeps that value when the source changes. leaf page check advises when the number's source has changed.

Data written to the page directory survives closing a tab or restarting the server. Draft text and interface arrangements are stored in the browser; the table shows which events preserve them.

The browser stores unsent draft text and interface state. Scroll position, the active tab or panel, and design mode belong to one browser tab. Draft text is shared between browser tabs showing the same page; arranged controls are shared across pages in that browser. Submitted comments and actions enter the page's event log, where all tabs and the agent can read them.

How long a server runs

The HTTP server makes the page directory available to a browser. A server started by an agent session stops when no live session claims the page. A claim registers a session to receive that page's feedback. A server started from a shell, or with --standing, runs until leaf server stop.

Served where you are

For a local agent session, Leaf binds to loopback, so the page opens only on the serving machine. For an SSH session, it uses the session's SSH destination. The URL contains an access key shared by all Leaf pages on that machine. The browser stores the key in a cookie; sharing it grants access to those pages.

If the default URL cannot be reached, the agent restarts the server with leaf server start --host NAME, using a reachable hostname. Leaf uses the machine's existing networks and creates no public tunnel. The serving reference explains addresses, authentication, and server lifetimes.
