Questions contain their answers

A Question is one logical record containing the request, its current answer and its lifecycle. lf-ask, decision widgets, thread conversations and other views interact with that record. An answer is a field of its Question, with no independent identity, collection or persistence.

This contract keeps automatic questions from decision widgets and keeps their canonical values in widget state, as requested. The Question record exposes those values directly. The name is Question; its meaning does not depend on which shortcut is available.

One record, several interfaces

lf-ask has no privileged role in the model. It is one presentation adapter. Adding or removing that wrapper does not create a different Question, copy its answer or change its completion rules.

A widget declaration identifies when it poses a question, which typed state is its answer, and what completes it. A thread question registers through the conversation contract. New packages participate through these contracts, without adding tag names to core.

What a Question contains

The following is the public semantic shape. All fields are read from the same application publication. 

{
  id: "widget:release-disposition",
  source: { kind: "widget", id: "release-disposition", tag: "lf-options" },
  thread: null,
  prompt: {
    text: "When should this ship?",
    target: "release-context"
  },
  answer: {
    value: ["later"],
    event: null // answering gesture, where one is recorded
  },
  status: "answered",
  next_actor: null
}
Field Meaning
id Stable source coordinate: widget:<widget-id> or reply:<message-id>, or approval:v<version>. The kind keeps widget, message and version identities distinct. A presentation wrapper has its own element id, but does not replace this identity.
source The widget, thread/message, or stamped version that owns the canonical input and answer. This is also where commands are admitted.
thread The containing thread’s id for a prose question or a widget frozen into a thread message; null for a page widget or version approval.
prompt The question’s words and the target that reveals its context. A generic x-question-context wrapper contributes its leading heading and target without changing the source. Text can be null for a standalone widget.
answer The current typed value and answering event, selected from the source. Display wording belongs to presentation. It is null before any answer content exists. It has no separate id or lifecycle.
status open, answered or withdrawn. Completion follows the source’s declared rule, independently of the value’s emptiness or truthiness.
next_actor user, agent or null: who currently needs to act. A discussion can hand an open Question to the agent without answering it.

Typed values come from declared structured state. Display wording is formatted by the source family for its views and is never parsed back into data. It is not a semantic field or independent answer API. For a widget, the declaration selects its answer coordinates; for prose, the answer contains the settling message or reaction and its event reference. A version approval uses source: {kind: "approval", version: N} and a typed answer.value === true once approved. x-awaits.value names the state verb supplying a widget’s typed answer, separately from x-awaits.answered. A record verb supplies its value; a custom verb supplies its structured detail.

A partial value can appear in answer while status remains open. A completed empty selection is answer.value = [] with status = "answered". A completed empty text answer is likewise distinct from no answer.

How it works

  1. The source declares the request. Authored widget state or an agent’s thread message establishes the Question. A stamped version declaring required sign-off establishes its approval Question. Standalone widgets participate automatically when their declarations say they are asking.
  2. Core publishes the Question. It combines authored state and the admitted log into one reading of the prompt, answer, completion and attention. No Question database or answer file is added.
  3. Interfaces select that record. The Questions panel, lf-ask, widgets and package views read the same publication. They can arrange it differently without keeping another answer.
  4. The user acts through the source’s command. A selection, edit, reply, reaction or version approval uses the existing admitted write path. A second view invokes that same declared command against the same owner.
  5. The publication changes. The source’s state supplies the new answer. Its completion rule determines whether the Question has been answered; its workflow determines whose action comes next.

Pending input draws its semantic result immediately through the existing local ledger. Widget Question membership and completion move when the POST’s authoritative reading arrives; a pending conversational send can hand attention to the agent immediately. Version approval and its undo update that Question’s answer and status immediately. Refusal restores the admitted state. The record does not introduce a second fold or a second settlement decision.

The same model in six situations

Situation Answer in the Question Lifecycle
Single choice: choose Later Typed selected option ids; display “Later”. The choice completes the Question.
Multiple choice: select two options The selected ids are already visible in the record. Still open until Done. Done with no selections is a completed answer.
Text edit requested by a draft widget The widget’s current typed text. The widget’s declared submission rule completes it; merely possessing baseline text does not.
Agent asks a question in a thread The user’s settling reply or declared settling reaction, including its event reference. The existing conversation rule settles the preceding questions. A closed thread without a reply does not fabricate an answer.
A stamped version requests sign-off Null until approved; then typed true with the approval event. The banner's Approve answers that version's Question. Undo reopens it, and a refused approval restores the admitted state. Arrival reaches the actual approval control. This creates no work task.
User discusses a widget question with the agent The widget’s value remains as it was. Still open, with attention on the agent while that discussion is theirs. Their reply alone does not select a widget answer.

One Questions API

const questions = readQuestions();
const question = questions.all.find(q => q.id === "widget:release-disposition");
console.log(question.answer?.value);

watchQuestions(owner, collection => render(collection));
await questionActions.open(question.id);

The API returns a complete immutable inventory and derived selections for on the user and unanswered. The inventory retains earlier thread questions even when a later prompt is the current one. Selection and filtering never determine whether a Question exists.

Answering remains a command on that Question’s source. There is no readAnswers(), answer collection or independent answer CRUD API. Internal presentation helpers format question.answer; they do not determine it. The shipped module and package references define the declaration and command signatures.

Core navigation and the Questions panel consume this API. The existing q/Q work walk remains; the Ask-only g a narrowing is removed. The name Question does not reserve another shortcut.

Questions and work queues

A Question models a request and its answer. A task models work someone has committed to do. The work queues combine Questions, tasks and delivery recovery, preserving their different completion routes.

This contract preserves the current participant scope: Questions are agent requests for user input. An ordinary user comment can create work owed by the agent without being classified as a Question. A workflow row currently called answer means response owed to that input; it is not an independent Answer entity.

Core derives queue rows directly from Questions. The former widget and prose question tasks are removed: tasks contains only explicit committed work. It does not reconstruct Questions from queue rows: the queues can suppress an older prompt while its unanswered Question still exists. A to-do ends through Done; a delivery retry resends input; neither invents a Question or answer.

Revisions, undo and withdrawal

A revision preserves a standing answer unless it explicitly retracts what that answer rests on. Changing the Question’s presentation does not retract it. Replacing its meaning uses the existing restated contract; undo withdraws the named gesture and the record is derived again.

Removing a request withdraws it without claiming an answer. A removed source leaves the active inventory; revisions and events retain its history. An agent-ended prose Question remains in the inventory as withdrawn while its source message remains.

An agent-ended prose request with no user reply or settling reaction is withdrawn, regardless of the task’s reported outcome. It records no user answer.

A restated source starts a fresh request under the same source id and the new document basis, with the prior answer retracted. The current inventory exposes that current Question, rather than an additional withdrawn copy; revisions and events preserve the earlier request and answer.

Resolving a thread hides an unanswered prompt from the current work queue, while retaining its open Question in the inventory. Reopening restores attention according to the conversation state. This distinguishes “stop showing this conversation” from “the user answered”.

A board reads the same Question

A board can group Questions by question.answer.value, and open the question’s evidence through its prompt target. This supplies structured data directly; the old askAnswers() display API is removed. The Next / Later / Drop example is a single-choice projection; grouping multiple selections and including partial values are choices for the board’s projection contract.

A board that changes an answer invokes the source’s declared command. It does not record a second board-owned value for the same answer. The general view-to-owner write contract is still needed to admit that gesture and handle value mapping and ordering; the Question record alone does not implement it.

The Questions implementation establishes typed answer selection and one identity. Shared board editing follows the separate view contract in notes/shared-decisions.md, with its owner choice updated to this model. A board’s card order remains a separate fact from a Question’s answer unless the source explicitly owns both.

Claude’s API review new

Claude reviewed the approved specification against the owning code. It supports the unified model and identified the following implementation contracts. These resolutions preserve the approved scope.

API review findings and resolutions
  • Duplicate request tasks: Questions replace the widget and prose-derived user tasks. Queues select the inventory; Tasks hold explicit work.
  • Typed answer owner: x-awaits.value selects state independently of completion. Semantic answers carry value and provenance; presentation formats wording.
  • Prompt ownership: generic x-question-context contributes a heading and arrival target. A standalone widget can have null prompt text. No wrapper substitutes identity or drops a second Question.
  • Retired widget lifecycle: a retained source whose request predicate stops holding is answered if its completion condition holds, otherwise withdrawn. Resolving a thread hides its queue route and retains its Questions.
  • Answer provenance: answer.event names the admitted answering gesture, or is null for an authored answer.
  • Identity collisions: the source kind prefixes the id; frozen widgets retain their thread coordinate.
  • Old Ask mechanisms: contextual digits, arrival ring, margin markers, Page Map and render checks become Question consumers. Old Ask APIs and g a disappear.
  • Vocabulary and scope: use next_actor; page widgets follow the shown document version, frozen questions their thread window. A pending prose reply changes the next actor and leaves status open. A message carrying a widget request adds no duplicate prose question.
  • Sign-off gate: preserve the current widget-question scope, including unanswered widgets held in discussion. Open prose questions do not newly block sign-off.
  • Explicit tasks: preserve the approved distinction between Questions and committed work. A user to-do and another chat’s Approval task are not folded into this inventory.
  • Accept all: retain declared bulk commands as a consumer of widget Questions.
  • Main integration: required version approval and canonical conversation APIs are incorporated. Approval is another Question source and keeps its exact stamped-version identity.
  • Prose withdrawal: the already approved rule applies: an agent-ended request without a user answer becomes withdrawn, regardless of task outcome.
