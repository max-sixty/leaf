Inspect source and browser observations

Inspect the saved page source, or add --revision N for a captured revision: 

leaf page inspect <page>

The command returns structured facts with their locations and measurement basis. A successfully measured large page still succeeds; unreadable input or a failed requested measurement is reported explicitly. No quality score, traffic-light rating or arbitrary CSS budget.

Authored CSS, by source
Bytes, CSS rules, declarations, inline styles and !important, with file and line locations. Separate page files, embedded sheets and registered page-owned widget styles from the selected layer. Count imports once; show child documents separately.
Existing browser observations, when available
Reuse Leaf’s passive overflow, arrangement and label readings, with affected element locations. Include viewport, scheme and observation time.
Measurement basis
Identify the exact source revision and the browser state inspected. Unavailable or stale readings remain explicit; a source edit must not inherit geometry from an older open tab.

The command and menu share the source report. Existing parsers and browser probes supply the measurements; normal page checks keep their validation role.

Open Page diagnostics from the Leaf menu

Page diagnostics opens beside the menu’s existing revision and runtime information. It loads on demand, showing source totals, file and line locations, and the current tab’s browser observations. Copy diagnostics copies the structured reading. The view is captured at opening; close and reopen to inspect again. Exports and public previews show browser context without starting a private session.

The menu’s browser readings must be passive. It must not open disclosures, scroll the page, or change styles to measure them. A collapsed-versus-expanded comparison belongs in a disposable browser session, identified by revision and viewport. New disclosure measurements can follow once the source inventory is useful in practice.

An especially useful later experiment is a separate preview with page-authored CSS disabled. That lets the user see what the default theme already supplies. It must be clearly marked as a comparison: removing layout CSS can break a valid visualization, and it should never change the live page.

Add measurements when they answer a real question

Disclosure anatomy
Labels, nesting, immediate body contents and child disclosure counts expose wrappers around further controls. Browser geometry could show an 18 px target inside a 40 px card. Those facts help the agent judge the design; body length alone cannot establish whether a disclosure is useful.
Style vocabulary
Literal colors, font sizes, radii and repeated declarations, alongside token references and source locations. Several colors may encode data; computed values cannot reveal whether an author used a token.
Rule effects
Highlight what a page-authored selector currently matches, and use browser facilities to identify winning declarations. Matching is not winning; states, media queries, nesting and shadow scopes need their actual context.
Page weight and startup
CSS, JavaScript and media bytes by owner; requests before first presented state and later loads. Separate delivered bytes from captured source bytes and reuse startup probes. This measures a different cost from visual complexity.
Recorded CSS coverage
Rules observed during a named interaction journey. “Not observed” is not “safe to delete”: a closed tab, responsive breakpoint or error state may need them.
Version comparison
Changes since the previous revision, with comparable viewport and journey. A smaller number is not necessarily better; compare the actual result.

Do not start with a “card count,” “unnecessary CSS” percentage or overall complexity grade. Those names claim design judgment that borders, byte counts and DOM depth cannot establish. A control, a chart and a card can all have the same border properties.

Reuse the existing owners

SourceDocument.authoring already indexes authored styles and locations. styles.py already parses CSS with tinycss2. RevisionArtifact captures page resources and import dependencies. These should produce the source inventory from exact revision bytes.

readViewChecks() already provides passive layout measurements, and user_views records revision, viewport, freshness and source matches. Reuse those readings. Keep source facts in Python and geometry in the browser; one small report owner combines compatible observations for CLI and HTTP consumers.

The menu already has page-about.js and the page-controls.js registration point. Extend those surfaces on demand. No new continuous monitor, duplicate diagnostics database, or generic metrics plugin framework is needed.

Static authored CSS is the honest initial scope. A script may generate CSS at runtime; that is not counted by scanning source sheets. Summing live stylesheets instead would count shared Leaf sheets repeatedly across shadow roots and misattribute the framework’s styles to the page.

Evidence and limits

The CSS counts above were measured in this checkout using Leaf’s parsers. The command, menu and default-styling guidance are implemented. Later measurements above remain ideas. Focused checks cover imported CSS attribution, sample documents, CSS-only source drift, immutable HTTP readings, and the menu’s copy, close and focus behavior.

Chrome’s CSS Overview is a useful precedent: inventory entries lead to affected elements. Its Coverage panel records use while interacting, which is why an unvisited state must remain outside the claim.
