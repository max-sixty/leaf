How Leaf works

An agent builds a page around the work. The user comments, explores, and makes choices. The agent responds by revising the same page.

Leaf supplies the interface and the record of that exchange: comments attached to passages, interactive widgets, decisions, and versions. The agent supplies the content and does the work, using its existing tools in Claude Code, Codex, or Pi.

Pages, core, and packages

A page is the document the user reads and acts on. Its HTML includes widgets such as choices, charts, and boards. A passage identifies the words a comment concerns.

Leaf’s core supplies shared state, events, and page lifecycle. Packages contribute widgets, domain behavior, styling, and authoring instructions. A page selects packages, its theme among them; Leaf combines those with its core declarations and assets into the page’s layer.

The layer’s registry gives agents, checks, Python, and the browser a shared description of its elements and capabilities. It declares valid markup and the meaning of widget actions; widget modules implement their behavior and presentation. Package interface draws everything a package leans on Leaf for and walks through a whole widget.

The layer's styles reach the page as one stylesheet, which Leaf links first in the page's head. The page's own CSS follows it and outranks it, apart from rules in the page's base and reset layers, which Leaf ranks among its own. The tiers draws where each rule goes.

Authored content starts the page’s state; the append-only log records changes. Each reading applies the events still in force. Undo records which gesture it withdraws, leaving the original event in history. Focus, scroll, selection, and open disclosures remain browser-local interaction; the page’s server keeps an unsent draft outside the log, for every tab and device.

The Leaf serving, checking, or exporting a page supplies its current runtime and composes its layer from the recorded selection. Historical revisions keep authored content and recorded decisions, while the serving Leaf supplies the code that draws them.

Browser and server

A page runs as two programs that share no memory: Leaf's browser runtime, in each tab that shows the page, and the page's server, a Python process. The server learns what the user did only from what a browser sends it. A widget deals only with the runtime: the runtime sets the element's state property, and the element dispatches lf-action, or lf-undo, to say what the user did (Widgets).

Facts that depend on the whole log, such as which questions still wait on the user, arrive with the server's reading rather than with the gesture. The server computes every reading from the authored markup and the log, without running any widget's module, so the agent's deliveries, its turn-end check and leaf page state see the same state with no tab open.

The exchange

An agent proposes queue policies for an importer. A choice or comment the user sends is an update. A comment opens a thread, the conversation about its passage, widget, or the page as a whole. To make this choice yourself, try the queue policy practice in Workflow.

  1. The agent prepares the page. It writes the alternatives, checks the page, and opens its link.
  2. The user chooses “Pause the producer”. The browser draws that choice immediately. The server validates the action against the registry and appends its meaning to the event log. The server’s next reading supplies the choice’s effect on obligations and work owed.
  3. Leaf delivers the update. The harness brings the choice and its context into the agent’s session. Its workflow tracks delivery and work, distinguishing receipt from the agent explicitly starting it.
  4. The agent incorporates the decision. It revises the proposal to use backpressure and stamps a version that records the choice in the markup. A revision captures authored content; a version names a revision the user can revisit. If the update was a comment, the agent answers in its thread.

An obligation records an input or answer owed and whose turn it is: first the user’s queue-policy choice, then the agent’s incorporation of that choice. A to-do records work the agent owes, such as measuring the importer’s throughput. Obligations and to-dos supply the On Me and On agent lists; threads keep the conversation, and workflows track the handling of updates.

The same link shows the revised proposal. Stable widget ids keep recorded choices attached across edits. When an edit changes what a decision was about, the author explicitly marks it restated and explains why the decision no longer applies. State and records defines these concepts; Revisions explains their continuity.

Author, hand over, and respond

The harness supplies the agent’s tools and runs its turns. This example follows a queue-policy review from the first page to the answer. Command inventory lists the available operations; Harness connections explains delivery and receipt.

Publish a page

The agent reads Leaf’s skill and the reference for each step: page authoring before writing, and its harness contract before handoff. These instructions set goals for the user’s experience and leave wording and presentation to the agent. Agent instructions and notices lists every source of instructions and when the agent reads it.

The agent creates a page directory and writes index.html with ordinary HTML and Leaf elements. Here, ./review names that directory, relative to the commands’ working directory.

leaf page init records the page’s package selection, its theme first. The Leaf serving the page supplies its runtime and composes the selected packages. The agent authors its content using the HTML and Leaf elements described in Extending.

leaf server start starts the page’s HTTP server and claims the page for the current agent session: that session receives its updates. The command returns a URL with an access key. The agent hands over the URL and ends its turn; the harness integration continues watching. 

leaf page init --package reading --package diagram ./review
# Write ./review/index.html with the harness's file tools.
leaf page check ./review --render
leaf page stamp ./review --text "Queue policy ready for review"
leaf thread create ./review --title "Importer queue policy" --obligation --text "Which queue policy fits the importer?"
leaf server start ./review

This example is a record meant to be revisited, so the agent reviews and stamps it before handoff. A quick page needs only leaf page check. Revisions defines valid saves, stamps and version addresses; Checks before a revision goes live describes validation.

Resume an existing page

To resume an existing page, the agent reads its active HTML and leaf page state ./review, which returns current state as JSON. leaf page claim ./review registers the current session as the recipient of the page's updates without starting its server. Starting the server also makes that claim.

Answer updates

A browser comment or choice sends an HTTP request. Leaf validates it, appends it to the event log, and delivers it to the agent with thread context and instructions assembled from the registry. The harness supplies this JSON batch or an id to open with leaf delivery read.

Choose a policy, then open Show activity below it to see the recorded choice. Open the page’s leaf menu and choose Undo; press Activity changed in the feed to see the choice marked undone. This example uses the page’s activity log and Undo; its queue policy is fictional.

Importer queue policy

The importer receives bursts of records faster than it can process them. Its queue has room for 1,000 records.

When the queue fills, what should happen?

Pause the producer Keep every queued record; wait for space before accepting more. Drop the oldest record Accept the newest record immediately; discard the oldest queued one.

Recorded actions

For a comment requesting a policy change, the agent follows the delivery’s receipt instructions and first posts a progress message naming the work. This also starts the event, so the user sees which update it is handling. It then reads the current page and thread, revises the policy, and replies. This example posts replies through the CLI; harness routes describes when Leaf captures a turn’s messages instead. 

leaf thread reply <answer.ref> --ephemeral --text "Checking the importer's queue policy."
leaf page state ./review
leaf page state ./review <thread-id>
# Revise ./review/index.html.
leaf thread reply <answer.ref> --done --text "The importer policy is updated."
leaf thread create ./review --title "Revised policy" --obligation --text "Does the revised policy match the workload?"

A comment needs a thread reply. A widget that asks, any widget whose registry entry declares awaits, creates an obligation on the user’s On Me list, with a prompt, typed answer, and lifecycle; the lf-group the author puts around it supplies the prompt in its label. The widget owns the value, and the agent records the decision in a stamped revision. The browser fetches the revised HTML and state.

Example: answer a page choice

The page asks which queue policy to use with lf-options id="queue-policy". When the user chooses Drop the oldest record, Leaf delivers that choice to the agent. The agent starts the choice event, reads the current choice, and revises the HTML to show the selected option: 

<lf-options id="queue-policy">
  <lf-option id="drop-oldest" selected>Drop the oldest record</lf-option>
  <lf-option id="block-producer">Pause the producer</lf-option>
</lf-options>

After checking and reviewing the result, the agent stamps the revision to record the decision. The stamped markup answers the choice event and ends its start: 

leaf task start ./review <event-id> --text "Recording the chosen queue policy"
leaf page state ./review
# Add selected to the picked option in ./review/index.html; check and review.
leaf page stamp ./review --text "Queue policy: drop the oldest record"
Delivery fields and answer semantics

In a delivery requiring a thread reply, answer.parent is the message it threads under. The event's id identifies the update to start, and answer.responds identifies the update the reply answers. The example batch uses 9d41b20f for all three because the comment opens a new thread. A later message has its own event id within that thread.

A user comment requires a reply in its thread. A decision on a page widget requires a stamped revision. If the obligation's widget declares a record form, the revised HTML uses it to show the decision, such as the chosen option. An obligation embedded in a thread message receives a thread reply, because that message's HTML is fixed. Moving a card can require no answer; the agent still receives the event. Resolving a thread takes it off the user's list and leaves a comment the agent has not answered owed its reply, which goes into the closed thread; the agent may reopen it. A multi-select obligation submits the choice when the user presses Done.

A delivery is one JSON document, whose format field names its version. Its envelope contains one or more page batches, preserving the captured event order, thread context, and handling instructions. A delivery id supplied by the harness names this whole envelope; an event’s id names one recorded event. Harness connections and receipt describes how to read and confirm a delivery pointer. The registry is Leaf's machine-readable definition of elements and events. It declares event instructions under $events.handling and response instructions under $events.answering. Leaf combines the applicable clauses in the batch's handling object. The agent follows those clauses and reads current state before answering: a newer update may already have settled the response the captured batch requested. The excerpt below is illustrative, with the batch's other fields omitted. 

{

    "h1": "Read the thread context before answering.",

  },

    {
      "id": "9d41b20f",

The event's list selects h1 and then h2 from this batch. These ids belong only to that batch. The event id identifies the update being answered.

Change the live page

The agent can save HTML, replace a widget’s data source, or report a widget state change while the user reads. The browser fetches the revised document and state when the server reports a change (Freshness checks and state reads). 

leaf data set ./review queue-metrics --file ./metrics.json

Here, the declared source queue-metrics receives the complete value in metrics.json. For a widget state change, leaf page report records its declared operation and fields. Saving HTML changes the live document; stamping adds a version address and changelog entry.

These changes preserve the user's recorded choices. If an edit changes what a decision was about, the author marks the widget restated to invalidate that decision. The Revisions view explains how decisions survive page edits.

Threads explains anchors and how they survive revisions, drawings, titles and summaries.

Source errors

A source error can leave the file on disk newer than the live page (Checks before a revision goes live). Read leaf page state alongside the active HTML to check which revision the user sees.

Wait for updates or finish

leaf page open ./review leaves the page available for feedback. Questions that need an answer go in thread messages with --obligation, which puts them in On Me. The harness integration keeps watching after the turn ends and sends later updates back to the same session.

leaf page close ./review marks the page finished and stops watching it. Leaf refuses it while an update awaits receipt or an answer, or an agent to-do is open. If the agent ends a turn with a delivered update unanswered, the Stop hook tells it so (Stop hook checks).

Background work and durable to-dos

Work longer than a few minutes runs in background workers, whose results start another agent turn.

leaf task start names the update or to-do the agent is handling in this turn, and a reply or stamped decision answers the update. Work that outlasts the turn, or that no update asked for, gets a to-do, which stays open across replies, revisions and sessions until the agent ends it. The agent opens it on a thread, a widget that takes to-dos, or the whole page, and starts it with the id leaf task create prints: 

leaf task create ./review page --title "Check the importer policy"
leaf task start ./review <todo-id> --text "Checking the importer under load"
# Run the check and put its result on the page.
leaf task end ./review <todo-id> done --text "The load check is recorded on the page"

A to-do ends as done, failed, or dropped, with a note saying where its result is or why there is none. A stamp with --completes <widget-id> ends every open to-do on that widget as done. Until then the to-do stays on the agent's list, On Claude.

Stop hook checks

When the agent ends a turn, Leaf’s Stop hook checks its pages for unanswered updates and delivery between turns. Claude Code shows a reminder as context, not an error. A new update normally opens a turn of its own after this one ends, preserving this turn’s final message as its answer. Where nothing watches afterward, as with Claude Code’s plain --print or a Codex task waiting with leaf wait, or where the next turn would open on a message in the user’s name, as with Codex’s codex queue, an update needing an answer enters the current turn instead. An update needing no answer waits for the next turn.

  • An update started in this turn lets the turn end. Long work runs in background workers whose results start a later turn, so the Stop hook doesn't hold a turn open for an update the agent started in it. The update reads On it, with the agent's line beside it, and no later turn is reminded of it, while the harness reports the session's background work running, as Claude Code does. Once nothing does, it reads Gone quiet, and the next turn answers it or starts it again.
  • Between turns, a page needs a watcher: Claude Code's or Pi's watch hook, a leaf wait, or Codex's adapter. Without one, the user's next update waits in the event log until the agent's next turn, which in Claude Code Leaf starts by messaging the session. A closed page or a developer's preview needs no watcher.

Harness connections and receipt

Claude Code’s background Stop hook watches between turns and wakes the agent; its prompt hook puts the update into the new turn. Codex’s adapter queues the update as the next message, or starts a turn when Leaf is an App Server client. Pi’s experimental extension runs inside Pi. Each route supplies the same delivery format and says who confirms receipt.

  1. Confirm receipt separately from transport. Leaf counts an update as received only when the agent or harness confirms it. A harness discards output from a timed-out hook, so the hook confirms well before its deadline and passes a complete delivery into the turn only after confirmation.
  2. Use a pointer when the whole delivery cannot fit or be confirmed. A delivery too large for the turn’s context, or one the hook could not confirm in time, arrives as an id. leaf delivery read <delivery-id> confirms nothing; the agent follows every next command, then runs leaf delivery ack <delivery-id> as the envelope’s acknowledge field directs.
  3. A direct wait confirms on its next call. A Codex task running its own wait uses leaf delivery ack <delivery-id> && leaf wait. Until then, the events remain available to the next wait, in case output was lost or cut off. The table's last column says what marks an update Delivered on each route.

Claude Code integration

leaf hook handles Claude Code's prompt and Stop hooks, and leaf session-end releases the session's pages. A background Stop hook runs leaf hook --watch and wakes the session when an update arrives.

Leaf reads Claude Code's session registry to tell whether a session is busy, waiting or idle. If nothing is watching the page, Leaf can message the session through its socket, or resume a retired background session with claude --bg --resume. The socket accepting a message doesn't show that the agent read it.

Turn-end check in Claude Code (experimental)

Late in a long session, the page can drift from the conversation: the agent leaves something to the user only in its chat reply, so On Me misses it, or a page goes on holding what no longer fits the work. In Claude Code, when the agent finishes a reply in a session holding a page, Leaf's hooks module forks the conversation. The fork is a copy of the conversation that answers one question without calling tools, and the agent never sees the exchange. Leaf sends it the skill's turn-end check with Leaf's rule for what goes On Me, as the agent reads it, and for each page its text as the user reads it, its On Me, the questions On Me no longer holds with their ids, and the items it shows under way. The fork names:

  • each decision, answer, permission or step the agent left to the user that no On Me item holds, such as which of two designs to keep or trying a build
  • anything on a page that no longer fits the work as it now stands, such as a result the work has since changed, finished work told as news, or a section the user dropped in chat
  • an On Me item the user answered elsewhere, or the work made moot
  • work the agent promised or set running, such as a background job, that no page shows
The turn-end check's prompt

Leaf's hooks module resends the main thread's last request with this message added. It holds turn-end-check.md whole, the paragraphs of the agent's guidance the check applies, quoted from the references the agent reads, each page's facts, and the answer's JSON form. Only the page facts change from turn to turn; the page here is illustrative.

Among asks, the fork leaves out what an On Me item already holds, what the user has answered since, and what the agent will settle itself. For each ask it gives a thread title, a message of a few sentences that the user can answer without the chat, the words of the passage it concerns, if one does, and the id of a question it asks again, if any, such as a step the user took that didn't work. The fork writes the message as the agent's guidance has the agent write one. Where the agent left answers the user picks among, or an action it takes once the user agrees, such as merging a pull request, the message usually holds a choice of them. A step only the user can take, such as trying a build, says what to do, and asks for the user's answer only for what they alone can report or the agent's next step waits on, usually as a choice where its answers can be listed, such as installed or failed. Leaf skips an ask whose title a question the agent asked already has.

Leaf posts each remaining ask as the agent's message, as the agent's leaf thread command would. The user's pick answers a choice, and any other ask carries an obligation, which their reply or a settling reaction answers. A question asked again goes in its thread, and reopens the thread if the user closed it. Any other opens a thread of its own, on that passage, or on the page as a whole where the fork named none or the page doesn't show its words once. Nothing on the page marks where an ask came from.

Where a few of a page's words have gone stale, the fork can give the words to put in their place. Leaf makes that change itself where the page shows the old words once: it finds the place in the page's source the user reads them from, swaps in just the words that change, checks that the page then reads as the fork asked, saves it as any save is checked, and tells the agent the old and new words, so the agent can change them back or rewrite them. A fix that needs more than a sentence, or that Leaf can't place, goes to the agent instead.

Only the agent settles an On Me item or adds to its own list, so the other findings reach it as messages. Each gives the fork's summary and the words from the conversation it rests on, which lead the agent to the original message even after a compaction. At its next prompt or tool call, the agent reads these and each record and change Leaf made, and withdraws a question it disagrees with by resolving its thread, as it would its own. A finding Leaf changed nothing for is work the agent owes before the user reads the page again, so when the session has gone idle Leaf wakes it for one rather than waiting for the user's next message.

The fork starts after the turn has ended, so neither the turn nor the user's next message waits for it. It reads the conversation from the session's prompt cache and answers in a few seconds. Leaf writes no record and changes no page once another turn has opened, since the fork's reading is then out of date; a finding still reaches the agent, naming the turn it came from. When a fork fails or its answer isn't the JSON Leaf asked for, Leaf writes nothing and records the failure in Claude Code's debug log.

Leaf also forks the conversation when the user writes in a thread, to post the agent's working line within seconds. Forks explains how.

Owning contracts

The delivered event batches reference owns the envelope and handling lookup. Conversation loop owns to-dos, starts, statuses, and the response loop.

Harness routes are specified in Claude Code, Codex, and Pi. Session lifetime owns the hooks, adapters, and App Server protocol behind them. Page storage owns revisions and browser replacement.

Which Leaf a session runs

A session runs one copy of Leaf, the copy its hooks run, and Leaf brings what the session keeps between processes to that copy. Claude Code installs each Leaf update as a new copy in its plugin cache, and a process loads the copy installed when it starts, as at a new session, a resume or a background job's wake, or when it runs /reload-plugins. Its hooks run $CLAUDE_PLUGIN_ROOT/bin/leaf, which runs the copy it sits in. Leaf's hooks module comes from the same copy and follows the session's pages through that copy's launcher, and the agent's bare leaf is that launcher too, since Claude Code puts the copy's bin/ on the Bash PATH. In Claude Code a running process stays on the copy it loaded after an install, and the session takes the update at its next new process or reload. Claude Code may delete the old copy while a process still runs it; its hooks then fail, asking for /reload-plugins. Codex and Pi also run Leaf's hooks through the launcher in the copy they loaded, but each keeps one copy and updates it in place, so the session's next hook runs the update. A path names no version there, so Leaf tells two copies apart by path and commit. Each hook records the copy it ran. A page server and a Codex delivery adapter outlive the hooks that start them, and each keeps checking which copy should run it: the installed copy the session's hooks last recorded, where that is another, as after Claude Code loads an update, or else a new copy Codex or Pi puts in place of its own. It then has that copy take over. Pi's watch between turns moves once Pi puts a new copy in place of its own. The server's restart renews a page left at an older page protocol as a hook would, and the adapter and watch then deliver its input. Leaf never reads a harness's record of the installed copy.

Each copy of Leaf speaks one page protocol, a number, and a page's protocol is the protocol number of the Leaf that last initialized it. The number covers only what one copy of Leaf writes and another must read, which is the page's event log and the records Leaf keeps outside its document. The copy serving a page supplies the runtime and composes the page's layer from the packages it selects, so a change to Leaf's own runtime, widgets or themes leaves the number alone. The build refuses a change to the schema of a logged event, or of layer.json, until the number moves. "Page protocol" in the layer registry reference says how the records Leaf keeps carry the number.

Derived data

Leaf derives what it shows from a few sources, and reuses each result until something it read changes.

Sources. On the server, a page's files: the log, its revisions, data and drafts. In the browser runtime, the application state (the server's reading, authored values and this tab's pending updates, published as one immutable snapshot), the live page's words, ids and parts, the layout, and what a widget or the browser owns, such as focus and scroll.

Hearing a change. The application state is a signal, so reading it subscribes. The browser reports a change to the page a microtask late, so before a reading of the page answers, Leaf takes the changes still pending.

Readings. A value derived from the state or the page is kept as a reading: one value per key, made again when an argument or anything it read changes, and dropped when its key goes. Publication gives an unchanged part its old identity, because the server sends patches and each unchanged part is shared, so a reading keyed by a record stands while the record does, and a publication about one thing makes only that thing's readings again.

On the server, a reading of a page is kept while the files it read are unchanged, under a name that never changes meaning, or, for a fact no file carries, such as another page's presence, until it is observed again after 2 s. The readings last served are kept too, so a later answer can be a patch.

Views. The margin, Page Map, Leaf panel, activity feed and widgets read the same readings for names, statuses and identities, and paint them on presentation passes (Drawing current state). A surface chooses placement and presentation, and never infers state from another surface's rendered text; drawn elements carry their identities so a press can find the thread or widget it acts on. What a thread shows lists what the conversation readings say, and the runtime owner table names each reading's owner. The code that measures a position or size keeps it until a size observer or a layout notice reports a change.

Replacing and withdrawing actions

  • A later action at the same coordinate supersedes it, as the pick of Later did. Undoing the later action restores the earlier one.
  • The user's undo withdraws one gesture of their own: a comment or reply, a reaction, an action or edit, or a resolve or reopen.
  • The author's restated: a stamped version lists element ids it deliberately rewrote, and every earlier action that depends on one of them is retracted.

Once the agent records a current decision in the markup, such as the added option as an ordinary lf-option with the same id and words, the document carries it and the action no longer changes what the page shows.

Decisions across revisions

A pick or drag records a structured action, shown immediately and delivered alongside comments. Once accepted into the log, it survives reloads, other tabs, and later revisions. The event log reference shows how actions and undo determine current state.

Claude Code also reports the session's activity directly: whether it is busy, a permission dialog, and an interrupted turn.   • The watcher. Claude Code's watch hook, leaf wait, or Codex's adapter registers with Leaf while watching for updates. Leaf treats the agent as available for updates while a watcher runs. A running Claude Code turn can also receive updates through its hooks. With no watcher after a turn ends, Leaf messages a Claude Code session when the next update arrives, so the agent is available too where that message starts a turn: a background job whose worker has retired is resumed with it, and a running session takes it at once where Claude Code's crossSessionInbound setting is accept.
  • The start. A start stops counting as active once it is 15 minutes old, or once the turn that wrote it is seen to end, unless Claude Code reports the session still busy with background work, such as subagents it started.

Leaf shows work as active when a start is still current, when the harness reports a step in an active turn or that the session is busy, or when that turn has received input requiring an answer. Claude Code reports a running turn as busy outside its permission and input dialogs, so an open page reads Working for as long as the turn runs, whatever the agent has started or still owes. The freshness rules above determine when a start or turn stops counting as active. Input is stalled if it remains queued for two minutes, or if the turn that received it ends without answering. The status doesn't date the agent's line: its hooks remind it to restate a line that has stood two minutes, and the menu's full status says when the line was written.

Anchors

A thread's anchor is the place on the page it is about. The first comment records it in the event log, and that record never changes; a reply or a revision can later move the thread to a new anchor. A comment can be anchored in these ways:

Anchor How the user makes it What the log stores
Passage Select words, then press c section, the id of the nearest element around the words; quote, the words; and prefix and suffix, up to 24 characters on each side
Element ⌥-click (Alt-click) an element, such as an image or a table, or press s and choose one section alone
Part of a picture ⌥-click a named box in a diagram or a point in a chart section and visual, the part's name
Data value Select words inside one value a widget drew from a data source section and datum, the value's key, and for a value from an external source, that source's revision
Drawing Draw on the page in Draw mode (w) An element anchor, plus the strokes
None Press c with nothing selected, or write in the Threads panel's comment box No anchor: the thread is about the whole page

An agent opens threads with the same anchors, using leaf thread create with --quote, --section, --part, or none of them.

Finding a passage

In the browser, a passage is an ordered list of segments, each {node, start, end}: a text node and a range of characters in it. A selection that crosses a bold word, a link, or two paragraphs is several segments. Text nodes exist only while the page is loaded, so the log stores the passage by its words instead, as the anchor table shows.

Each time the page is drawn, Leaf searches the anchor's section for the quote. If exactly one occurrence has the stored prefix and suffix around it, that occurrence is the passage. If none has them but the quote occurs only once, that one is the passage. In every other case the anchor finds nothing. Leaf never takes the first of two identical passages, because a comment made on the second would then appear on words it was never made on.

Leaf reads a page's text in two ways. says is the text the rendered page shows, including words a widget draws and declares as part of the page, such as a tab's label. wrote is only the text the author put in the HTML. Anchors and quotes use says, because the user selects what they see. Comparing two versions uses wrote, so words a widget draws do not appear as edits.

The browser makes an anchor from a selection. leaf thread create makes one in Python, from the HTML file. Both apply the same rules: the same whitespace characters collapse to one space, the same elements count as separate blocks, the context is the same 24 characters, and the search is the same.

The file holds the author's HTML, not the words a widget's script draws between its parts, such as a board column's heading or a diagram drawn from its source. A quote may not cross such words on either side. leaf thread create refuses a quote that crosses them, that occurs more than once in the section, or that sits in content the user's decision removed, and says what to quote instead. An agent's anchor is therefore one the user's page can find.

Drawings

In Draw mode, which w turns on and off, the user draws freehand on the page and writes a comment beside the ink. The drawing is anchored on the element under the start of its first stroke, or the nearest one. The comment stores up to 32 strokes as positions within that element's box, the box's size, the words the ink covers, and the window size and colour scheme it was drawn in.

The page draws the ink at the element's current size, so it stays on the element in a narrower window, though text that reflows inside the element can move out from under it. The agent reads the covered words in the comment, and leaf page picture renders that revision again in the same window with the ink over it.

Widgets in messages

An agent's reply can carry a small widget, typically a question with options, written as HTML in the reply's Markdown. Leaf validates that HTML when the reply is posted and stores it in the log with the reply, so the thread shows the same widget in every version of the page. A later leaf page init refuses a vocabulary that could no longer render it.

A widget on the page takes its state from the version being viewed: that version's markup plus the actions taken up to it, minus any a stamped version marked restated. A widget in a message belongs to no version. Its state is its markup plus every action taken on it, whichever version is open, and no revision can retract one. Choosing the answer to its question hands the thread back to the agent.

Titles

A title names a thread in Threads, in a few words of plain text. The agent can rename a thread later with leaf thread edit --title.

The agent's reply can take minutes, so when the user opens an untitled thread, Leaf also asks the harness's model for a title at once, in a separate request: in Claude Code, Leaf's plugin asks Haiku from inside the session, on the session's own login; in Codex, an App Server request; in Pi, a print-mode run of the model the user configured. Summaries

leaf thread summarize folds a run of consecutive messages in one thread under a summary of where they landed, a few sentences long and led by a name the agent may give the range. The thread shows the summary in place of the messages, which stay in the log and unfold from the summary's “5 earlier messages”. A range may take in earlier summaries, which the new one replaces. A summary answers nothing and closes nothing, so a question it folds stays On Me.

Once a thread is long, Leaf suggests a range to the agent with the user's next message. It takes in any earlier summaries and leaves the newest exchange outside, so a summary over it leaves the thread one summary; the agent decides whether to summarize. Editing a message inside a written summary's range removes the summary, so an outdated summary cannot hide the correction. A thread shows only the latest progress message an agent posts while working, and the one it left above each message the user has written since. Its next message there replaces the latest, its next reply the ones above the user's messages, and its turn ending does too where nothing before them still waits on an answer.

In Claude Code, the agent's own conversation, the main thread, takes in a thread message only between its steps: an idle session thinks before its first words, and a busy one first finishes the command it is running. Leaf makes three kinds of fork, set off by two moments: the user writing in a thread, and the main thread ending a turn. None can call tools, so each answers in text and Leaf acts on the answer. The fork that does a message's work is the main thread's own subagent, with the session's tools, which the main thread spawns where it judges the work can run beside its own. Leaf's Python decides every fork Leaf makes: when to make one, what to ask it, and what to do with its answer. Leaf's hooks module, TypeScript that Claude Code loads from Leaf's plugin, makes each with Claude Code's $.model.fork and hands back what came of it. It adds only what it alone sees, such as the tool calls the main thread is running and the end of a main thread's turn. Claude Code keeps the module it loaded until it loads another copy or the module's own code changes, while a session whose hooks run a Leaf checkout runs each hook from that checkout as it stands, so the session's module can be older than its Python. That is why the module only carries out Python's instructions: a change to what Leaf forks for, what it asks a fork or what it does with the answer changes only the Python, and an older module carries it out as it does any instruction. The module changes only for a Claude Code call or event Leaf starts to use. The fork subagent is no instruction of Leaf's: the main thread spawns it with Claude Code's Agent tool, and the module leaves a subagent's calls and turns alone.

Where a thread message goes

A thread message reaches the main thread as any input does: at its next tool call, or, when the session is idle, at the prompt of a turn the watch wakes. Beside that delivery, Leaf asks a line fork about the message. A line fork resends the main thread's last request with one question from Leaf, can't call tools, and returns within a few seconds with the working line, the agent's message saying what it will do about the user's message, such as “reading the reconnect traces”. Leaf posts the line as the agent's progress message, and from then until the agent answers, the message reads On it. The line fork's prompt is in Anatomy of a fork journey, as Leaf wrote it in one run.

A line fork writes for a round: the user's messages waiting in an open thread with nothing of the agent's after the oldest of them. A message that follows quickly in the same thread, such as “and also…”, joins the round, and a new line fork reads them all. A message sent after the agent has spoken in the thread, by its line or otherwise, starts no line fork, since the agent's words already stand after the round's first message. A background process of Leaf's hooks module asks for each line fork, and only for messages sent after it first read the page; every message reaches the main thread either way.

The line goes in only while its round still awaits it: while the thread's waiting messages are the ones the line fork read, and the agent has said nothing in the thread since the oldest of them. Leaf checks this as it appends the line, so a line never lands after the main thread's own words in its thread, nor speaks for a round a later message joined. The user chose to deliver the message at once rather than hold it from the main thread until the line goes in. Holding it would keep the line ahead of the main thread's words, but it needs a holder for each thread, a bound for a line fork that never answers and a wake when the bound runs out, and all it buys is the line's order, since the main thread judges every message itself and needs nothing from the line fork. What the user accepted: the main thread sometimes speaks in the thread before the line fork answers, and that line goes in nowhere.

Where the thread has grown long enough that Leaf would suggest a range of it to summarize, the module starts a second fork beside the line fork. It folds the thread's earlier discussion into one summary, which Leaf writes as the agent's and tells the main thread of. It answers on its own, so the line doesn't wait for it. The delivery of a message that came to a round awaiting a line, while the hooks module's process asks for line forks, leaves the suggestion out, and if the fork fails, Leaf tells the main thread the range it suggested.

The fork subagent

The fork subagent's shell commands run in the session's environment, so each leaf command it runs acts as the main thread's, in the main thread's turn. Leaf's hooks skip a subagent's tool boundary, which Claude Code names in the hook's input, so no delivery reaches it: the main thread takes the session's input and passes its fork what it needs. Leaf's hooks module leaves a subagent's calls and turns alone too.

Without it, the main thread's turn would end with the message owed and under way nowhere the page shows, and Leaf would wake the session for it again.

Claude Code tells the main thread as the fork's run ends, with a task notification that starts a turn of an idle session or joins the turn already running, and the main thread takes the fork's report into its context. Further messages in a thread

Each message the user sends in a thread whose earlier messages are all answered starts a round of its own, and a line fork writes its line, like the first. The main thread routes it as it did the first: it can pass a later message in a thread it gave a fork on to that fork with SendMessage, with the message's answer.ref, and a send resumes a fork whose run has ended; or it can give the message to a new fork, or answer it itself. Messages in different threads get a line fork each, side by side.

A message the user sends while the fork still works on the thread's last one usually finds the line standing after that one, so no line fork reads it: it goes to the main thread at its next tool call or prompt, which passes it on.

The main thread stays in charge

The main thread decides who does each message's work. It spawns a fork for a message whose work it judges can run beside its own, can steer the fork or ask it to stop with SendMessage, and answers the other messages itself. It takes its to-dos in the order it judges, and runs work bigger than a message in subagents. A fork is to change neither the session's files nor its plan: the main thread gives a fork only work that changes nothing it works on, as the Leaf skill's Claude Code reference asks. Nothing else enforces it.

The user chose that the main thread judge every message and spawn the fork itself, so Leaf keeps no record of a fork. The line fork could also judge whether a fork could do the work and tell the main thread so, but that only adds a line to what the main thread reads, and the main thread decides anyway, knowing its own work better than a fork judging from a snapshot of it. A later change might have Leaf spawn the fork itself and send it the thread's later messages. Its answer would come sooner, since it would wait neither for the main thread's next tool call nor on a main thread blocked in a long command. But Leaf would need its own judgment of which messages to give a fork, and for each thread it gives one, the turns, records and hooks that hold a thread for an agent Leaf spawned and tell the main thread what that agent did, since Claude Code tells a session nothing of an agent a plugin spawns.

Browser runtime

The browser runtime upgrades Leaf elements, draws threads and shared controls, sends updates, and keeps the page current. Its inputs meet in one read-only state.

The server supplies actions in effect for the displayed revision, threads, obligations and activity (Current state). The browser applies them to authored values and adds only what pending gestures decide by themselves.

Loading the runtime

Startup prepares a stable page before enabling its controls. Page loading distinguishes usable controls from the arrival of saved state.

Page loading

Live revisions

A revision’s executable identity is its registry, loaded JavaScript modules and inline module scripts. Each install pairs the revision with its corresponding state.

What both paths preserve

Replaced elements with matching authored ids inherit local values differing from authored defaults: typed values, checked state, disclosures, inner scroll, focus and caret. Replacements without matching ids do not preserve those values. Reading position follows a passage, not a pixel offset. Fresh documents use a one-time tab handoff that later reloads and Back do not replay; drafts and control arrangements use separate browser stores.

Installation waits during comment or reply writing, passage selection, card dragging, a pending update’s server response, or an open version menu. Open latest in the panel, or the leaf's menu's row for the newer page, installs the waiting revision immediately.

Server lifetime

The HTTP server exposes the page directory to browsers. A session-started server stops when no live session claims the page; a claim names the recipient of its updates. A server started from a bare shell or with --lifetime persistent runs until leaf server stop.

On leaf.page, a private browser session gets a hosted agent environment using the same page and event machinery (How leaf.page works).

Page addresses

A page's server binds the address its session arrived through: the SSH destination for an SSH session, otherwise loopback. The page keeps its host and port in service.json, so serving it again, changing its packages or reviving it keeps the same URL, and a watcher restarts a server whose process dies at that URL.

Each harness's contract says how its agent serves a page and hands over the URL. When the user can't reach it, the serving reference has the agent serve it on a hostname the user's browser can reach, or hand over an exported file. Leaf uses existing networks and opens no public tunnel. Another session takes a page over with leaf page claim, which moves its updates to that session without restarting the server.

Who can open a page

A page's URL carries an access key, which the browser keeps in a cookie. One key covers every Leaf page on the machine that serves it, so anyone with one page's URL and a network route to that machine can read and act on all of them. A page served on loopback opens only on that machine; one served on an SSH destination or another hostname opens from that network.

On leaf.page, each browser works on a private copy of a page. Its comments, choices and the hosted agent's revisions are visible to no other browser (The leaf.page website).

Offline exports

leaf page export PAGE -o FILE captures a stamped version as one HTML file that shows the page as it stands: its content, each widget drawn with the decisions recorded on it, and its images and fonts, with no script. Leaf draws it in the host's browser. With --runtime the file carries Leaf's runtime instead, so reading controls and page-owned code work offline; new Leaf choices, comments and Undo need the served page. An agent need not be running to record a choice on a live server. Either way the file holds none of the conversation with the agent, on screen or in its source: no threads or their attachments, to-dos, plan or changelogs. Pages containing live samples cannot export.

A package adds widgets to Leaf. The package interface is every name of Leaf’s that a package uses: each declaration key, property, event, element, function, custom property and class that Leaf defines. It is what a package’s author learns beyond HTML, CSS and JavaScript.

Widgets

A widget is a custom element: a tag the package names, such as <lf-verdict>, with a JavaScript class that the browser runs for each occurrence of the tag on a page. Every widget’s tag starts with lf-. Leaf drives that element from outside, as a script drives any element on a web page. It sets properties on the element, which are values assigned to the element object, as in element.state = …. It hears the events the element dispatches, which are named messages that reach whoever listens on the element. The element draws itself and says what the user did, and needs no base class and no function of Leaf’s to do either.

Example widget

lf-verdict asks whether to ship a release and records the answer. Its package is a directory of three files: 

verdict/
  registry.json
  defaults.css
  widgets/lf-verdict.js

Leaf finds each file by its name, and loads the module on a page that uses the tag. leaf package init DIR --widget lf-verdict writes a starter of this shape, and leaf page init --package DIR PAGE adds the package to a page (Build a package). The agent that writes the page puts the tag inside an lf-group, Leaf’s element for a named part of a page, whose label asks the question: 

<lf-group id="release" label="Ship 4.2 today?">
  <lf-verdict id="verdict"></lf-verdict>
</lf-group>

Declaration

registry.json declares the tag. Leaf’s server reads this file and never runs the module, so the file states everything the server acts on. 


{

    "description": "A ship-or-hold decision. Put it in an `lf-group` whose label asks the question.",
    "attributes": {
      "properties": { "verdict": { "enum": ["ship", "hold"] } },
      "required": ["id"]
    },
    "content": "empty",
    "verbs": {
      "decide": { "record": { "attr": "verdict" } }
    },
    "awaits": { "value": "decide" },
    "example": "<lf-group id=\"release\" label=\"Ship 4.2 today?\"><lf-verdict id=\"verdict\"></lf-verdict></lf-group>"
  }

The agent that writes a page reads description and example to choose the tag and write it. The attributes the tag may carry in a page’s markup, as a JSON Schema. An attribute is a name="value" pair in a tag, and leaf page check refuses one this schema doesn’t name. enum lists the answers the server accepts, each a string because an attribute’s value is text, and the module offers them as buttons. Any tag may carry an id, and required makes this one carry it, because Leaf keeps a widget’s answer under its id. The tag holds nothing the page’s author writes: the module draws all of it. A tag that leaves content out holds its author’s markup. A verb is one kind of action the user takes on the widget, under a name the package chooses, and the server refuses an action whose verb the declaration lacks. A verb keeps one answer for the whole widget unless its declaration says otherwise, so a later press replaces an earlier one. record names the attribute that holds the answer: the server checks an action’s value against the verdict attribute’s schema before it appends the action to the event log. Leaf’s instructions have the agent write the answer into that attribute when it next revises the page, so the markup shows the decision. A verb that keeps an answer for each part of a widget, or records something other than one attribute, says so with keys this widget leaves out (Registry keys). The widget asks the user something, where one that only records would leave awaits out. The question is the label of the group around the widget, and it stays on On Me, the user’s list of everything waiting on them, until it is answered. value names the verb whose value is the answer, so the question is answered once decide has one. Leaf then delivers that answer to the agent.

Module

widgets/lf-verdict.js defines the element, with one property for Leaf to set and one event for Leaf to hear. 


import { html, render } from "/vendor/lit.js";

const LABELS = { ship: "Ship", hold: "Hold" };

customElements.define(
  "lf-verdict",
  class extends HTMLElement {
    set state({ decide }) {
      const button = ([value, label]) =>
        html`<button
          type="button"
          aria-pressed=${decide.value === value}
          aria-disabled=${!decide.available}
          @click=${() => this.press(value)}
        >
          ${label}
        </button>`;
      render(Object.entries(LABELS).map(button), this);
    }

    press(value) {
      const action = { verb: "decide", detail: { value } };
      this.dispatchEvent(new CustomEvent("lf-action", { detail: action }));
    }
  },
);
Lit, a third-party templating library, draws the buttons. Leaf serves a copy at this path, and the module imports no code of Leaf’s own. A label for each answer the declaration’s enum lists. The server reads only the declaration, so the module names the answers again. Leaf sets state once the module has defined the element, and again each time the state changes, whether this tab, another tab, Undo or a new version of the page changed it. It holds each declared verb’s state by name, here decide, and the setter draws all of it each time. decide.value is the answer, or null before there is one, and aria-pressed marks its button. The page’s theme (the package that gives the page its look) draws a plain <button> and its pressed state, and a screen reader says which is pressed. decide.available is false while the user may not press, as when the page has no server to record the action. aria-disabled shows that and, unlike disabled, leaves the button in the keyboard’s reach. Leaf records nothing for a press while it is false, so the module needs no check of its own. The widget protocol lists what else a verb’s state holds. An action names its verb and carries its own detail. For a verb with a record, the detail is the value to record, under the key value, which Leaf then sets as decide.value. The element dispatches the action on itself in an lf-action event. A custom event carries its payload as its detail, so the action’s own detail sits one level inside the event’s. Leaf listens on the element it sets state on, so the event needs no other option. Leaf has set the new state by the time dispatchEvent returns, so the press shows at once. If the server then refuses the action, Leaf sets state back to what the server holds.

Needs and their forms

Whatever a package needs of Leaf is one of the kinds below, and each kind has its own form. lf-verdict needs three of them: the first two, and a theme’s choice.

A package leans on Leaf for The form it takes
What Leaf must know before any module runs A key in the widget’s declaration, such as awaits.
What changes while the page runs The widget protocol, which has three parts: properties Leaf sets on the element, such as state; events the element dispatches, such as lf-action; and attributes, properties and methods of the element that Leaf reads, such as data-lf-part, which marks a part of the widget that a user can comment on.
What a widget and a page’s author both need An element that Leaf defines on every page. A widget’s template writes it as a page’s markup does. <lf-age> is one: it shows how long ago a moment was and keeps that current.
What only Leaf can do or know A function the module imports, such as readObligations(), which reads what waits on the user or the agent.
A theme’s choice A custom property the stylesheet reads, such as var(--lf-accent), the theme’s accent colour.
A fact about where the widget’s box stands A custom property that Leaf or the page’s layout sets and the stylesheet reads, such as --lf-full-height, which a layout filling the window sets on the boxes that must fill their share of it.
What the widget’s box tells Leaf A custom property the stylesheet sets, such as --lf-ring-at, which says where the box’s focus ring belongs.
Leaf’s look for a part the widget draws A class the module writes on the part, such as .lf-rows for a list whose rows share their columns. A control needs none: a native one, such as a <button>, takes the theme’s look, and a function in Leaf’s library builds one that looks like Leaf’s own controls.
A part of an element Leaf builds inside the widget A class on that part, which the stylesheet selects, such as .lf-compose-field, the frame of a comment box that one of Leaf’s functions builds.

A widget uses HTML, CSS and the browser’s own APIs as any web page does, and none of that is Leaf’s. Leaf also ships a library of shared web code, such as the functions that build its controls and the ticks of a time axis. That code keeps none of the page’s state, a module imports it as it imports any library, and it is outside the interface too.

Design principles

Principle What it buys
Leaf drives a widget from outside. It sets properties, hears events, and reads the element’s attributes and the custom properties its stylesheet sets, as it could for any custom element. A widget need not import any code of Leaf’s, so one can be written to run on a page without Leaf too. A component from another UI library becomes a widget with a declaration and a wrapper of a few lines: the declaration’s record gains a property key that names the component’s property holding its value, and Leaf sets and reads that property (the widget protocol, “A third-party component”).
Leaf’s server runs no module. The declaration holds what the server must know, and nothing a module can answer for itself. Leaf checks a page’s markup, checks an action and lists a question on On Me from the declaration alone. So an edit of a page with a mistake in its markup never goes live, an action enters the log only after the server has checked it, and the agent that writes a page learns a widget by reading its declaration.
A function exists only for what Leaf alone can do or know. What HTML, CSS or the browser already does is written as that, and what a page’s author needs too is an element. People and agents already write HTML and CSS well, and the browser keeps a native control’s focus, activation and accessibility. A function of Leaf’s wrapping HTML or a native control would only add a name to learn. An age that stays current is the element <lf-age>: a page’s author writes it too, and a widget’s template needs no import for it.
Each kind of need has its own form. A package’s author knows where to look for a name, and a new need takes the form its kind already has.
The widgets Leaf ships use the same interface, with no private route into Leaf. Another author’s package can do whatever one of Leaf’s widgets does, and each of Leaf’s widgets is a worked example of the names it uses.

Adding a name

Each name in the interface is one more thing every author has to learn, and one more thing every later change to Leaf has to keep working. Leaf’s own widgets are written beside its runtime, where exporting one more function is the quickest way to finish a change. So whoever changes Leaf and finds a widget needing something of it asks these questions before adding a name:

  1. Does the widget need Leaf for this? HTML, CSS, the browser’s APIs and Leaf’s library add nothing to the interface.
  2. Can Leaf do it from outside? What Leaf does by setting a property, hearing an event or reading an attribute also works for a widget that imports nothing.
  3. Which kind of need is it? It takes that kind’s form. A need that fits no kind is a gap in the design, which the maintainer settles first.
  4. Who else would use it? A name that only one of Leaf’s widgets would use usually shouldn’t exist: either Leaf does the work for every element, or that widget does it alone. Where a page’s author, who writes no module, has the same need, the answer is an element that both can write.

Leaf’s developer instructions put these questions to every change to a widget (packages/AGENTS.md, “A widget’s need of Leaf”), and name the package interface among the invariants every change keeps (AGENTS.md, “Keep the package interface small”). Regular maintenance also looks for names the interface can lose, such as a function that only one example calls. The author of a package outside Leaf asks the first question the same way, and reports a need that only a new name would meet as an issue.
