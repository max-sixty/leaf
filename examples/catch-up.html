pull request #418 · Jaana's first contribution

Merge --stdin as it is?

#418 reads the files to check from standard input, one path per line, so git ls-files '*.md' | marram --stdin checks only tracked docs. Its tests pass on Linux, macOS and Windows, and it follows the existing argument handling.

One gap: without -z, git ls-files quotes any path holding a non-ASCII character or a newline, so docs/ja/入門.md arrives as "docs/ja/\345\205\245\351\226\200.md" and fails to open. git ls-files -z writes each path whole, ended by a NUL byte, the way xargs -0 reads them. I'd ask for it before merging: a translated docs tree hits this on its first run, and the change is a few lines. The review I'd post: 

Thanks, this is a clean change and the tests cover it well. Before I merge, could you add `-0` so `--stdin` can also read NUL-separated paths, as `git ls-files -z` writes them? Without it, git quotes a name like `docs/ja/入門.md`, which then doesn't open. Happy to point you at where the parser would take it.

private security report · Nadia, Nov 9

Open an advisory for redirects into internal networks?

marram follows redirects wherever they lead, so a docs link that redirects to 169.254.169.254 makes CI request the cloud metadata service and log its status. The body never reaches the log: an attacker learns which internal hosts answer, not what they hold.

Reproduced
1.7.2 on a self-hosted EC2 runner logged 200 OK
Nadia asks
a CVE, and public disclosure on Dec 9
Fix
refuse redirects from a public address into a private or link-local one unless --allow-private is set

I'd open the advisory: the fix is small, and 1.7.3 ships on Nov 27, before Nadia's date. A team whose public links redirect into its own network, such as a sign-on page, would need the flag.
