Proposal: one message workflow, distinct page state

The proposed next implementation combines message delivery and response progress into one reading, derives thread attention from it, and separates the page's overall agent state. Review those boundaries below; the backend has not changed yet.

Level Question Proposed reading
Message workflow What happened to this input and its answer? Sending, Sent, Queued, Picked up, Working, Replying; typed activity and uncertainty qualify the reading
Thread attention Does this discussion need me? Needs you, Waiting, or no attention mark; explicit resolution remains separate
Overall page state Is the page's agent available and active? Ownership, carrier availability, current activity, and declared overall work

Consolidate the message classifications

Interaction receipts, sending failures, and streamed response state become one shared workflow reading. Keep exact input, delivery, turn, claim, and reply bindings underneath it. The displayed stage selects the strongest applicable evidence; proactive work can have no preceding message and appears on its thread or widget instead.

Store no new thread-status table. Derive stage, optional typed activity, condition, and next actor from the existing evidence. A condition retains its cause: a failed send, an interrupted turn, or lost observation are different problems. Typed Thinking can refine Working only with host evidence bound to that input or subject; otherwise it stays overall page activity. A completed turn alone never proves an answer.

Show one compact mark beside the message timestamp. Derive thread groups and margin treatment from the same reading and outstanding reader Asks. A reader Ask takes placement precedence while older agent work stays visible as secondary detail. No obligation means no attention mark, not automatic resolution. A settled input normally loses its active-work mark rather than gaining a permanent Answered badge.

Overall activity does not confer message progress

The banner and Leaves tray describe the page's agent relationship and overall work. A busy agent does not make every message Working. Thread counts can sit beside overall state as separate information, for example “Agent active · 2 threads need you.” Both readings can use the same evidence while answering different questions.

External requests are operation buttons

These ask a host to do something: for example, a command-hub operation or a release rollback. Leaf records the request, the host executes it, and a receipt records success or failure. Each request seat allows one pending operation; success completes it, while failure reopens it.

Keep this command lifecycle because Sent or Picked up cannot prove that a rollback succeeded. Its work and result can feed shared activity and attention, but this proposal does not change the request protocol.

Defer a typed notification bus

Later, workflow changes, new reader Asks, page availability changes, and request outcomes can produce typed events. Notices, accessibility announcements, badges, and other consumers can subscribe and decide what to show. First check the existing subscription machinery; the bus should report domain transitions without becoming another state store.

This is deferred work, along with durable unread tracking. The current Threads count measures unresolved discussions, not unread messages.

Recommended initial implementation

Implement the shared message workflow and derived thread attention, together with the overall page-state separation. Prove newer input during an older reply, a reader Ask concurrent with agent work, an ended turn, stale observation, and exact response settlement.

Then retain typed thinking and tool observations. Independently running jobs and delegated work follow with their own observation and continuation contracts. The full design is in notes/thread-status-proposal.md.

Earlier UI work — accordion and summary design history

Historical snapshots and prototype fixtures follow. They describe the earlier UI review, not outstanding decisions for the activity model.

Expandable thread summaries

Summaries now read as part of the conversation: no filled background or accent stripe, a quiet sentence-case label, and italic prose aligned with the messages. The italics distinguish the agent's retrospective account from the original exchange. The summary stays visible; Show messages reveals its sources. This applies the less prominent disclosure treatment described by GOV.UK and the supporting-detail pattern in Carbon.

When a conversation grows long, Leaf suggests summarization in the context delivered to its agent. The agent chooses a contiguous range and writes a short summary; the original messages remain available underneath it.

Open the summary to inspect the originals, then use the control along their right edge to fold them again. Later replies stay outside the covered range. A new summary can extend that range as the discussion continues. Summaries preserve discussion history; decisions and current status still belong in the document.

Try the working summary example: open Threads and select “Workshop planning”. Show messages expands the original exchange; its right-edge arrow collapses it. Search still finds the original wording. Covered questions that need an answer stay visible, and editing a covered message removes the outdated summary.

Keep the current exchange in view

The same conversation before and after summarization: seven older messages become one checkpoint, leaving the latest question and reply field visible. The originals remain available through Show messages.

Try the real Threads panel

One conversation expands at a time. The reply field spans the conversation’s width. Author and time sit above each message; delivery receipts sit below the message they describe. Unfinished drafts survive switching threads. Search, filters, and links to individual messages reveal their target.

Use Enter or Space on a title to expand it; arrow keys and Home/End move between titles. Use t / Shift+t to walk threads, c to reply, and Cmd/Ctrl+Enter to send. Escape leaves the reply box, collapses the conversation, then steps back out of the panel.

Sending and Sent share a delivery line so confirmation does not shift the conversation. The local review also checks that collapsed titles retain reader obligations and ongoing agent work. The richer activity ontology remains separate work.

Keep the next turn visible

Collapsed titles show On you when the reader owes the next turn. Ongoing agent work stays visible even when a newer message is queued. Full delivery details remain with their message.

The same eleven conversations

Opening Threads previously filled the panel with the first two discussions. The compact accordion fits all eleven titles in the same viewport, then opens the selected discussion in place.

One conversation, one inset

The full-width composer removes the empty gutter. Author and time move above the message, giving prose the full reading width. Message spacing separates turns while the collapsed rows stay compact.

Layout decision — complete

The compact accordion was selected and implemented. The spacing study no longer asks for another layout choice.

Keep the structure, remove the repetition

The title and message count remain compact. An open conversation uses one shared inset for its quote, messages, and reply field. Author and time form a small header instead of consuming a separate column. A Draft marker preserves unfinished work, and the bottom control collapses long threads.

Carbon’s accordion guidance explicitly allows inputs to fill the panel even when prose has different margins. That supports the full-width composer here; precise spacing remains a Leaf design choice.

Signal distinguishes Sent, Delivered, and Read for each message. Applying that distinction here, Sent belongs beneath the sent message and no longer appears as a thread title’s status. Current work and failure states can still help identify a thread before opening it.

Component reuse is possible: Web Awesome supplies compatible web components, while Radix uses React and would introduce another rendering framework beside Leaf’s Lit components. Neither decides chat spacing or message delivery placement. This pass keeps Leaf’s components; a broader disclosure refactor could use native details/summary, including exclusive groups, without adding a library.
