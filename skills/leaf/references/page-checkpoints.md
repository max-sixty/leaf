# Page checkpoints and ending

## Pre-handover review

The main skill's "Publish and review" section says when a page takes this review.
It adds the browser render check, in both colour schemes, to the markup check every
activation runs:

```bash
leaf page check <page> --render
```

Fix every failure; a screenshot is no substitute. The check reads the desktop at the
size of the window the user last viewed the page in, over the last day, or in a
1280x720 laptop window before they have; `browser.desktop` names the size it read and
which of the two it was.

A clean check saves screens at desktop, widest-window and phone widths, up to eight down
the page at each width, plus one just before each layout change, such as a sidebar
stacking. Inspect the end of a longer page yourself. Look in every screen for illegible
labels in drawings, lone tiles, pins covering headings, and a summary that comes too
late on a phone, and fix what the page controls.

Test recorded actions in a disposable review copy
[served without an agent claim](serving-pages.md#page-lifetime), so the tests stay out
of the user's page and task.

Then decide whether a fresh reader sees the page before the user does. A reader with
only the user's request and the saved screens catches what your own notes fill in for
you: a step you skipped, a term you never defined, something you only described in words
when it needed a picture. A subagent can be that reader, and it costs the time it takes
before the user gets the page. Give the page one when it will be read later or by other
people, who can't ask you what you meant, or when it makes an argument the user must
follow to decide, where one gap breaks the chain. Hand over without one when the page is
short and the user is waiting on it in the middle of their own work: there the wait
costs more than the reader would find, and the user can ask about anything unclear as
they read.

When you run one, give it only the request, saved screens and served page, without
your notes. Have it try the task from the initial view, verify the visible outcome,
and judge the effort of finding information, comparing it and reaching a decision or
action. Its first judgment comes from what the user can see and do, before reading
source or the author's explanations. Have it report anything it can't follow, has to
guess or has to picture from a description, and fix what it finds.

In your own read-through, check that headings state findings, claims have evidence,
decisions have controls, and every line of prose is needed, and draw anything the page
explains only in words when a picture would show it.

For a page with contents, start at the top at desktop and phone widths and jump to a
later section without first scrolling to find the navigation. Follow the page's links
with pointer and keyboard, and check that each destination leaves the user oriented.

For a page with obligations on On me, the check also saves the window at each of the first
eight as `m` reaches it from the top (`conversation-loop.md`, "The On lists"). At each,
review the question against `authoring-on-me.md`, "On the page", and check that the
numbers shown match the actions offered and the next `m` reaches the next item on the
user's On me list.

If you can't see the rendered page, review the words, evidence and choices from the
active HTML and `leaf page state <page>`, and report the visual and keyboard review as
not done. When the check's `browser` field is `unavailable`, report the render check as
unfinished, along with the run of the page's code if it needed one.

## Page diagnostics

`leaf page inspect <page>` reports the saved source's CSS and JavaScript inventory,
attributed to files and locations, separately from the selected layer. Page-owned widget
implementations are listed too. `--revision N` inspects an immutable revision;
`--compare-to N` adds changed source files and metric deltas from revision N.
These are source bytes, not transfer or execution measurements. CSS generated by
JavaScript is outside the CSS inventory.

**About this page** in the Leaf menu shows page details, the displayed revision's inventory and a
passive reading of the current tab. **Copy diagnostics** copies the structured report,
including the rendering environment captured with each observation. **Show on page**
reveals an observed element; a stale target requires a fresh observation. Retained
browser readings keep their own revision, viewport, runtime, layer and freshness.
Source comparisons do not subtract browser measurements across different states.
Exports and public previews show browser context alone, without starting a private session.
The report supplies measurements for a design judgment, without scores or CSS budgets.
It is optional and adds no handoff gate.

## Stamp checkpoints

Stamp a record at each checkpoint the user would name, such as an approved plan or the end of
the conversation, and wherever a reference requires a stamped version, as taking in an
answer to a page's obligation does (`authoring-revisions.md`). Answering a message is not by
itself a checkpoint.

```bash
leaf page stamp <page> --text "<what changed>"
```

The stamp gives the current source the next public version number. A browser at the
page's root follows new revisions; one open at `/versions/vN.html` stays on that
version.

## Ending

To finish, handle every event in the delivered batch and write the answer each
acknowledged update's `answer` names (`event-batches.md`). A finished record ends on a
stamped final version that honours open obligations and the reports still in force; an
unstamped page can close directly. Then run:

```bash
leaf page close <page>
```

`page close` ends the agent's side of the page, and refuses while events are pending or an
update still owes its answer. It takes the page off the watch, and closing the last
watched page ends the watcher. It doesn't stop the server or delete the page
(`serving-pages.md`, "Page lifetime"). Don't close a persistent page because one
session's work on it is done.
