How far back should z reach?

Leaf's log already keeps every gesture forever, so the storage half of Vim's persistent undo is there; the safety half is missing. On a page you left three weeks ago, z reopens a thread you resolved then, below the fold, and no key or control puts back what an undo took.

Six reach rules and three add-ons, cheapest first

A reach rule decides which of your gestures z may take back; the rules differ on how far back that goes and whether it can change something you are not looking at. An add-on combines with any rule.

Which undo should Leaf build: a tighter reach, a visible reach, redo, or a panel?

Pick a rule or a preset, then operate it on the page below. My recommendation is Show, then take with the bar naming its target, now: it has no limit and never acts where you aren't looking. Redo is the other half of Vim's safety, but it costs more than it looks (below), so I'd build it second and the Changes panel on top of both.

Redo fits the log as an undo of an undo, with three costs

Today an undo names one gesture, and taken_back (events.py) returns every id an undo names, which every Python fold reads. Undo is one-way because the door refuses an undo naming an undo, taken_back is a flat set, and the undo list skips undos.

Redo is an undo naming your own standing undo. Nothing leaves the log and no counter-event is invented, so the invariant in AGENTS.md holds as written. taken_back changes so that an undo counts only while no standing undo names it. The playground's log, under the simulated page, folds exactly this way: turn on redo, press z then Z, and the second undo strikes through the first.

The costs are these. First, a restored gesture reads at its original place in the log, as every fold reads effects, so it shows nothing once a later event on the same target stands: any reply, the agent's included, reopens a thread, and a later pick supersedes an earlier one. The door has to refuse that redo, and the one general check is to fold the log with and without the undo and compare what the page shows. In the playground, undo the Scope resolve, reply in Scope, and Redo is no longer offered. Second, readers that follow undoes one level have to follow the chain: the words a delivery carries (GestureWords.says) and the browser's coverage lookups. Third, an undo owes the agent no answer, but a redo brings back the restored gesture's answer obligation, which the stop hook enforces and the delivery never mentions; the delivery must carry it, and the agent's guidance that an undo and its target cancel out needs a clause for a redo.

The alternative, re-sending the gesture as a new event, avoids the position problem but loses the gesture's identity: the agent reads a fresh pick, and the history can't pair the undo with what it undid.

Vim's undo tree differs in kind. g- and g+ restore any past state, superseded branches included, where this redo restores only what would still show. The Changes panel offers selective undo instead: any standing gesture, in any order.

What each design changes in the code
Last 7 days
projection/commands.js compares the head's ts with the clock. The 7 is a constant someone has to pick, which is the arbitrary limit you wanted to avoid.
This visit only
commands.js notes the undo candidates present at the first reading, and undoable() refuses a head among them. Browser only.
Say what z takes
served_state/document.py adds each candidate's words from GestureWords (gesture_words.py). Today served_state/browser.py builds that only for a page that shows history, so every state read would pay for it. undoSentence and the notice read the words in place of the per-kind words in commands.js.
Show, then take
document.py marks each candidate the agent has picked up, from the delivery evidence the workflows already read. commands.js holds an armed state that the next gesture or key clears, and so does a scroll that takes the target out of view. The reveal goes to the target the way an lf-activity row's link does: a thread opens, a widget scrolls into view and is outlined. It needs the words above too.
Only what's in view
Every press reads each candidate's geometry, and a thread open in the panel counts as in view. z then means something different after every scroll.
Redo on Z
taken_back counts an undo only while it stands; UndoReading.error admits an undo naming your own standing undo when folding without it changes what the page shows; document.py serves a redo list; projection/model.js lets a local redo override the server's reading that the target is withdrawn, as a pending forward action does; commands.js binds Z; gesture_words.py, the coverage lookup in browser.py, and projection/presentation.js follow the chain; delivery.py carries the restored answer; the undo handling text in registry.json, lf-activity.js's "undone" label, events.md, and event-batches.md learn the redo.
Changes panel
A third tray beside Asks and Leaves, with its glossary entry, keyboard and touch routes. It is served the history reading on demand, which today reaches only a page placing lf-activity, filtered to your own gestures. That reading stops at 50 rows (history.py's LIMIT), an arbitrary limit the panel would need to page past. Its Undo and Redo go through the one withdraw door.
