Design · Catch up

Catch up as a widget

Catch up is now lf-deck, a widget the agent writes on the page around the questions it is waiting on. The user takes them one card at a time, as in Slack's Catch up: answering a card brings up the next, Later leaves one waiting for the end of the pass, and Back returns to change an answer.

Try it

The sample is a page of its own, so nothing you do in it reaches this page, and Reset starts it again. Pick Keep Redis, and the next card comes up as soon as the answer is recorded. Press Later on the upgrade note, pick two beta platforms and press Done, then Later past the draft and the retry question, and approve the release notes. The bar then counts the cards still to answer, and Go through the 3 starts again from the first of them. Back returns to a card you answered, where its own controls change the answer. From the keyboard, m goes to the open card's question and its number keys answer it; m again leaves it for later. On a phone, a swipe left is Later and a swipe right moves on from an answered card.

What changed from the last version

  • It's a widget on the page. The agent writes lf-deck around its asks as it would any other widget, and chooses which questions go in it and in what order. The Catch up button at the panel's foot, and the deck covering the whole window, are gone.
  • A card is the item itself, where the agent wrote it. Each child of the deck is a card, usually an lf-ask with its evidence and widget, so nothing is moved or copied. The question of what a card holds, and the summary candidate, went away with that.
  • An answer moves on in about 50 ms. The next card comes up as soon as the server's reading of the answer arrives: 36 to 56 ms from the click across six timed answers in Chrome and Firefox, with the old card flying off over it for 200 ms. The last prototype waited a fixed 700 ms after that reading and then flew the card for 240 ms, nearly a second per answer, and ran three whole Leaf windows on one page.

How it works

The deck shows one member at a time, as a tab set does, and uses the same runtime support (x-views). The runtime picks the card it opens on and the deck records each card it shows, so a reload comes back to the same card; no event records it. Inactive cards are hidden="until-found", so find-in-page, a link to something inside a card, and the m walk each open the card holding what they reach.

A card waits while it holds an obligation open on the user, read from the server's inventory with obligationsIn, the rule lf-tally counts by, and the bar counts in the tally's words. When the reading says the open card no longer waits after the user answered it on the card, the next waiting card comes up. A wait that ends any other way, such as a comment that leaves the card with the agent, leaves the card where it is with Next, since news shouldn't move what the user is reading. Later records nothing, so a card left for later stays on On me. The deck adds no event kind and no protocol bump, and no other widget knows it exists.

The bar stands above the card and its forward control keeps the room of its widest label, so neither cards of different heights nor changing labels move a control under the pointer, and a card that comes up takes no press for a quarter second. Only a touch drag moves a card; a mouse drag across a card still selects its words, which is how a comment starts.

Should every page have the deck?

It ships as an optional deck package, so a page has it only when the agent selects the package, and only agents who select it learn it. In the default package every page would have it, and every agent writing a page would read one more entry; its code loads only on pages that use it.

recommendedMove it into the default package Agents can reach for it on any page where the user has several things to get through. Keep it an optional package Agents use it only when a page selects deck.
