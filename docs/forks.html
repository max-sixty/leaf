how it works

Forks

In Claude Code, Leaf hands the user's thread messages to forks: copies of the session's conversation that run beside the session. A fork posts the agent's first words in the thread within a few seconds, whether the session is busy or idle, and a fork with the session's tools can do a small task and answer it while the session carries on with its own work.

Today the first words come from a fork in every Claude Code session, unless LEAF_FORK_REPLIES=off is set. A fork that does the work, and takes its thread's later messages, is built, and acts only with LEAF_FORK_WORK=on in Claude Code's environment; the rest of the design is planned. Each part below says which, and What's built and what's planned lists them.

This page is the design's reference, for people and for agents. It explains the mechanism. The exact rules live in the session lifetime contract and in the module headers listed under Where each rule is written. The research and measurements behind the design are in notes/fork-replies.md.

Names on this page

Main thread
The session's own conversation, the one the user talks to, as opposed to the forks and subagents made from it.
Line fork
A fork made with $.model.fork, which resends the main thread's last request with one question from Leaf and returns text in 2 to 3 s. It can't call tools. It writes the working message and sorts the message.
Working fork
A background subagent with the main thread's transcript, model and tools ($.agent.spawn with subagentType: "fork"), spawned without a name, so the main thread reaches it by its agent id. It does one thread's work and answers it.
Working line
The agent's progress message in a thread, saying what it will do about the message, such as “reading the reconnect traces”. It stands until the agent's answer replaces it.
Waiting messages
The user's messages in a thread since the agent's last answer there. The newest one owes the thread's answer.
Kept back
A new thread message a line turn holds from the main thread while a line fork writes its working message and sorts it: an agent turn admission opens with the message, which ends as the line fork answers or lapses 30 s after it opened.
Holds
A turn holds a thread's messages from the moment it takes the thread, by picking up its messages or answering it, until another turn does. Who holds a message gives the exact rule.
Take
The line fork's judgment that a working fork should do the work (take), and the act that gives the thread to one: the line turn closes and the fork's own turn takes the thread.
Hand over, hand back
Leaf hands a kept-back message over to the main thread, as the line fork's hand_over judgment asks or when its line turn ends. A working fork hands its thread back to the main thread, with HAND BACK: or by ending unanswered (hand_back).
Pages follower
The background process Leaf's hooks module runs for a session that holds a page. It lists the messages Leaf keeps back, and the module asks a line fork about each. While it runs it holds the session's fork lane, a lock that tells admission a follower will list what it keeps back (forks.take_lane), so the code says “lane” where this page says the follower is running.
Turn
A span of an agent's work that Leaf's records name. The main thread works in its turns, and each line fork and each run of a working fork has a turn of its own, a line turn or a fork's, whose kind never changes.
Delivery
How Leaf hands messages to a turn: their text and thread, and for the message that owes an answer, the reply reference its leaf thread reply names. A delivery too large for a hook goes by pointer, and the agent's leaf delivery ack records it.
Pickup
The event in the page log that records a turn taking messages in. It names the session and the turn. A line turn's pickup is held: it holds the thread without taking the messages in.
Start
The record that the agent is at work on one message or to-do, written by leaf task start or by a progress reply the agent posts. It names its turn and stops counting when the turn ends.
Clerk's line
A line Leaf queues for the main thread, which it reads at its next tool boundary or prompt. A line telling it of a to-do a fork opened wakes an idle session.
To-do
Work the agent owes on a thread until it ends it, opened with leaf thread reply --todo. A to-do is the obligation a significant task becomes.

The path of one thread message

When the user writes in a thread with no other waiting message, while the session's pages follower runs, and no running fork's turn took the thread, admission opens a line turn that picks the message up, which keeps it from the main thread, and the module asks a line fork for the working message. From then until the agent answers, the message reads On it. The line fork reads the message against the conversation, writes the working message, and sorts the message by who should do the work. Leaf posts the line as the agent's and sends the message where the sort says. If no line comes, the line turn lapses 30 s after it opened, as any unconfirmed agent turn does (activity.STARTING_GRACE), and the message is the main thread's; Leaf ends the turn at once when the line fork fails or the newest message owes no reply.

Keeping a message back is a turn's pickup in the log, as every hold is: the line turn's, which admission records with the message. That pickup is held: it holds the thread as any pickup does, but no reader of delivery counts it, so the message reads as sent to the session until a turn opens it, the working fork's take or the main thread's. The session's agent-turns record marks the turn a line turn as admission opens it, and a turn's mark never changes, so every reader, the holder in leaf page state among them, tells a line turn from a fork's by that mark, and a line fork's late or repeated step, as a reloaded hooks module can send, does nothing once its line turn no longer runs. Its ways out are an agent turn's: the turn closing, which writes the session's agent turns, or lapsing. A line turn that has ended keeps nothing. The lane decides only whether admission opens one, since the line fork runs in the hooks module rather than the follower. This adds a pickup to each kept-back message, and an entry to the session's agent turns. Until 2026-11-15, keeping back was read from the follower's lease and a hand-over file outside the log, because the lease ending had to end it.

How the line fork sorts a message

The message Where it goes Status
Small: a question or task a fork can finish beside the main thread, such as a lookup, research that writes only its own scratch files, or a dispatch to another session A working fork, which answers it built judged take; acted on only with the flag
Significant: work on the session's files, branch, page or pull requests, or research long enough to need progress of its own A to-do on the thread, which the main thread schedules planned judged hand_over today, but research that writes only its own scratch files is judged take
Needed now: the user's answer to a question the main thread asked, or steering its current work The main thread, at its next tool boundary, or woken if idle built judged hand_over

Today the line fork judges two ways (forks.ANSWER). take means a fork with the session's tools could do the work start to finish beside the main thread: it needs nothing the main thread is changing or about to change (its files and branch, the page's source, its pull requests), settles no question the main thread is weighing, and waits on nothing the session is running. hand_over means the work belongs with the main thread. Leaf records each judgment in the page's diagnostics (fork_outcome). Without the flag, Leaf posts the line and gives every message to the main thread.

The planned sort splits hand_over in two. Input the main thread needs now can't wait as a to-do, since it changes the work the to-do would wait behind. Research sits on the line between small and significant: a fork can do it, but when it runs for minutes it needs progress lines of its own, so the line fork decides by the message. A working fork that finds a task bigger than it looked can still make it a to-do (To-dos).

A working fork takes a message

When the line fork judges take, Leaf posts the working message, then, in one page transaction, closes the line turn, opens a turn for the working fork and records that turn's pickup with a delivery made for it (forks._take), so the message never goes to the main thread between them. Leaf's hooks module then spawns the working fork with that delivery and tells Leaf which agent runs the turn (forks.started); or it resumes the fork that answered the thread before, whose agent id Leaf names the turn with as it opens it (Follow-ups and flurries). The fork works with the session's tools and answers with its own leaf thread reply, using the reply reference its delivery names, and the turn its task names (Who a leaf command acts as). built only with the flag

Who holds a message

Leaf ties work to the turn it runs in: a pickup, a start or an agent's reply names a turn, and a pickup or a start stops counting when that turn ends. The main thread works in its own turns, and Leaf keeps a turn for each line fork and each run of a working fork in the session's agent-turns record (state.AGENT_TURNS), which marks each a line turn or a fork's. A line turn opens as admission keeps a message back. A take closes it and opens the working fork's turn before Claude Code starts or resumes the fork, which closes when the hooks module reports that the fork's run ended. A turn whose start nothing has confirmed lapses 30 s after it opened: a line turn, which nothing renews, and a fork's until the module confirms the fork it spawned or resumed runs, as when the module lost the take. The confirmation and the fork's tool boundaries renew a fork's turn, which then lapses only when nothing has renewed it within the working grace, 15 minutes. built only with the flag

A turn holds a thread from the moment it takes it until another turn does, whether it is the main thread's turn or a fork's. A pickup takes a thread, and so does an answer:

  • Of the turns that picked up any of a thread's waiting messages, the one with the newest pickup holds all of them.
  • A message no turn has picked up yet is held by the turn that last took its thread, by a pickup or an answer, if that turn is a running fork's. So a running fork keeps its thread's further messages even after it has answered, and the main thread gets them once its own answer took the thread over.
  • An answered message is held by the turn that answered it, which the reply names.

Every reader of received input asks one reading which turn holds each thread, with its waiting messages (forks.page_holding): delivery, the hooks, the page's activity reading, keeping a thread back for a line fork, the end of a fork's run and every writer's command. A fork's turn keeps the main thread off the messages it holds only while it runs, that is while it is open and renewed. Once it closes or lapses, those messages are the main thread's to answer, though the closed turn still holds what it picked up until another turn picks it up.

leaf page state names a holder on each thread and each answer the agent owes: the main thread, a line turn while a line fork judges the thread, or a fork by the agent id the main thread reaches it by (agent, null in the second or so before Claude Code has started the fork). A thread's holder is the turn that holds it, with whether that turn is running, closed or lapsed. An answer's holder is who owes it now: its thread's holder while that is a running turn, and otherwise the main thread (holding.owed_by). Delivery, the Stop hook and the watch read the same reading. A main thread recovering what it owes there, as after a compaction, leaves a running fork's answer to the fork, and a message a line fork is judging to it. No shipped instruction asks it to: the field alone does it. On the eval recovery-leaves-a-forks-answer, the agent left the fork's answer 3 times in 3 with holder and 0 in 3 without it. built

One rule for a fork's writes

A fork's turn may act only on the messages it holds or that no turn holds. One function checks each of its writes as the write is made (holding.refuse_unheld): its pickups, which are its take, its tool boundaries and its acknowledgement of a delivery handed to it by pointer; its replies, including a message in the thread that answers nothing, which counts against the thread's latest messages; and its starts. An answered message is held by the turn that answered it, so a fork may repeat its own answer, but may not answer again a message the main thread answered, even with the reply reference the fork's delivery gave it.

When the main thread takes a thread over

While a fork's turn runs, the main thread isn't given the messages the fork holds. Its deliveries leave them out (delivery.deliverable), its Stop hook and watch neither keep its turn from ending over them nor remind it of them (activity.agent_holds), and its own pickups leave them out (holding.pickable). While the fork's turn runs, the thread's further messages go to the fork, before and after it answers.

The main thread is sovereign all the same: it can answer a message the fork holds. Its answer takes the thread over at once, as a pickup would once the fork's turn ended, and the fork's later reply, start or message in that thread is refused. The thread's next message then goes to the main thread while the fork still runs.

Once the fork's turn closes or lapses, a message it left waiting is the main thread's input: the main thread's next delivery hands it over with a reply reference of its own. The main thread's pickup of it is then the newest, so it takes the thread over, and the fork's later pickup, reply or start on that thread is refused.

Who a leaf command acts as

A working fork's shell commands run in the session's environment, so a leaf command it runs looks like one of the main thread's. The fork tells Leaf which are its own: the fork's task names the turn Leaf opened for it and tells it to name that turn in each leaf command, as in leaf --turn <turn> thread reply … (forks.work_prompt). The command still begins with leaf, so a permission rule allowing leaf commands still matches it. The turn it names decides the writes that name a turn: a reply, a start, a pickup and an acknowledgement. built only with the flag

The three actors a leaf command can run as, where the session holds the page.
Actor The command What it may do
The main thread names no turn act on anything the session owes, in the main thread's turn
An agent with an open turn names that turn reply, start and acknowledge in that turn, on the messages it holds or no turn holds (One rule for a fork's writes)
An agent whose turn ended names a turn that isn't open nothing: every command it runs is refused (state.acting_agent_turn)

A fork's commands act in its turn from its first one: the turn has its id from the moment Leaf opens it, while the fork's agent id comes only once Claude Code has spawned the fork. A resumed fork's message names its new turn in place of the one its transcript names. A command naming a turn that has ended, the old one among them, is refused. A command Leaf prints for the fork to run next, such as the answer to an owed update or a delivery's acknowledgement, begins with the same --turn as the fork's command that printed it.

A command that names no turn acts as the main thread on a thread a running fork or a line fork holds, whether the main thread's own, a worker's, a fork's that left out its turn, a fork's script's or a terminal's. It goes through with the main thread's authority, as you chose on 14 Nov over refusing it, and says beside its result which fork holds the thread, and for an answer, which takes the thread, that it took it and how to stop the fork (holding.authorize). built

You chose on 15 Nov that the fork names its own turn, as its task tells it, over Leaf's PreToolUse hook rewriting each of its leaf commands to name its agent id. That hook could mark only a leaf that began its Bash call, so it denied every other form, and it couldn't tell a new fork's command from a worker's until Claude Code had said which agent it spawned, so it denied those too in the meantime.

Claude Code runs none of a plugin's tool.call hooks for an agent that plugin spawned (measured at Claude Code 2.1.322), so Leaf's hooks module can't see a fork's tool calls. The PostToolBatch hook in hooks.json names the fork: at each of the fork's tool boundaries it renews the fork's turn and hands it the thread's further messages (hook_transport.carry_agent_turn), and it hands the fork nothing else of the main thread's.

When a fork's run ends

As a working fork's run ends, the hooks module tells Leaf (forks.ended), which closes the fork's turn and judges each thread by the messages that turn picked up itself and by what the turn wrote: its replies name it, so Leaf never credits the fork with an answer or a to-do another turn wrote. The judgment says who owes the thread next. A message the user took back counts for nothing. Leaf's clerk tells the main thread of every outcome except taken_over, since the turn that took the thread over already has it, and resolved, since the thread owes nothing. built only with the flag

Each outcome forks.ended gives a thread, and what the main thread hears of it.
Outcome When The main thread hears
answer The fork's own replies answered every message it picked up. That the fork answered, so it can read the answer and correct it where what it knows shows it wrong; and that the thread owes nothing, where nothing waits in it and no to-do on it is open. A message the user wrote since, which the fork never picked up, Leaf passes on as any new message.
todo As for answer, and a reply of the fork's own opened a to-do on the thread that is still open, usually its answer. That the fork answered and opened the to-do, named with its text, which the main thread now owes and schedules. If the session is idle, Leaf wakes it.
hand_back A message it picked up still waits, and the closed turn still holds the thread: the fork gave it back with HAND BACK: and a reason, failed, or ended without answering. That the fork gave the thread back, and why, and the user's waiting messages themselves, as new input at its next tool boundary or prompt (delivery.deliverable). If the session is idle, Leaf wakes it.
taken_over Another turn picked the thread up since the fork did, or answered one of the messages the fork picked up, as the main thread can while the fork runs. Nothing: the turn that took the thread over has it. The page's diagnostics name that turn.
resolved The user resolved the thread, or a choice's answer closed it, while the fork worked, and no message it picked up was answered. Nothing: the thread owes nothing.

How a fork tells the main thread

Claude Code tells the main thread nothing of a fork a hooks module spawns: no row in its transcript, and no notification or wake when its first run ends. So Leaf tells it, in lines its clerk queues: one as a fork takes a thread, naming the fork's agent id so the main thread can SendMessage it, and one as the fork's run ends. A take's line waits until the hooks module says the fork runs (forks.started): once Claude Code has started a new fork, since Leaf learns its id only then, and once it has delivered a resumed fork's message. A line waits for the main thread's next tool boundary or prompt; a take's line still waiting as the fork's run ends leaves the queue, since the end's line says where the thread stands. Where the run leaves the main thread owing something, the answer to a thread the fork gave back or a to-do the fork opened, Leaf also wakes an idle session for it. The end of a resumed run is different: Claude Code notifies the main thread of it, which starts a turn on an idle session, and that turn reads the queued lines. built only with the flag

The user chose the clerk's line on 2026-11-11, over the fork's own SendMessage to main. Leaf writes the line from the log, so it also covers a fork that failed or was stopped before it could write, and Leaf's own wake comes only when the main thread owes something, after a first run and a resumed one alike, though Claude Code still wakes it at every resumed run's end. A fork's SendMessage would name the fork as its sender and could say what the fork did beyond the outcomes above, but it would wake the main thread for every answer, and add a second report to a resumed run's notification.

In a probe, a fork's SendMessage arrived as an agent message and started a turn on an idle main session 60 ms later. Claude Code offers no third way: a hooks module can start a fork only with $.agent.spawn, whose first run never notifies the main thread, since the module's call to the Agent tool is refused (2.1.322). A resumed run's notification wakes an idle main thread whichever way tells it; in two live runs that woken turn took 23 s and 28 s over 4 and 5 model requests, and checked the forks' answers.

The main thread reaches a fork by its agent id, the one address Leaf gives it: the take's line, the holder in leaf page state and the advice beside a command acting on the fork's thread each name it. A SendMessage to the id reaches the agent in every run, resuming an ended one, and in every generation of the session. A name doesn't: Claude Code gives a name to the newest agent spawned under it, so a second fork for a thread, as after the main thread answered there last, takes the first one's. Once the main thread has sent to a name, its send there after the name moved is refused; where it never sent, a send meant for the older fork reaches the newer one; and after claude --resume the name reaches no agent (2.1.325). So the hooks module spawns each fork without a name. built only with the flag

Follow-ups and flurries

Leaf gives a thread's work to one working fork where it can, so a flurry of messages in one thread usually makes one worker, and a thread never has two. While a fork's turn runs, the thread's further messages go to it, before and after it answers, and once its run has ended, a message the line fork judges take goes to the same fork, resumed. Otherwise a further message goes wherever its thread already is. built only with the flag

  • While a fork's turn runs, the user's further messages in its thread reach it at its next tool boundary, inline, or by pointer when they are too large for the hook, which the fork's own leaf delivery ack records into its turn. That holds after the fork has answered too: its turn holds the thread until another turn takes it, and Leaf keeps nothing back for a second fork in a thread a running fork took, by a pickup or an answer (holding.Holding.took). A message that arrives as the fork's run ends, after its last tool boundary, goes to the main thread once the turn has closed, since keeping back is decided as a message is admitted.
  • A message the line fork judges take, in a thread whose last answer names a fork's turn that has since closed in the session's present generation, goes to that fork again (forks._resumable). Leaf opens a new turn for the fork under its agent id and records its pickup, as a first take does, the hooks module resumes the fork by that id, and the main thread hears which fork has the thread once the module has delivered the fork's message. Leaf's message resuming it (forks.resume_prompt) carries the thread's delivery and tells the fork to read leaf page state before it answers, since its transcript lacks what the rest of the session did on the page meanwhile. The fork can SendMessage the main thread to ask about it.
  • A thread the main thread answered last gets a new fork, once the fork it took the thread from has ended, and so does one whose fork ran in an earlier generation. A thread whose fork Claude Code can't resume goes to the main thread instead: the module ends the turn Leaf opened, which gives the thread back. A message the main thread writes in the thread unasked, such as a correction of the fork's answer, answers nothing, so the thread stays the fork's.
  • Messages in different threads start a fork each, side by side.
  • planned fallback If a fork per thread proves wasteful, one standing fork per session would take every small message in turn: cheaper, but slower when messages in several threads arrive together.

The main thread as coordinator

The main thread stays in charge of the session's work. It hears each fork's agent id as the fork takes a thread, and can steer the fork, or ask it to stop, with SendMessage to that id, or answer the thread itself, which takes the thread from the fork (When the main thread takes a thread over). It takes its to-dos in the order it judges, and runs work bigger than a message in subagents, as the shipped skill's Stay responsive already asks. A fork is to change neither the session's files nor its plan: the line fork gives a fork only work that needs nothing the main thread is changing, and the working fork's task tells it to change nothing the main thread is changing or about to change. Nothing else enforces it.

To-dos

built only with the flag A working fork that finds the work bigger than a message, such as a change to the session's files, branch, page or pull requests, or research long enough to need progress of its own, does what it can without those changes, answers with what it found, and opens a to-do on the thread with leaf thread reply --todo, as the main thread does. Its task (forks.work_prompt) offers that beside HAND BACK:, which it keeps for a message the main thread has to act on now: an answer to a question the main thread asked, steering its current work, or a question it is weighing. The to-do is the session's and stays open after the fork's turn ends, while the fork's start on it stops counting with the turn. The main thread hears that the fork opened it, and an idle session is woken for it (the todo outcome above).

planned A message the line fork sorts as significant becomes a to-do on its thread that the agent owes until it ends it, so the main thread takes it in its own order instead of being interrupted by it. Such a message has no working fork, and who opens its to-do is still to be designed.

Where each rule is written

  • src/leaf/hook_transport.py: carry_agent_turn, a fork's tool boundary.
  • hooks/claude-code.ts: lineFork, workFork and the turn.complete hook, which make the forks and report a working fork's end.
