How Leaf works

An agent builds a page around the work. The user comments, explores, and makes choices. The agent responds by revising the same page.

Leaf supplies the interface and the record of that exchange: comments attached to passages, interactive widgets, decisions, and versions. The agent supplies the content and does the work, using its existing tools in Claude Code, Codex, or Pi.

Pages, core, and packages

A page is the document the user reads and acts on. Its HTML includes widgets such as choices, charts, and boards. A passage identifies the words a comment concerns.

Leaf’s core supplies shared state, events, and page lifecycle. Packages contribute widgets, domain behavior, styling, and authoring instructions. A page selects packages and a theme; Leaf combines those with its core declarations and assets into the page’s layer.

The layer’s registry gives agents, checks, Python, and the browser a shared description of its elements and capabilities. It declares valid markup and the meaning of widget actions; widget modules implement their behavior and presentation.

The exchange

An agent proposes queue policies for an importer. A choice or comment the user sends is an update. A comment opens a thread, the conversation about its passage, widget, or the page as a whole. To make this choice yourself, try the queue policy practice in Workflow.

  1. The agent prepares the page. It writes the alternatives, checks the page, and opens its link.
  2. The user chooses “Pause the producer”. The browser draws that choice immediately. The server validates the action against the registry and appends its meaning to the event log. The server’s next reading supplies the choice’s effect on obligations and work owed.
  3. Leaf delivers the update. The harness brings the choice and its context into the agent’s session. Its workflow tracks delivery and work, distinguishing receipt from the agent explicitly starting it.
  4. The agent incorporates the decision. It revises the proposal to use backpressure and stamps a version that records the choice in the markup. A revision captures authored content; a version names a revision the user can revisit. If the update was a comment, the agent answers in its thread.

An obligation records an input or answer owed and whose turn it is: first the user’s queue-policy choice, then the agent’s incorporation of that choice. A to-do records work the agent owes, such as measuring the importer’s throughput. Obligations and to-dos supply the On Me and On agent lists; threads keep the conversation, and workflows track the handling of updates.

The same link shows the revised proposal. Stable widget ids keep recorded choices attached across edits. When an edit changes what a decision was about, the author explicitly marks it restated and explains why the decision no longer applies. State and records defines these concepts; Revisions explains their continuity.

Author, hand over, and respond

The harness supplies the agent’s tools and runs its turns. This example follows a queue-policy review from the first page to the answer. Command inventory lists the available operations; Harness connections explains delivery and receipt.

Publish a page

The agent reads Leaf’s skill and the reference for each step: page authoring before writing, and its harness contract before handoff. These instructions set goals for the user’s experience and leave wording and presentation to the agent. Agent instructions and notices lists every source of instructions and when the agent reads it.

The agent creates a page directory and writes index.html with ordinary HTML and Leaf elements. Here, ./review names that directory, relative to the commands’ working directory.

leaf page init records the page’s package and theme selection. The Leaf serving the page supplies its runtime and composes the selected packages. The agent authors its content using the HTML and Leaf elements described in Extending.

leaf server start starts the page’s HTTP server and claims the page for the current agent session: that session receives its updates. The command returns a URL with an access key. The agent hands over the URL and ends its turn; the harness integration continues watching. 

leaf page init --package diagram ./review
# Write ./review/index.html with the harness's file tools.
leaf page check ./review --render
leaf page stamp ./review --text "Queue policy ready for review"
leaf thread create ./review --obligation --text "Which queue policy fits the importer?"
leaf server start ./review

This example is a record meant to be revisited, so the agent reviews and stamps it before handoff. A quick page needs only leaf page check. Revisions defines valid saves, stamps and version addresses; Checks before a revision goes live describes validation.

Resume an existing page

To resume an existing page, the agent reads its active HTML and leaf page state ./review, which returns current state as JSON. leaf page claim ./review registers the current session as the recipient of the page's updates without starting its server. Starting the server also makes that claim.

Answer updates

A browser comment or choice sends an HTTP request. Leaf validates it, appends it to the event log, and delivers it to the agent with thread context and instructions assembled from the registry. The harness supplies this JSON batch or an id to open with leaf delivery read.

Choose a policy, then open Show activity below it to see the recorded choice. Open the page’s leaf menu and choose Undo; press Activity changed in the feed to see the choice marked undone. This example uses the page’s activity log and Undo; its queue policy is fictional.

Importer queue policy

The importer receives bursts of records faster than it can process them. Its queue has room for 1,000 records.

When the queue fills, what should happen?

Pause the producer Keep every queued record; wait for space before accepting more. Drop the oldest record Accept the newest record immediately; discard the oldest queued one.

Recorded actions

For a comment requesting a policy change, the agent follows the delivery’s receipt instructions and first posts a progress message naming the work. This also starts the event, so the user sees which update it is handling. It then reads the current page and thread, revises the policy, and replies. This example posts replies through the CLI; harness routes describes when Leaf captures a turn’s messages instead. 

leaf thread reply <answer.ref> --ephemeral --text "Checking the importer's queue policy."
leaf page state ./review
leaf page state ./review <thread-id>
# Revise ./review/index.html.
leaf thread reply <answer.ref> --done --text "The importer policy is updated."
leaf thread create ./review --obligation --text "Does the revised policy match the workload?"

A comment needs a thread reply. A widget that asks, any widget whose registry entry declares x-awaits, creates an obligation on the user’s On Me list, with a prompt, typed answer, and lifecycle; an optional lf-ask supplies its heading as the prompt. The widget owns the value, and the agent records the decision in a stamped revision. The browser fetches the revised HTML and state.

Example: answer a page choice

The page asks which queue policy to use with lf-options id="queue-policy" choose. When the user chooses Drop the oldest record, Leaf delivers that choice to the agent. The agent starts the choice event, reads the current choice, and revises the HTML to show the selected option: 

<lf-options id="queue-policy" choose>
  <lf-option id="drop-oldest" chosen>Drop the oldest record</lf-option>
  <lf-option id="block-producer">Pause the producer</lf-option>
</lf-options>

After checking and reviewing the result, the agent stamps the revision to record the decision. The stamped markup answers the choice event and ends its start: 

leaf task start ./review <event-id> --text "Recording the chosen queue policy"
leaf page state ./review
# Add chosen to the picked option in ./review/index.html; check and review.
leaf page stamp ./review --text "Queue policy: drop the oldest record"
Delivery fields and answer semantics

In a delivery requiring a thread reply, answer.parent is the message it threads under. The event's id identifies the update to start, and answer.responds identifies the update the reply answers. The example batch uses 9d41b20f for all three because the comment opens a new thread. A later message has its own event id within that thread.

A user comment requires a reply in its thread. A decision on a page widget requires a stamped revision. If the obligation's widget declares a record form, the revised HTML uses it to show the decision, such as the chosen option. An obligation embedded in a thread message receives a thread reply, because that message's HTML is fixed. Resolving a thread or moving a card can require no answer; the agent still receives the event. A multi-select obligation submits the choice when the user presses Done.

A delivery is one JSON document, whose format field names its version. Its envelope contains one or more page batches, preserving the captured event order, thread context, and handling instructions. A delivery id supplied by the harness names this whole envelope; an event’s id names one recorded event. Harness connections and receipt describes how to read and confirm a delivery pointer. Data structures lists every field.

Leaf combines the applicable clauses in the batch's handling object. The agent follows those clauses and reads current state before answering: a newer update may already have settled the response the captured batch requested.

Change the live page

The agent can save HTML, replace a widget’s data source, or report a widget state change while the user reads. The browser fetches the revised document and state when the server reports a change (Freshness checks and state reads). 

leaf data set ./review queue-metrics --file ./metrics.json

Here, the declared source queue-metrics receives the complete value in metrics.json. For a widget state change, leaf page report records its declared operation and fields. Saving HTML changes the live document; stamping adds a version address and changelog entry.

These changes preserve the user's recorded choices. If an edit changes what a decision was about, the author marks the widget restated to invalidate that decision. The Revisions view explains how decisions survive page edits.

Threads explains anchors and how they survive revisions, drawings, titles and summaries.

Source errors

A source error can leave the file on disk newer than the live page (Checks before a revision goes live). Read leaf page state alongside the active HTML to check which revision the user sees.

Wait for updates or finish

leaf page open ./review leaves the page available for feedback. Questions that need an answer go in thread messages with --obligation, which puts them in On Me. The harness integration keeps watching after the turn ends and sends later updates back to the same session.

leaf page close ./review marks the page finished and stops watching it. Leaf refuses it while an update awaits receipt or an answer, or an agent to-do is open. If the agent ends a turn with a delivered update unanswered, the Stop hook tells it so (Stop hook checks).

Background work and durable to-dos

Work longer than a few minutes runs in background workers, whose results start another agent turn.

leaf task start names the update or to-do the agent is handling in this turn, and a reply or stamped decision answers the update. Work that outlasts the turn, or that no update asked for, gets a to-do, which stays open across replies, revisions and sessions until the agent ends it. The agent opens it on a thread, a widget that takes to-dos, or the whole page, and starts it with the id leaf task create prints: 

leaf task create ./review page --title "Check the importer policy"
leaf task start ./review <todo-id> --text "Checking the importer under load"
# Run the check and put its result on the page.
leaf task end ./review <todo-id> done --text "The load check is recorded on the page"

A to-do ends as done, failed, or dropped, with a note saying where its result is or why there is none. A stamp with --completes <widget-id> ends every open to-do on that widget as done. Until then the to-do stays on the agent's list, On Claude.

Stop hook checks

When the agent ends a turn, Leaf’s Stop hook checks its pages for unanswered updates and delivery between turns. Claude Code shows a reminder as context, not an error. A new update normally opens a turn of its own after this one ends, preserving this turn’s final message as its answer. Where nothing watches afterward, as with Claude Code’s plain --print or a Codex task waiting with leaf wait, or where the next turn would open on a message in the user’s name, as with Codex’s codex queue, an update needing an answer enters the current turn instead. An update needing no answer waits for the next turn.

  • An update started in this turn lets the turn end. Long work runs in background workers whose results start a later turn, so the Stop hook doesn't hold a turn open for an update the agent started in it. The update reads On it, with the agent's line beside it, until the next turn answers it or starts it again; otherwise it soon reads Gone quiet.
  • Between turns, a page needs a watcher: Claude Code's or Pi's watch hook, a leaf wait, or Codex's adapter. Without one, the user's next update waits in the event log until the agent's next turn, which in Claude Code Leaf starts by messaging the session. A closed page or a developer's preview needs no watcher.

Harness connections and receipt

Claude Code’s background Stop hook watches between turns and wakes the agent; its prompt hook puts the update into the new turn. Codex’s adapter queues the update as the next message, or starts a turn when Leaf is an App Server client. Pi’s experimental extension runs inside Pi. Each route supplies the same delivery format and says who confirms receipt.

  1. Confirm receipt separately from transport. Leaf counts an update as received only when the agent or harness confirms it. A harness discards output from a timed-out hook, so the hook confirms well before its deadline and passes a complete delivery into the turn only after confirmation.
  2. Use a pointer when the whole delivery cannot fit or be confirmed. A delivery too large for the turn’s context, or one the hook could not confirm in time, arrives as an id. leaf delivery read <delivery-id> confirms nothing; the agent follows every next command, then runs leaf delivery ack <delivery-id> as the envelope’s acknowledge field directs.
  3. A direct wait confirms on its next call. A Codex task running its own wait uses leaf delivery ack <delivery-id> && leaf wait. Until then, the events remain available to the next wait, in case output was lost or cut off. The table's last column says what marks an update Delivered on each route.

Claude Code integration

leaf hook handles Claude Code's prompt and Stop hooks, and leaf session-end releases the session's pages. A background Stop hook runs leaf hook --watch and wakes the session when an update arrives.

Leaf reads Claude Code's session registry to tell whether a session is busy, waiting or idle. If nothing is watching the page, Leaf can message the session through its socket, or resume a retired background session with claude --bg --resume. The socket accepting a message doesn't show that the agent read it.

Turn-end check in Claude Code (experimental)

Late in a long session, the page can drift from the conversation: the agent leaves something to the user only in its chat reply, so On Me misses it, or a page goes on saying what the work has since changed. In Claude Code, when the agent finishes a reply in a session holding a page, Leaf's hooks module forks the conversation. The fork is a copy of the conversation that answers one question without calling tools, and the agent never sees the exchange. Leaf sends it the skill's turn-end check with Leaf's rule for what goes On Me, as the agent reads it, and for each page its text as the user reads it, its On Me, the questions On Me no longer holds with their ids, and the items it shows under way. The fork names:

  • each decision, answer, permission or step the agent left to the user that no On Me item holds, such as which of two designs to keep or trying a build
  • what a page still says that the work or the conversation has since changed, such as a result or a section the user dropped in chat
  • an On Me item the user answered elsewhere, or the work made moot
  • work the agent promised or set running, such as a background job, that no page shows

Among asks, the fork leaves out what an On Me item already holds, what the user has answered since, and what the agent will settle itself. For each ask it gives a thread title, a message of a few sentences that the user can answer without the chat, the words of the passage it concerns, if one does, and the id of a question it asks again, if any, such as a step the user took that didn't work. A step the user is to take is asked the same way: the message says what to do, and asks for a reply only for what the user alone can report, such as what a build showed them, or where the agent's next step waits on it, since the reply tells the agent to go on. Leaf skips an ask whose title a question the agent asked already has.

Leaf writes each remaining ask as the agent's message with an obligation. A question asked again goes in its thread under its id, as leaf thread reply --obligation <id> asks it, and reopens the thread if the user closed it. Any other opens a thread of its own, as leaf thread create --obligation does, on that passage, or on the page as a whole where the fork named none or the page doesn't show its words once. Each stays On Me until the user replies or settles it with a reaction, and nothing on the page marks where it came from.

Where a few of a page's words have gone stale, the fork can give the words to put in their place. Leaf makes that change itself where the page shows the old words once: it finds the place in the page's source the user reads them from, swaps in just the words that change, checks that the page then reads as the fork asked, saves it as any save is checked, and tells the agent the old and new words, so the agent can change them back or rewrite them. A fix that needs more than a sentence, or that Leaf can't place, goes to the agent instead.

Only the agent settles an On Me item or adds to its own list, so the other findings reach it as messages. Each gives the fork's summary and the words from the conversation it rests on, which lead the agent to the original message even after a compaction. At its next prompt or tool call, the agent reads these and each record and change Leaf made, and withdraws a question it disagrees with, with leaf task end, as it would its own.

The fork starts after the turn has ended, so neither the turn nor the user's next message waits for it. It reads the conversation from the session's prompt cache and answers in a few seconds. Leaf writes no record and changes no page once another turn has opened, since the fork's reading is then out of date; a finding still reaches the agent, naming the turn it came from. When a fork fails or its answer isn't the JSON Leaf asked for, Leaf writes nothing and records the failure in Claude Code's debug log.

The delivered event batches reference owns the envelope and handling lookup. Conversation loop owns to-dos, starts, statuses, and the response loop.

Shared readings

The browser runtime combines the server’s reading, authored values and pending updates. Shared selectors supply names, statuses and identities to the margin, Page Map, Leaf panel, activity feed and widgets. What a thread shows lists what the conversation selectors say; the runtime owner table identifies each reading’s owner.

A surface chooses placement and presentation, using these shared readings for meaning. It never infers state from another surface's rendered text. Drawn elements carry their identities so a press can find the thread or widget it acts on.

Page files and history

A page directory holds its authored HTML and modules, package and theme selection, revisions, event log, media, and external data. Packages selected by a local path are copied into it; the serving Leaf supplies bundled packages and the runtime. Copying the directory preserves the authored content and recorded decisions. Current state

Leaf appends comments, widget actions, agent replies, reports and version records to the page's events.jsonl. The active revision's HTML supplies each widget's initial values, and each read applies the recorded actions to them. Leaf keys each action by [widget, unit, verb]: the owning widget, the part of its state being changed, and the operation. Undo appends an event naming the action it withdraws, and both records stay in the log. The rules live in the events contract and the package contract's User state, which agents and package authors read. The sections below follow one choice and its undo through this computation.

Replacing and withdrawing actions

  • A later action at the same coordinate supersedes it, as the pick of Later did. Undoing the later action restores the earlier one.
  • The user's undo withdraws one gesture of their own: an action, or a resolve or reopen. Sent messages cannot be withdrawn.
  • The author's restated: a stamped version lists element ids it deliberately rewrote, and every earlier action that depends on one of them is retracted.

Once the agent records a current decision in the markup, such as the added option as an ordinary lf-option with the same id and words, the document carries it and the action no longer changes what the page shows.

Agent-reported state

A verb declared with "writer": "agent" accepts reports from the agent. leaf page report appends a report event, which updates the widget until a stamped version settles the report. The package contract's User state gives the complete rules.

Following new events

leaf page events PAGE --follow prints every stored record, then each new record as Leaf appends it. To resume after the last printed record, pass its seq value to --after.

Typed external data under data/ is replaced in place rather than logged, so the feed does not carry it. The events contract's Following the log gives the feed's whole contract.

Revisions

When Leaf reads changed, valid page source or dependencies, it captures an immutable revision and makes it live. Identical captured inputs reuse a revision. leaf page stamp adds a changelog entry, a version number and a stable address such as /versions/v2.html. The live URL follows revisions; a tab displaying v1 stays on v1.

The Versions list (g V) holds each stamped version. Each version older than the one shown offers Compare, which marks the blocks that changed since it. v, or Show changes under Annotations in the leaf's menu, marks what changed since the version the user last saw, or else the newest older one. A second press of v, or the lit Compare, clears the marks.

An open tab installs a live revision while preserving reading position and active controls, waiting where it would interrupt the user (Live revisions). A comment follows its passage, or its surviving section if the passage disappears. If neither can be identified, the thread detaches rather than choosing unrelated text.

A request to permit an action is an ordinary decision: an lf-options group whose options take the action its heading and prose describe or keep things as they are, so declining is an answer too. Its pick answers the widget's obligation on On Me, and choosing it again reopens it. Each request is independent of other unanswered widgets and page stamps, and the pick persists with the widget's id across unrelated edits. When the action or evidence changes enough to invalidate that permission, the author explains the change and marks the widget restated. A request that depends on another decision is presented after that decision, once the action to permit is concrete.

Decisions across revisions

A pick or drag records a structured action, shown immediately and delivered alongside comments. Once accepted into the log, it survives reloads, other tabs, and later revisions. The event log reference shows how actions and undo determine current state.

An edit preserves recorded choices unless it explicitly changes their basis. The agent marks an affected element restated and explains why in the version note. Otherwise the choice still applies. Wording, labels, placement and vocabulary can change; the log keeps each action's original meaning.

z withdraws the user's latest action, naming that action and how long ago it was made. Where that action is out of view, or the agent has already picked it up, the first press shows it and the second takes it back. Either way it leaves the user at what it took back, so undoing a resolve opens the thread again where they had it open. Progress on an update and the page

Leaf distinguishes progress on one update from the page’s status. A busy agent has not necessarily started every comment. The agent names the update or to-do it is handling and the work it is doing, in one line. That line appears beside the relevant thread or widget and in the panel; replies carry the results.

A session is the agent conversation attached to the page; a turn is one run within it. A watcher receives updates between turns. The illustrative sequence below follows a request to shorten a lede; its times are examples, not delivery guarantees.

  1. 0s observation Queued for Claude The comment appears in its thread immediately, reading Queued for Claude until the agent has it.
  2. 1s observation Delivered The hook puts the comment into the agent’s turn, and Claude Code's transcript then confirms it reached the agent. Until the agent names its work, the panel shows its leaf in the working tone and no words.
  3. 5s intervention On it The agent says what it is doing: Cutting the lede to two sentences. The comment reads On it, and the same sentence becomes the page’s status.
  4. 1m intervention Each new phase gets a new line When the work moves from editing to checking, the agent starts the same update again: checking the page at phone width.
  5. 2m observation Answered The revision goes live, the agent's reply reports it, and the status returns to Ready — select text to comment.

Status readings

The server combines the agent’s latest start or status with observed session, turn, and watcher activity. Browser tabs and leaf page state read that same result. All pages uses each serving page’s published activity summary.

  • The turn. The harness integration records when a turn starts and ends. Leaf treats it as active while its opening, a start, a status declaration, or a reported step is less than 15 minutes old. Claude Code also reports the session's activity directly, including permission dialogs and interrupted turns. An interruption can therefore mark the turn ended as soon as the user presses Escape.
  • The watcher. Claude Code's watch hook, leaf wait, or Codex's adapter registers with Leaf while watching for updates. Leaf treats the agent as available for updates while a watcher runs. A running Claude Code turn can also receive updates through its hooks. With no watcher after a turn ends, Leaf messages a Claude Code session when the next update arrives, so the agent is available too where that message starts a turn: a background job whose worker has retired is resumed with it, and a running session takes it at once where Claude Code's crossSessionInbound setting is accept.
  • The start. A start stops counting as active once it is 15 minutes old, or once the turn that wrote it is seen to end, unless Claude Code reports the session still busy with background work, such as subagents it started.

Leaf shows work as active when a start is still current, when the harness reports a step in an active turn, or when that turn has received input requiring an answer. The freshness rules above determine when a start or turn stops counting as active. Input is stalled if it remains queued for two minutes, or if the turn that received it ends without answering. The status doesn't date the agent's line: its hooks remind it to restate a line that has stood two minutes, and the menu's full status says when the line was written.

The On lists

The panel's On view gathers outstanding work across the page, using the obligations, to-dos and workflows defined under State. A status sentence alone creates no obligation.

List What belongs there
On Me Open obligations: each widget that asks, on the page or in a thread message; each agent message sent with --obligation; and each update the user needs to send again.
On Claude (or the attached agent’s name) Updates still owed a reply or a stamped revision, and open agent to-dos.

On the page, an item On Me is answered only in the widget or thread that asks it, and Leaf adds no control of its own to end one. A widget’s obligation is answered by the actions its x-awaits declaration names, such as a pick, or the Done a multi-select choice offers as its own control. A question in a thread is answered by the user’s reply there or a settling reaction, such as 👍. A thread’s attention identifies which side it awaits, using its updates, questions, and to-dos. The page-wide lists collect that work across threads and widgets. While a thread about a decision awaits the agent, its unanswered update represents the work on the agent’s list; the decision returns to On Me when it needs the user again.

Where the agent's messages appear

The agent writes progress messages, statuses, replies, and version notes. Leaf adds observations about delivery and activity. These commands reach different surfaces; starting work places its line both in the panel and beside the update or to-do.

Written by the agent

  • leaf thread reply <answer.ref> --ephemeral Names the upcoming work in the user’s thread before reads or edits. It sets the page’s status and the comment’s Working label, then folds behind Show 1 progress message when the answer arrives.
  • leaf task start … <id> --text "…" Names the current operation for an update or to-do, such as running the browser suite. Its line remains beside the thread or widget until answered or ended. The panel’s leaf and tab icon take the status’s colour; All pages repeats its line.
  • leaf page open … Leaves feedback open and clears starts while keeping to-dos. It creates no obligation. Questions that need an answer belong in a thread message with --obligation, so On Me opens the conversation.
  • leaf page close … The agent has finished with the page, and the status reads Done with this page (Wait for updates or finish says when Leaf refuses it).
  • leaf thread reply <answer.ref> Answers the user’s comment and clears its label. --done delivers the result; --obligation asks the user back; --todo promises work that stays on On Claude until ended.
  • leaf thread reply <page> <thread> A later message in a thread already answered, such as the result of work the first reply promised.
  • leaf thread reply … --obligation Opens a question on On Me and makes the thread read Your turn. A reply or settling reaction answers it at once, so On Me clears without waiting for the agent. A step the user is to take, such as trying a build, is asked the same way. The agent can end it with leaf task end as answered elsewhere or withdrawn.
  • leaf thread reply … --obligation message:<id> Puts a question the user's reply left standing back on On Me, such as when they asked something back. It keeps its id and words, so a plan step naming it reads open again, and stands on this message.
  • leaf thread create, leaf thread edit, leaf thread resolve A thread the agent opens on a passage, a message it corrects, marked edited, or a thread it closes (✓ Resolved by Claude).
  • leaf page stamp --text "…" Names a version and its note in Versions. The live page updates and the panel says Updated to v4. A tab on an earlier version stays there; its version notice offers Latest.

leaf page report records a widget state change. A widget supplied by an optional package can use these reports to show a background worker's progress.

When the agent says what it is doing

  • When an update arrives. The agent names the requested work before starting it, or answers immediately when no work is needed. Each delivery repeats this instruction beside the applicable events.
  • When the work changes. A new subject or phase—reading, editing, testing, or waiting on a result—gets a new line by starting the item again. Every start names its operation.
  • During long work. Background workers keep the agent free for the user’s next comment. The start names the running work beside its update; the agent renews it when a worker reports (Stop hook checks).
  • When it is the user’s turn. A waiting status names the answer or decision wanted.

Finding a passage

In the browser, a passage is an ordered list of segments, each {node, start, end}: a text node and a range of characters in it. A selection that crosses a bold word, a link, or two paragraphs is several segments. Text nodes exist only while the page is loaded, so the log stores the passage by its words instead, as the anchor table shows.

Each time the page is drawn, Leaf searches the anchor's section for the quote. If exactly one occurrence has the stored prefix and suffix around it, that occurrence is the passage. If none has them but the quote occurs only once, that one is the passage. In every other case the anchor finds nothing. Leaf never takes the first of two identical passages, because a comment made on the second would then appear on words it was never made on.

Leaf reads a page's text in two ways. says is the text the rendered page shows, including words a widget draws and declares as part of the page, such as a tab's label. wrote is only the text the author put in the HTML. Anchors and quotes use says, because the user selects what they see. Comparing two versions uses wrote, so words a widget draws do not appear as edits.

The browser makes an anchor from a selection. leaf thread create makes one in Python, from the HTML file. Both apply the same rules: the same whitespace characters collapse to one space, the same elements count as separate blocks, the context is the same 24 characters, and the search is the same.

The file holds the author's HTML, not the words a widget's script draws between its parts, such as a board column's heading or a diagram drawn from its source. A quote may not cross such words on either side. leaf thread create refuses a quote that crosses them, that occurs more than once in the section, or that sits in content the user's decision removed, and says what to quote instead. An agent's anchor is therefore one the user's page can find.

Anchors across revisions

Before publishing a new revision, Leaf checks each open thread's quoted passage against the revised content. The results are shown below.

When the quoted words change but their element survives, Leaf moves the thread to the element its anchor names in section and records the move in the log as a reanchor event, without adding a message. Clicking the quote scrolls to the element. The same happens when a revision repeats the words without context that tells the copies apart.

When the element is gone too, Leaf refuses the revision and names the thread. The agent keeps the element, moves the thread with a reply that names a new passage, or detaches it with a reply passing --detach, which says the subject has left the page. Leaf refuses a revision that removes the element an open element-anchored thread is on in the same way. Only the agent chooses a new passage for a thread, in a reply that says why; Leaf's own move goes only to the element the anchor already named.

A detached thread stays open in Threads, and its first comment keeps its original anchor in the log. Its quote is greyed out and cannot be followed; hovering it shows “This passage is no longer in the version shown”. Threads' No longer here filter lists detached threads. A later reply can move one to a replacement passage.

Anchors are found in whichever version the user is viewing. Opening an older version from the version menu shows threads on passages that version lacks as “This passage can't be identified in the version shown”, also listed under No longer here.

Drawings

In Draw mode, which w turns on and off, the user draws freehand on the page and writes a comment beside the ink. The drawing is anchored on the element under the start of its first stroke, or the nearest one. The comment stores up to 32 strokes as positions within that element's box, the box's size, the words the ink covers, and the window size and colour scheme it was drawn in.

The page draws the ink at the element's current size, so it stays on the element in a narrower window, though text that reflows inside the element can move out from under it. The agent reads the covered words in the comment, and leaf page picture renders that revision again in the same window with the ink over it.

Widgets in messages

An agent's reply can carry a small widget, typically a question with options (--markup on leaf thread reply). Leaf validates the markup when it is posted and stores it in the log with the reply, so the thread shows the same widget in every version of the page. A later leaf page init refuses a vocabulary that could no longer render it.

A widget on the page takes its state from the version being viewed: that version's markup plus the actions taken up to it, minus any a stamped version marked restated. A widget in a message belongs to no version. Its state is its markup plus every action taken on it, whichever version is open, and no revision can retract one. Choosing the answer to its question hands the thread back to the agent.

Titles

A title names a thread in Threads, in a few words of plain text. The agent sets one with --title on the command that first handles the thread, and can rename it later with leaf thread edit --title.

The agent's reply can take minutes, so when the user opens an untitled thread, Leaf also asks the harness's model for a title at once, in a separate request: in Claude Code, Leaf's plugin asks Haiku from inside the session, on the session's own login; in Codex, an App Server request; in Pi, a print-mode run of the model the user configured. The request holds only the thread's passage and first message, nothing from the agent's conversation, and runs in parallel with the agent's work. Leaf uses the first title it receives. While the agent is working on an untitled thread, the panel shows animated dots in place of the title; a thread nobody named shows its opening words.

Summaries

leaf thread summarize folds a run of consecutive messages in one thread under a disclosure labelled “Earlier discussion” or a label the agent chooses, with a summary of their decisions, reasoning, and open questions. The original messages stay in the log and unfold from the disclosure. A summary answers nothing and closes nothing.

Once a thread is long, Leaf suggests a range to the agent with the user's next message, leaving the newest exchange outside it; the agent decides whether to summarize. Editing a message inside a written summary's range removes the summary, so an outdated summary cannot hide the correction. Progress messages an agent posts while working fold on their own behind “Show N progress messages” when its next ordinary reply arrives.

Panels and Escape

Escape's next step depends on focus

Touch coverage and testing

On a phone or touch screen, Leaf's commands have gestures or visible controls in place of keys, which Using describes. These notes say where touch works differently, what a page's author still has to check, and how far Leaf's touch testing reaches.

Browser runtime

The browser runtime upgrades Leaf elements, draws threads and shared controls, sends updates, and keeps the page current. Its inputs meet in one read-only state.

The server supplies actions in effect for the displayed revision, threads, obligations and activity (Current state). The browser applies them to authored values and adds only what pending gestures decide by themselves.

Startup prepares a stable page before enabling its controls. Page loading distinguishes usable controls from the arrival of saved state.

Live revisions

A revision’s executable identity is its registry, loaded JavaScript modules and inline module scripts. Each install pairs the revision with its corresponding state.

What both paths preserve

Replaced elements with matching authored ids inherit local values differing from authored defaults: typed values, checked state, disclosures, inner scroll, focus and caret. Replacements without matching ids do not preserve those values. Reading position follows a passage, not a pixel offset. Fresh documents use a one-time tab handoff that later reloads and Back do not replay; drafts and control arrangements use separate browser stores.

Installation waits during comment or reply writing, passage selection, card dragging, a pending update’s server response, or an open version menu. Latest in the version notice installs the waiting revision immediately.

Server lifetime

The HTTP server exposes the page directory to browsers. A session-started server stops when no live session claims the page; a claim names the recipient of its updates. A server started from a bare shell or with --lifetime persistent runs until leaf server stop.

On leaf.page, a private browser session gets a hosted agent environment using the same page and event machinery (How leaf.page works).

Page addresses

A page's server binds the address its session arrived through: the SSH destination for an SSH session, otherwise loopback. The page keeps its host and port in service.json, so serving it again, changing its packages or reviving it keeps the same URL, and a watcher restarts a server whose process dies at that URL.

Each harness's contract says how its agent serves a page and hands over the URL. When the user can't reach it, the serving reference has the agent serve it on a hostname the user's browser can reach, or hand over an exported file. Leaf uses existing networks and opens no public tunnel. Another session takes a page over with leaf page claim, which moves its updates to that session without restarting the server.

Who can open a page

A page's URL carries an access key, which the browser keeps in a cookie. One key covers every Leaf page on the machine that serves it, so anyone with one page's URL and a network route to that machine can read and act on all of them. A page served on loopback opens only on that machine; one served on an SSH destination or another hostname opens from that network.

On leaf.page, each browser works on a private copy of a page. Its comments, choices and the hosted agent's revisions are visible to no other browser (The leaf.page website).

Offline exports

leaf page export PAGE -o FILE captures a stamped version, its resources and the decisions recorded on its widgets in one HTML file. The file holds none of the conversation with the agent, on screen or in its source: no threads or their attachments, to-dos, plan or changelogs. Reading controls and page-owned code work offline; new Leaf choices, comments and Undo need the served page. An agent need not be running to record a choice on a live server. Pages containing live samples cannot export.
