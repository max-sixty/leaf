How leaf works

Leaf serves an authored page alongside an append-only event log. The browser combines them to show the current document, reader choices, and conversations. The agent receives feedback through its host's delivery loop and updates the page with ordinary file writes.

The loop

sequenceDiagram
  participant Agent as agent session
  participant Leaf as leaf server
  participant Browser as your browser
  Agent->>Leaf: authored files · commands
  Leaf->>Browser: page + current state
  Browser->>Leaf: comments · drags · picks
  Leaf->>Agent: leaf wait carries the event batch

One turn, from the agent's side

The output below is a real page's delivery cycle, on a version asking which of two ways to shed load when a queue backs up: 

$ leaf page init ./review
initialized /home/you/review

# the agent writes ./review/index.html — an ordinary file write

$ leaf version check ./review
✓ index.html: parses, widgets, authored modules, and theme validate, protected ids and decisions carried over, nothing overflows the 720px column

$ leaf version stamp ./review --text "Two ways to shed load — which?"
stamped v1 — Two ways to shed load — which?

The batch carries a pick and a comment. The pick survives later revisions; the comment names the selected passage, so the agent receives the objection with its context. Each event's handling gives the instructions for that kind of feedback. The agent replies in the comment's thread and revises index.html when the feedback calls for it. A valid save goes live, and a meaningful checkpoint can then be stamped as v2.

Feedback returns to the agent task that owns the page. Claude Code receives it through leaf wait; Codex uses a detached adapter. Both carry the same immutable delivery, with the events and their handling instructions. The host integration owns delivery and acknowledgement, so opening a browser page does not itself prove that an agent received its comments.

The wait owner acknowledges a complete batch after its next consumer has received it: model context in a direct loop, or the receiving host when an adapter forwards the batch. Until acknowledgement, waits repeat the events. A truncated batch must be retrieved again in full before acknowledgement.

The page directory keeps the document and its history between sessions. A session-lifetime server retires when no live session claims the page. A server started from the user's shell, or with --standing, remains available until leaf server stop. The banner and tab icon show whether an agent is working, waiting for the reader, or absent.

A command never edits the document

The agent writes the document to index.html. Replies, comments, and version notes go through the leaf command, which appends them to the event log. Browser gestures enter through the same validation and append boundary, giving every event a stable identity and order.

The browser combines the active revision with the log and updates when the server announces a change. Replies appear in the thread panel, their passages are highlighted, and the banner reflects the agent's activity. Reader choices appear immediately and remain effective across later revisions.

The thread panel groups messages behind conversation titles. Opening another conversation preserves the unfinished draft; links to messages and search results open the conversation they name. The shortcut bar shows the commands available in the current context.

Each changed, valid save becomes an immutable revision, including the document and its local dependencies. An invalid save leaves the last valid revision live and shows its diagnostic. version stamp checks the current source and records a public version pointing to its revision, served at an address such as /versions/v2.html. The live address follows revisions; a tab pinned to v1 stays there. Live updates wait while the reader is composing or dragging, and preserve their reading position.

What a page is made of

An authored HTML document supplies the page's title, description, and content. Leaf adds the security policy, identity, theme, runtime, and canonical address when serving it. Authors start with the existing vocabulary and add local presentation where the page needs it.

  1. Plain semantic HTML. The theme styles bare elements, so headings, prose, tables, code, and details carry the page's voice unclassed. Most of any page is this.
  2. Class idioms. A small closed set the theme defines for shapes HTML has no element for, among them .eyebrow, .lede, .tag, .callout, .facts, aside.sidenote for a note in the page's margin, and ol.steps, which numbers this list.
  3. lf-* widgets. Custom elements that say what things are: <lf-options> for a question the reader answers, <lf-board> for work in columns. Attributes carry scalars, children carry prose, a leading <strong> is an item's title, and a JSON-Schema registry keeps the renderer, the linter, and the agent's documentation agreeing about the vocabulary.
  4. Bespoke presentation. A page-local <style> and hand-drawn inline SVG, both riding the theme's tokens. This is the last escape hatch for presentation only one page needs, never a second palette. The architecture diagram above does not need it: <lf-diagram> comes from the optional diagram package.

The theme styles authored HTML and Leaf elements. Interactive elements load their declared behavior modules when the page uses them. Page-specific behavior can use inline module scripts or local modules under page/; reusable behavior belongs in a package. The page-authoring reference defines the module and dependency rules.

A page seeking approval declares <meta name="lf-review" content="sign-off">. That declaration enables the banner's "✓ Looks good" control and versions with the document.

This page is running the plugin's own theme.css and widget modules. Each example sits in a lf-specimen — the gutter that marks quoted material — so an example decision never reads as one the page is asking you to make.

The committed catalog runs wider: mermaid diagrams, unified diffs with per-file collapse, annotated code walkthroughs, file trees, timelines, metric rows, plans with milestones, and dense command surfaces. The examples gallery opens each complete page in its own browser view.

Reader choices survive revisions

Dragging a card or choosing an option records a structured action. The browser applies it immediately, and the agent receives it alongside comments. The log preserves the choice across reloads and later revisions; other tabs follow the same state.

z withdraws the reader's last undoable gesture; pressing it again steps further back. The log records the withdrawal, and the browser redraws the state with that gesture excluded. Reloading the page gives the same result.

A reaction attaches brief feedback to a passage or agent reply without opening a thread. The default tokens ask the agent to keep, change, clarify, shorten, support, or prioritize something. The reaction appears beside its target and can be removed there. Packages declare the available tokens and their meaning.

To override a reader's choice, the agent marks the rewritten element restated and explains the change in the version note. Without that declaration, the recorded choice still applies; a conflicting revision is refused.

Each page owns its layer

page init composes the kernel and selected packages into a checked layer in the page directory. Revisions capture the layer they use, so changing the installed defaults cannot change a version already approved. The package contract owns composition order and replacement rules.

The kernel owns the shared runtime, chrome, and collaboration protocol. Packages supply reusable elements, modules, styles, and guidance. The default package provides common shapes; optional packages add capabilities such as diagrams and diffs. Project packages use the same format and can replace or extend the selected layer. The extension guide lists the bundled packages and builds a small package.

Validation before publication

Before activating a revision or stamping a version, Leaf checks the source's structure, vocabulary, dependencies, and standing reader decisions. An invalid source leaves the last valid revision available. For a finished record, version check --render also checks the page in Chrome in both color schemes, catching failures such as console errors, invisible widgets, and horizontal overflow.

Served where you are

Leaf uses the session's SSH destination as its default serving address, or loopback for a local session. A loopback URL opens only on the serving machine. The URL carries a machine-wide access key, which the browser stores in a cookie. Sharing that key grants access to every Leaf page on the machine.

When the default address is unreachable, the agent can re-serve the page with server start --host NAME on a hostname the reader can reach. Leaf uses the machine's existing networks and creates no public tunnel. The serving reference covers addresses, authentication, and server lifetimes.
