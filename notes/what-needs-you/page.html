What needs you: tasks

Each side has a queue: what waits on you, and what the agent owes you. Either side can put items on the other's. A task is the record of work the agent owes, open until the agent ends it, so a reply, a Resolve or the end of a session can no longer settle work nobody did. This page tracks the plan, how the model works so far, and what is still open.

The code for queues and tasks is marked experimental, so later agents change it freely. Steps 5 to 7 haven't started.

This is the model as built through step 4. An item says whose queue it is on, who put it there, what it is about (a thread, an Ask, a widget or the page) and whether it is open. a pages through yours.

A task is work the agent owes, open until the agent ends it

leaf task end PAGE TASK done "Version 4"
Field Holds Example

The agent opens a task for work that outlasts its turn, such as a build, a CI wait or a change promised for the next version, and for work no message of yours asked for, such as revising the page on its own initiative. Work that finishes inside the turn needs no task: Working names your move directly (below).

The append door holds the rules. Only the agent opens or ends a task. It ends once, with task end or a version stamped --completes on its widget; a reply, a Resolve, another version and the end of the session all leave it open. While it is open, its thread reads waiting on the agent, it counts on the agent's queue, and the banner names it. leaf status idle is refused while any task is open.

Working always names an item on the agent's queue

leaf task start PAGE ITEM "line" writes a start event naming the item in hand, either a move of yours it owes an answer to or a task it opened, with the line the banner shows. So the banner's Working line always points at something you can open.

Case The item Working names
You comment or reply in a thread Your message, by its id
You press an option, or move a card Your press. A start on a widget task also covers your earlier moves on that widget.
Work that outlasts the turn: a subagent, CI, a dispatched session The task the agent opens for it
One turn answers five threads Each of the five in turn; the banner shows the latest start
You asked in the terminal, not on the page (“build step 3”) A task the agent opens on the page
The agent's own initiative: writing the page, revising a section A task the agent opens, on the page or the widget
Housekeeping: re-vendoring, restarting the server, merging main None. It owes you nothing, so it isn't Working
Waiting for your answer None: status waiting puts down what was started, and the item is on your queue

A start lasts until its item ends: the reply or stamped version that answers your move, or the task's end. It holds the item only for the turn that wrote it. If the turn ends with the item still running, the item reads stalled; a later start takes it in hand again. status waiting and status idle put down every earlier start, leaving tasks open with nothing running on them. The put-down is a put_down event in the log, so every reader, including the check that decides whether your next move wakes the agent, agrees on what is in hand.

How they meet:

  • A task and the message it came from. Your message opens an owed reply. The agent's reply settles it, and a task it opens carries the work on. Nothing records that the task answers that message, beyond both standing on one thread.
  • A task inside an Ask. “Show me a sketch first” in an Ask's thread opens an owed reply, and the agent may open a task there. The Ask still counts as yours, though you are waiting on the sketch.
  • An Ask answered in prose. Your message opens an owed reply, and the Ask stays on you until the agent writes your pick into the page.
  • Resolve. It settles the owed replies in the thread and leaves a task open.

The records pair up by who owes them, which is why question and answer read as mismatched kinds. An Ask and a task are both structured work with an end; a prose question and an owed reply are both a message one side owes the other. Only the owed reply has stages, and they track how far your message has reached the agent, from sent to replying, not the work it asked for.

Hierarchy, and who says a task is done

Two questions about the shape of a task: whether one task can belong to another, and who decides that a task is finished. Both are in TODO.md to think about, and both shape steps 6 and 7.

Can one task belong to another?

Today, no. A Leaf task has exactly one link: its subject, the thread, widget or page it is about. Nothing points from one task to another, or from a task to the message that asked for it. Step 4 keeps that.

Pi's tasks form a tree. A task that spawns subtasks owns them, and it can wait on them until they finish. Leaf has no equivalent yet.

Two Leaf cases could want a link like that:

  • Work that answers your message. Say you comment "make the table wider". Step 4 needs no task for this: Working names your comment itself, so the thread reads Working until the agent's reply settles it. Only work that outlasts the turn, such as a CI run or a build, gets a task, and that task names the thread your comment is in rather than the comment. That is enough to show the work beside the right thread. It can't say which of several comments in one thread the work answers; if that ever matters, the fix is one field naming the comment, not a tree.
  • Work handed to another session. Say the agent here dispatches a separate session to fix a bug, as this session has done several times this week. The work now belongs to a session this page knows nothing about, so the page can't show it as under way or learn when it ends. Fixing that needs the dispatched session's task to point back at the task that dispatched it, which is a parent link. That belongs in step 7, Items outlive their session, which already deals with work that moves between sessions: it is also where a task whose session ended without an outcome lands on your queue.

Why not a general tree now: a tree brings rules nothing here needs yet. Does a parent end when its children do? Whose queue shows a child? Can a child outlive its parent? The two cases above need at most one link each, so the tree can wait until a case needs more.

Who decides a task is done?

Today, the agent alone. It ends a task with leaf task end as done, failed or dropped, with a note saying where the result is or why there is none. A version stamped with --completes also ends the task on that widget as done. You have no step in it.

Proposed: it depends on whether the result can be checked.

  • A result the agent can check, such as a TODO written, a test passing, a file moved or a PR merged. The agent ends the task as done and its note cites the evidence. Nothing goes on your queue, because there is nothing for you to judge.
  • A result only you can judge, such as a design, a rewrite or a choice of wording. The agent finishes its part and the task moves onto your queue to review, for example "Rewrote § Pi comparison". a reaches it with everything else on you. Reading it and moving on accepts it, which ends the task. Replying sends it back to the agent's queue, with your reply as the next thing to answer.

Moving a task from the agent's queue to yours is step 6, Either side adds to the other's queue. The agent decides which case a task is, guided by its instructions, the same way it already decides whether to ask you with an Ask or in a thread.

The agent picks the banner line

Today the banner shows the line of the latest start. Later, the line is a field the agent sees and sets: Leaf fills it from the item in hand when the agent is answering something quickly, and the agent can replace it, for example with one line covering five threads it is answering at once.

Which kinds of item exist

Left open on purpose. The queues collect whatever is open and owed today, under a kind that says only where each item came from. Which kinds deserve their own rules gets decided once we've used the queues; step 5 is where Asks and tasks would share one shape.

How Pi Durable models the same ground

The two work at different levels. In Pi, every model turn, tool call and tool result is a message in the user–assistant conversation, and each is a task. In Leaf, a message is your comment or the agent's reply, and one reply is the outcome of a whole run of those: dozens of model and tool steps work towards answering you.

Pi Durable Leaf
A message Every model turn, tool call and tool result Your comment, or the agent's reply to it
A task One step: a model request, a tool call, a compaction, a subagent One thing owed between you and the agent: an answer to your comment, a rebuild, a review
How long it runs Usually seconds; a subagent or reminder longer A turn, or hours to days across sessions
What the record is for Resuming exactly where a crash left off Knowing what is owed, by whom, and whether it was done

So a Leaf item is not one of Pi's tasks but one high in the tree: in Pi's terms, a task the conversation owns, whose children are the steps that work towards it. Leaf sees those steps only as the banner's Working line.

At its own level, Pi Durable works like this:

  • A message is input, not a task. Sent while the agent is busy, it either steers (“joins the running work after the current tool calls”) or queues as a follow-up. A requestId makes the submission exactly-once. Nothing like “picked up” is recorded on it.
  • Work is tasks, and a task's stages are its own. A task type declares named phases, and its state holds a checkpoint naming the current one. Its status is running, waiting on named tasks, or terminal with an outcome (completed, failed or aborted). Code registers one with tx.createTask(Type, input, {ownership}), owned by a task or a conversation.
  • Asking you is not a record. An approval hook asks, and stores your answer with api.memo(), so that “after a restart, the hook finds the stored answer instead of asking again”. The question is the agent's running work, paused on you.

Your model fits Pi's. A Pi task has an owner and waits on whatever it needs, so an Ask is the agent's task waiting on you, and your queue is every task waiting on you. Pi differs in two places, neither a conflict. A message is input that starts or steers the agent's work rather than an item of its own, so putting an item on the agent's queue is your message creating work there. And Pi records nothing about delivery, so Leaf's stages from sent to replying belong to the message, not to the task.

How Working became a task

Before step 4, leaf status working --on SUBJECT "…" wrote a claim into the page's status file, outside the log, while a task was a separate record in the log. Both said the agent had taken the subject on. Pi Durable splits that fact by lifetime rather than by record: a foreground task belongs to the current turn, and a background task outlives it.

The first proposal made each claim a task that lasted the turn. What was built goes one step further: your moves are already items on the agent's queue, so a start names your move directly, and only work the agent takes on itself needs a task. The claims left the status file for the log, every reader of claims (workflows, the activity fold, the Stop hook, the banner, the margin and Page Map labels, neighbour rows, the stamp guards) now reads starts, and the instructions tell the agent to start an item.

Decided: leaf status working --on folds into the task commands, so one command takes work on, and status keeps only waiting and idle.
