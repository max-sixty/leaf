How leaf works

A leaf is a page an agent hands you, and the loop that carries what you do on it back to the agent.

Your feedback goes back to the agent

Leaf serves the agent's page beside an append-only event log, and your browser combines the two into the current document, your choices, and every thread. What you do there goes back to the agent session that owns the page. 

sequenceDiagram
  participant Agent as agent session
  participant Leaf as leaf server
  participant Browser as your browser

  Leaf->>Browser: page + current state

  Leaf->>Agent: the host's carrier brings the event batch

What you see after you send

Select a passage and comment on it, pick an option, or drag a card. The page shows your move at once, and a label beside it follows the agent's side: Sent once the server has it, Picked up once the agent's turn has taken it, and Working once the agent names the work your move asks for. The label clears when a reply or revision answers the move. A move still at Sent after two minutes reads Waiting for pickup, because nothing has taken it. Updates lists every label.

The batch carries a pick and a comment. The comment names the passage it was left on, so the agent receives the objection with its context, and each event's handling says what that kind of feedback asks for. Each host delivers the same envelope

In Claude Code, a background leaf wait ends when feedback arrives, and Leaf's prompt hook puts it in the turn that starts when the wait ends; feedback that arrives as a turn ends goes into that turn through the Stop hook. In Codex a detached adapter queues it as the task's next message, or, where Leaf is a client of the task's Codex App Server, starts a turn with it. Every route carries a delivery of the same shape, which names the route and says who acknowledges it. The host owns delivery, so an open page does not prove that an agent received your comments.

Leaf tracks each move's receipt, work, and response separately:

  • Receipt: which input reached the agent. Claude Code's hooks confirm the whole envelope as they put it into the turn; one too large for the turn's context goes in as a pointer, and the agent confirms it with leaf wait --ack <delivery-id> once it has read it. A Codex task running its own wait gets the envelope printed and confirms it the same way; printed output can be lost or cut off, so unconfirmed events stay available to the next wait. The Codex adapter acknowledges what it carries, and the agent follows the adapter's route rather than starting a competing wait.
  • Work: what the agent is doing. A move that asks for an answer, delivered into the agent's running turn, makes the banner read Claude working — on your update until the agent says what it is doing. leaf status names the operation, and its --on names the thread or widget being worked on, which makes that move's label read Working.
  • Response: what settled the move: a reply in its thread or a revision. Receipt and work leave it open. Once it is answered, the agent names your next move with a waiting status.

A command never edits the document

The agent writes the document to index.html. Replies, comments, and version notes go through the leaf command, which appends them to the event log. Browser gestures enter through the same validation and append boundary, giving every event a stable identity and order.

The browser redraws when the server announces a change: replies appear in the thread panel beside their passages, and the banner and tab icon say whether an agent is working, waiting for you, or absent.

The agent says what it is doing before it does it

While an agent works on a page, it keeps a status: one sentence naming the operation and its subject, written before the step starts, so what you read is what is happening now. The status stands in the banner at the top of the page and beside the thread or widget the work is about, and replies in the thread carry the rest.

Sent You comment on the lede. The page shows your comment at once, marked Sent. Picked up Leaf hands your comment to the agent's turn and confirms it. Your comment reads Picked up, and until the agent writes its own words the banner reads Claude working — on your update. The work is named Before doing the work, the agent writes leaf status … working "cutting the lede to two sentences" --on <thread>, which puts that line beside the thread and in the banner, and your comment reads Working. Each new phase gets a new line When the work moves from editing to checking, the agent writes the status again: Claude working — checking the page at phone width. Answered The revision goes live, the agent's reply reports it, and a waiting status names what the agent wants back: Claude awaits — does the shorter lede keep enough?

Every update, and where you read it

Some updates the agent writes with a command. The rest Leaf writes itself, from what it can observe: how far your input has got, and whether the agent's turn and watcher are still running. A status and the agent's turn each show in two places; the dotted line is a status written with --on.

Written by the agent

  • leaf status … working "…" What it is doing, in the banner: Claude working — running the browser suite. With --on, the same line stands beside that thread or widget until the agent answers there. The tab icon takes the banner's colour, and the page's row in the Leaves drawer repeats the line.
  • leaf status … waiting "…" What it wants from you, as in Claude awaits — pick one of the two layouts, shown while a watcher runs or the agent's turn does. With no sentence the banner invites a comment: Claude awaits — select text to comment.
  • leaf status … idle The agent has finished with the page, and the banner reads Leaf closed. Leaf refuses it while input of yours has not been picked up or a picked-up move still has no answer.
  • leaf thread reply --for … An answer in your thread, which clears the label beside your comment.
  • leaf thread reply … <thread> A later message in a thread already answered, such as the result of work the first reply promised.
  • leaf thread reply … --awaits A question for you. The thread reads On you to answer, and the question joins the Asks drawer.
  • leaf thread open, leaf thread edit, leaf thread resolve A thread the agent opens on a passage, a message it corrects, marked edited, or a thread it closes (✓ Resolved by Claude).
  • leaf page stamp --text "…" A revision. The page updates in place, the status line says Updated to v4, and the text joins the versions menu as that revision's note. While you read an earlier revision, a chip offers the new one: New page available → open v4.

leaf page report lets optional packages' widgets show a worker's progress.

Written by Leaf beside your input

Beside each comment, pick, or drag, a label follows your input through the agent's turn. The label clears once a reply or revision answers it.

Sent The server has your input.
Queued The agent's host queued it for the agent's next turn.
Picked up The agent's turn has taken it.
Working A status written with --on names this input's thread or widget.
Replying The answer is streaming into the thread.
Waiting for pickup Two minutes after sending, nothing has taken it.

A label the agent's host does not report never appears. Queued comes from Codex's own queue. Replying, Interrupted, and Codex's step readings need Leaf connected to the task's Codex App Server, and Not answered needs a host that records its failures, as the leaf.page website's does. Claude Code tells Leaf when a turn ended and when it waits on a dialog.

When the agent writes one

  • When your input arrives. Your comment comes before the work in hand: the agent names the work it asks for before starting it, or answers at once when it asks for none. Each delivery repeats these steps to the agent beside the events they apply to.
  • When the work changes. A new subject, or a new phase such as reading, editing, testing, or waiting on a result, gets a new line. leaf status refuses working with no sentence, since the banner already says that the agent is working.
  • During long work. Work longer than a few minutes goes to background workers, so the agent stays free to answer your next comment. Its status names what is still running, and it writes it again when a worker reports.
  • When it is your move. A waiting status names the answer or decision the agent wants, rather than saying that it is waiting.

The conversation loop reference is the agent's copy of these rules.

How Leaf decides what the banner says

The banner states only what Leaf can observe about the agent's session, the agent process that holds the page: whether it still runs, whether its turn is running, whether a watcher runs between its turns, and the last status it wrote. The server decides the reading, so every open page, the Leaves drawer, and the agent's own leaf page state show the same one.

  • The turn. Leaf's hooks and carriers stamp a turn as it opens and closes. An open turn is believed while something in it renewed it within a quarter of an hour: its opening, a status, or a step the host reports. Claude Code also publishes each session's state, which tells Leaf when a turn waits on a dialog such as a permission prompt, and when a turn ended without a hook, so an interrupted turn reads as ended the moment you press Escape.
  • The watcher. A leaf wait, or Codex's adapter, holds a lease while it runs. Leaf counts the agent as taking input while a watcher runs or while a Claude Code turn runs, since that turn's hooks take new input too.
  • The status. A working status, and each --on line, is believed until it goes a quarter of an hour without renewal or two minutes pass after the turn that wrote it ends, whichever comes first. The two minutes let an agent woken again straight away renew it before the page reports it gone.

Work is believed when a working status or --on line is still inside the rule above, when the host reports a step for the running turn, or when a move that asks for an answer was delivered into the running turn. Input has stalled when it stayed Sent for two minutes, or when the turn that picked it up ended without answering it. Once a working reading is about a minute old, the banner shows its age, as in Claude working · 5m ago — running the browser suite.

What the status line announces

News that arrives without you doing anything shows for a few seconds in the status line at the bottom of the page, and a screen reader hears the same words. News arriving together shares one notice, as in Claude replied; Input needed. What was already there when you opened the page isn't announced, except messages you haven't read.

Notice When
Claude replied, Claude commented, Claude updated a reply, 3 replies in 2 threads An agent message you haven't read arrives, or one is edited.
Input needed, 2 items need your input Something new waits on you: an Ask on the page or in a thread, or a thread whose latest reply asks you something.
Response failed, Response interrupted The agent's host reports that an answer to you failed or stopped.

Updated to v4 A new revision replaces the page in place.

Every valid save is a revision

Each changed, valid save of index.html becomes an immutable revision, including the document and its local dependencies, and goes live at once. leaf page stamp marks a revision as a public version, served at an address such as /versions/v2.html: the live address follows revisions, and a tab pinned to v1 stays there.

A live update waits while you are composing, dragging, or undoing, have a gesture still on its way to the server, or have the version menu open, and it keeps your reading position.

A page that asks for approval declares <meta name="lf-review" content="sign-off">. A stamped version that declares it offers the banner's approval control, enabled once you have answered every Ask, the questions the page puts to you.

Checked before it goes live

Before activating a revision or stamping a version, Leaf checks the source's structure, vocabulary, dependencies, and your standing decisions. An invalid save leaves the last valid revision live and shows its diagnostic. For a finished record, leaf page check --render also opens the page in Chrome in both color schemes, catching console errors, invisible widgets, and horizontal overflow.

Your choices survive revisions

Dragging a card or choosing an option records a structured action. The browser applies it immediately, the agent receives it alongside comments, and the log keeps it across reloads, other tabs, and later revisions. The event log reference shows the records a pick and its undo write, and how they fold into state.

To override a choice, the agent marks the rewritten element restated and explains the change in the version note. Without that declaration the recorded choice still applies, and a revision that contradicts it is refused.

z withdraws your last undoable gesture; pressing it again steps further back. The log records the withdrawal, and the browser redraws the state without that gesture, so a reload gives the same result.

A reaction attaches brief feedback to a passage or agent reply without opening a thread. The default tokens ask the agent to keep, change, clarify, shorten, support, or prioritize something; packages can declare others.

What a page is made of

An authored HTML document supplies the page's title, description, and content. Leaf adds the security policy, identity, theme, runtime, and canonical address when serving it. Authors reach for four things, in this order:

  1. Plain semantic HTML. The theme styles bare elements, so headings, prose, tables, code, and details carry the page's voice unclassed. Most of any page is this.
  2. Class idioms. A small closed set the theme defines for shapes HTML has no element for, among them .eyebrow, .lede, .callout, aside.sidenote for a note in the page's margin, and ol.steps, which numbers this list.
  3. lf-* widgets. Custom elements that say what things are: <lf-options> for a question the user answers, <lf-board> for work in columns. A JSON-Schema registry keeps the renderer, the linter, and the agent's documentation agreeing about the vocabulary.
  4. Bespoke presentation. A page-local <style> and hand-drawn inline SVG, both using the theme's tokens: the last escape hatch for presentation only one page needs, never a second palette. The drawings on the Layout tab are this.

Interactive elements load their declared behavior modules when the page uses them. Page-specific behavior can use inline module scripts or local modules under page/; reusable behavior belongs in a package. The page-authoring reference defines the module and dependency rules.

Widgets you can operate

This page runs the plugin's own theme and widget modules. Each example sits in an lf-sample, the gutter that marks quoted material, so an example decision never reads as one the page is asking you to make.

The catalog runs wider: diagrams, diffs with per-file collapse, annotated code walkthroughs, file trees, timelines, metric rows, plans with milestones, and dense command surfaces. The examples gallery opens each complete page in its own view.

Each page owns its layer

page init composes the kernel and selected packages into a checked layer in the page directory. Revisions capture the layer they use, so changing the installed defaults cannot change a version already approved. The package contract owns composition order and replacement rules.

The kernel owns the shared runtime, chrome, and collaboration protocol. Packages supply reusable elements, modules, styles, and guidance: the default package provides common shapes, and optional packages add capabilities such as diagrams and diffs. Project packages use the same format and can replace or extend the selected layer. The extension guide lists the bundled packages and builds a small one.

Layouts

A Layout is a class that arranges the box it is on. On main it shapes the page, and on a block it arranges that block's children.

Class Arrangement
layout-column Text in a centred 720px column, which figures and boards can extend past. A plan, review, report or explanation read top to bottom, as most pages are, this one included.
layout-wide One flow as wide as the window, up to 1600px. A code comparison or a data explorer.
layout-sidebar A header across the page, then a body beside a narrower side column. A board and its status, a release dashboard, or a review with its verdict beside the diff.
layout-workspace The window's full height, divided into panes that scroll separately. A queue beside the item it opens, or a playground's controls beside its preview.
layout-tiles Equal cells, as many to a row as fit, on a block inside a page. A row of metrics or status tiles.

Layouts are plain CSS in a cascade layer beneath the page's own stylesheet. A page adjusts a Layout with ordinary rules, such as a different column share or gap, and a page that no Layout fits writes its own grid.

The reading column

On a layout-column page, headings, paragraphs, lists and code sit in a 720px column centred in the window. Under every Layout, Leaf's theme keeps paragraphs, list items and headings to 720px.

A block that needs more room, such as a diagram, a board or a wide table, extends past the column into the margins while the text above and below it stays in place. The block's width is one of these values:

  • column is the text measure.
  • wide is up to 1080px. Every wide block uses this one width, so wide blocks on a page line up with each other.
  • available is all the width the window has after the page's gutters and anything standing in the margin.

Each widget declares a default in the registry, such as wide for lf-board and available for lf-diagram. A data-width attribute on any block sets a width or overrides the default. Where one margin is narrower than the other, the block takes more from the wider side.

A log, feed or long listing with data-bound scrolls inside a bounded height and opens at its newest entry, so it does not lengthen the page.

Margins

The space beside the column holds these, each only where the window is wide enough for it:

  • The rail, on the right, where Leaf places a marker beside each commented or decided passage. It needs a window about 960px wide, or about 1010px on a touch screen.
  • A sidebar, the page's first aside.sidebar, on the left. It holds a table of contents, a legend or reference facts, and stays in view under the banner as the page scrolls. It needs about 1130px.
  • Sidenotes, each an aside.sidenote, on the right, level with the block they annotate. They need about 1150px.

The column moves off centre to make room for a sidebar or sidenotes. In a narrower window, each sidebar and sidenote sits in the column where the page wrote it.

Wide pages

Every Layout on main other than layout-column makes a wide page. A wide page fills the window up to 1600px, inside a gutter that grows from 24px to 64px. Every block, the title included, starts at the same left edge, and paragraphs still wrap at 720px. The title is set larger than on a column page; a workspace sets it smaller, so its header stays one row.

layout-wide holds a single flow at that width. layout-sidebar puts the page's header across the top, and below it a body and a side column, written as the Layout's aside. The body takes the larger share of the width. An aside written before the body sits on the left, and one written after it on the right. The two stack in source order in a window narrower than about 870px, and in a wider window when the body's content needs the full width, such as a board with many columns.

The side column is unrelated to aside.sidebar, the margin sidebar of a column page. The theme draws a section.panel as a bordered card with a short heading, which sets one region apart from the next. 

<main class="layout-sidebar">
  <header><h1>Release 4.2 rollout</h1></header>
  <div>…</div>      <!-- body: the work in progress -->
  <aside>…</aside>  <!-- side column: status, counts, contents -->
</main>

Examples with a side column: Live progress, Triage board, Command hub. Examples with a single wide flow: Code comparison, Data explorer.

Workspace

layout-workspace fits the page to the window's height, between Leaf's banner and bottom bar. Its header is one row, the title with status tags beside it. The body below the header takes the remaining height. It is one lf-pane, a widget that lays out its own panes, or a grid of panes placed by the page's own CSS. Each pane scrolls its content separately under its own header, and a pane's footer stays in view, so the actions in it are always in reach.

An lf-tabs list="side" set as the body shows its tab list as a queue, such as tickets or findings, with the selected item open beside it.

The workspace holds the window's height only in a window at least 720px wide and 480px tall. In a smaller window the panes take their natural height and the page scrolls as a whole. 

<main class="layout-workspace">
  <header><h1>Payments alerts</h1></header>
  <div id="regions">
    <lf-pane label="Queue">…</lf-pane>
    <lf-pane label="Alert">…</lf-pane>
  </div>
</main>

Examples: Notification playground, Merge a worktree, Alert review.

Tiles

layout-tiles on a block sets its children in equal cells at least 9rem wide, as many to a row as fit, with every cell as tall as its row. Where one row can't hold them, three tiles stack and four go two by two, so neither leaves a single tile on a row of its own. A row of headline numbers is a layout-tiles block of lf-metric elements.

Page tabs

An lf-tabs set at the top of a page makes page tabs, as on this page. The tab strip sticks under the banner, and one panel shows at a time. Every panel belongs to the same page. It has the page's width and Layout, and it shares the page's threads and version history.

Banner, rail and panels

Leaf adds its own controls around a page: a banner at the top of the window, a bottom bar of keyboard hints and status, markers for comments and decisions, and panels for threads and Asks. None of them changes the page's layout, so opening or closing one leaves the text wrapped as it was and the reading position where it was.

The banner and the bottom bar have fixed heights, and the page scrolls between them. Touch screens, which have no keyboard to hint, get no bottom bar.

Markers sit in the rail wherever the window leaves room for it to the right of main: on a column page from a window about 960px wide, and on a wide page from about 1920px, or at any width where the page sets data-rail="right". Elsewhere, and inside a pane, a marker is a small pin over the page beside its target, placed where it covers no text or control if the page has room. The o key, or Hide annotations in the banner's More menu on a touch screen, hides every pin and passage highlight to show what lies under them.

A thread card opens beside its marker, in the room to the right of the text it is about. Where that room is narrower than the card, the card crosses into the column by the difference. The Threads panel and the Asks drawer open over the page's edges, one at a time.

Narrow windows

In a phone-width window every Layout reduces to one column, and a page's regions stack in the order they are written: margin asides return to the column, a side column goes above or below the body, and a workspace's panes take their natural height. Tiles keep more than one to a row: on a 390px phone, two tiles stay side by side and four go two by two.

The page directory is the record

Everything durable about a page lives in its directory. Copying the directory copies the page, its history, and every decision on it. There is no database. Three stores hold what a page shows, each written its own way:

Current state is computed on every read

Nothing stores the page's current state. The live revision's markup is where it starts, and the log records every change since. On each read, the server folds the log over that markup: for each widget, unit, and verb, the latest action still standing wins. leaf page state reports from that one reading, and your browser draws it together with any move you have made that the server has not yet answered.

A change enters the log only through the append door, which checks each event against the verbs the page's layer declares and records what the action meant when it was taken. A later reader recovers that meaning from the record, even once the widget that sent it is gone. Nothing is removed from the log: an undo is a new event that names the gesture it withdraws. The event log reference follows one pick and its undo through the log and the fold.

External values are replaced, not logged

A value an agent or another process supplies, such as a benchmark result or a build's status, lives in one JSON file per source. The page's markup binds each source to a contract its value must meet; the first write records that contract in data.json, and the source keeps it for the page's lifetime. Any process may rewrite the file, so every reading checks the value against that contract, and a failing value shows as that source's error rather than as data.

Rewriting the file changes what an open page shows without a new revision. No earlier value is kept. A number frozen into prose with lf-num keeps the value it was authored with, and leaf page check advises when its source has moved on.

The browser keeps your view and your unsent words, nothing more. View state belongs to one tab. A draft shows in every tab of the page, and the chrome you arrange follows you across pages. Once you send a comment or make a move, it is in the log, where every tab and the agent read it.

How long a server runs

A server is only a way to reach the page directory. One started by an agent session retires when no live session claims the page; one started from your shell, or with --standing, stays up until leaf server stop.

Served where you are

Leaf serves on the session's SSH destination, or on loopback for a local session, where the URL opens only on the serving machine. The URL carries a machine-wide access key, which the browser keeps in a cookie, so sharing that key grants access to every Leaf page on the machine.

When the default address is unreachable, the agent stops the server and starts it again with leaf server start --host NAME on a hostname you can reach. Leaf uses the machine's existing networks and opens no public tunnel. The serving reference covers addresses, authentication, and server lifetimes.
