how it works

Forks

In Claude Code, Leaf hands the user's thread messages to forks: copies of the session's conversation that run beside the session. A fork posts the agent's first words in the thread within a few seconds, whether the session is busy or idle, and a fork with the session's tools can do a small task and answer it while the session carries on with its own work.

Today the first words come from a fork in every Claude Code session. A fork that does the work, and takes its thread's later messages, is built, and acts only with LEAF_FORK_WORK=on in Claude Code's environment; the rest of the design is planned. Each part below says which, and What's built and what's planned lists them.

This page is the design's reference, for people and for agents. It explains the mechanism. The exact rules live in the session lifetime contract and the module headers Where each rule is written lists, and the research and measurements behind the design in notes/fork-replies.md.

Names on this page

Main thread
The session's own conversation, the one the user talks to, as against the forks and subagents made from it.
Line fork
A fork made with $.model.fork, which resends the main thread's last request with one question from Leaf and returns text in about 2 s. It can't call tools. It writes the working line and sorts the message.
Working fork
A background subagent with the main thread's transcript, model and tools ($.agent.spawn with subagentType: "fork"), named leaf-<thread> after the thread it works on. It does that thread's work and answers it.
Working line
The agent's progress message in a thread, saying what it will do about the message, such as “reading the reconnect traces”. It stands until the agent's answer replaces it.
Waiting messages
The user's messages in a thread since the agent's last answer there. The newest one owes the thread's answer.
Turn
A span of an agent's work that Leaf's records name. The main thread works in its turns, and each run of a working fork is a turn of its own.
Pickup
The event in the page log that records a turn taking messages in. It names the session and the turn.
To-do
Work the agent owes on a thread until it ends it, opened with leaf thread reply --todo. A to-do is the obligation a significant task becomes.

The path of one thread message

When the user writes in a thread whose waiting messages the main thread hasn't yet received, Leaf keeps the message back from the main thread and asks a line fork for the working line. It does so while the session's pages follower, a background process Leaf's hooks module runs for the session, is running. From that moment the message reads On it. The line fork reads the message against the conversation, writes the working line, and sorts the message by who should do the work. Leaf posts the line as the agent's and sends the message where the sort says. If no line comes within forks.BOUND_S, 30 s, Leaf gives the message to the main thread anyway, and a line fork that fails gives it there at once.

How the line fork sorts a message

The message Where it goes Status
Small: a question or task a fork can finish beside the main thread, such as a lookup, research that writes only its own scratch files, or a dispatch to another session A working fork, which answers it built judged take; acted on only with the flag
Significant: work on the session's files, branch, page or pull requests, or research long enough to need progress of its own A to-do on the thread, which the main thread schedules planned judged hand_over today
Needed now: the user's answer to a question the main thread asked, or steering its current work The main thread, at its next tool boundary, or woken if idle built judged hand_over

Today the line fork judges two ways (forks.ANSWER). take means a fork with the session's tools could do the work start to finish beside the main thread: it needs nothing the main thread is changing or about to change (its files and branch, the page's source, its pull requests), settles no question the main thread is weighing, and waits on nothing the session is running. hand_over means the work belongs with the main thread. Leaf records each judgment in the page's diagnostics (fork_reply). Without the flag, Leaf posts the line and gives every message to the main thread.

The planned sort splits hand_over in two. Input the main thread needs now can't wait as a to-do, since it changes the work the to-do would wait behind. Research sits on the line between small and significant: a fork can do it, but when it runs for minutes it needs progress lines of its own, so the line fork decides by the message. A working fork that finds a task bigger than it looked can still make it a to-do (To-dos).

A working fork takes a message

On a take, Leaf posts the working line, then in one transaction under the page's lock opens a turn for the fork and records that turn's pickup of the thread's waiting messages, with a delivery made for it (forks._give). The message passes from Leaf keeping it back to the fork holding it with no moment in which neither has it. Leaf's hooks module then spawns the working fork with that delivery, or resumes the fork that answered the thread before (Follow-ups and flurries), and tells Leaf which agent runs the turn (forks.started). The fork works with the session's tools and answers with its own leaf thread reply, using the reply reference its delivery names. built only with the flag

Who holds a message

Leaf ties work to the turn it runs in: a pickup or a start names a turn, and stops counting when that turn ends. The main thread works in its own turns, and Leaf keeps a turn for each run of a working fork in the session's agent-turns record (state.AGENT_TURNS). A fork's turn opens at the take, before Claude Code starts or resumes the fork, and closes when the hooks module reports that the fork's run ended. It also lapses when nothing has renewed it within the working grace, 15 minutes; the fork's tool boundaries renew it. built only with the flag

The newest pickup holds the thread. Of the turns that picked up any of a thread's waiting messages, the one with the newest pickup holds all of them, whether it is the main thread's turn or a fork's. Every reader of received input asks one function which turn that is (forks.holding_turns): delivery, the hooks, the activity fold and the end of a fork's run.

One rule for a fork's writes

A fork's turn may act only on the messages it holds or that no turn holds. One function checks each of its writes as the write is made (forks.refuse_unheld): its pickups, which are its take, its tool boundaries and its acknowledgement of a delivery handed to it by pointer; its replies; and its starts. For this rule an answered message is held by the turn whose pickup of it is newest, so a fork may repeat its own answer, but may not answer again a message the main thread took over and answered.

Takeover

While a fork's turn runs, the main thread waits for it. Its deliveries leave out the messages the fork holds (forks.held_inputs), its Stop hook and watch neither hold its turn over them nor remind it of them (activity.agent_holds), and its own pickups leave them out (forks.pickable). The thread's further messages go to the fork.

Once the fork's turn closes or lapses, a message it left waiting is the main thread's like any it received, with the reply reference the fork's delivery gave it. The main thread's pickup of it is then the newest, so it takes the thread over, and the fork's later pickup, reply or start on that thread is refused.

Who acts

A working fork's shell commands run in the session's environment, so a leaf command it runs looks like one of the main thread's. Leaf's PreToolUse hook in hooks.json, which Claude Code runs before every agent's Bash call that runs leaf, tells them apart by the agent id in the hook's payload. For an agent the session has run a turn for, open or ended (state.agent_known), it rewrites the command to put --agent-id and the agent's id after its leading leaf (hooks.agent_command). The command still begins with leaf, so a permission rule allowing leaf commands still matches it. built only with the flag

The three actors a leaf command can run as, where the session holds the page.
Actor The command What it may do
The main thread names no agent act on anything the session owes, in the main thread's turn
An agent with an open turn is marked, and the agent's turn is open act in its own turn, on the messages it holds or no turn holds (One rule for a fork's writes)
An agent whose turn ended is marked, and the agent has no open turn no reply, start or acknowledgement: each is refused (state.acting_agent_turn)

A subagent the session ran no turn for, such as one of the main thread's own workers, isn't marked and acts as the main thread. The mark follows the agent rather than its turn, so a fork resumed or still running after its turn ended is refused rather than taken for the main thread.

A marked agent's Bash call that runs leaf other than as its first word, as cd x && leaf … does, or runs a second leaf after the first, is denied with the instruction to run each leaf command on its own. Unmarked, such a command would act as the main thread, and a mark spliced into it could land inside quoted text.

The marking lives in hooks.json rather than Leaf's hooks module, because Claude Code runs none of a plugin's tool.call hooks for an agent that plugin spawned (measured at Claude Code 2.1.322), so the module can't see a fork's tool calls. The PostToolBatch hook in hooks.json names the fork too: at each of the fork's tool boundaries it renews the fork's turn and hands it the thread's further messages (hook_transport.carry_agent_turn), and it hands the fork nothing else of the main thread's.

When a fork's run ends

As a working fork's run ends, the hooks module tells Leaf (forks.ended), which closes the fork's turn and judges each thread by the messages that turn picked up itself. The judgment says who owes the thread next. Leaf's clerk tells the main thread of each outcome but a takeover, since the turn that took the thread over already has it. built only with the flag

Each outcome forks.ended gives a thread, and what the main thread hears of it.
Outcome When The main thread hears
answer The fork answered every message it picked up. That the fork answered, so it can read the answer and correct it where what it knows shows it wrong; and that the thread owes nothing, where nothing waits in it and no to-do on it is open. A message the user wrote since reaches it as any new message does.
todo It answered, and opened a to-do on the thread that is still open. That the fork answered and opened the to-do, named with its text, which the main thread now owes and schedules.
hand_over A message it picked up still waits, and the closed turn still holds the thread: the fork gave it back with HAND BACK: and a reason, failed, or ended without answering. That the fork gave the thread back, and why; the main thread now owes its answer. A session no watch follows is woken for it.
taken_over Another turn picked the thread up since the fork did. Nothing: the turn that took the thread over has it.

How a fork tells the main thread

Claude Code tells the main thread nothing of a fork a hooks module spawns: no row in its transcript, and no notification or wake when its first run ends. So Leaf tells it, in lines its clerk queues: one as a fork takes a thread, naming the fork so the main thread can SendMessage it, and one as the fork's run ends. A line waits for the main thread's next tool boundary or prompt, and Leaf wakes an idle session only for a thread given back. The end of a resumed run is different: Claude Code notifies the main thread of it, which starts a turn on an idle session, and that turn reads the queued lines. built only with the flag

Open question: the clerk's line, or the fork's own SendMessage

The alternative to the clerk's line is the fork's own SendMessage to main. In a probe it arrived as an agent message and started a turn on an idle main session 60 ms later. It would wake an idle session at once, name the fork as its sender, and could say what the fork did beyond the outcomes above, so the main thread neither redoes nor contradicts it. Leaf writes the clerk's line from the log, so it also covers a fork that failed or was stopped before it could write. Not decided yet.

Follow-ups and flurries

One working fork works a thread, so a flurry of messages in one thread makes one worker however many messages the user sends. A further message goes wherever its thread already is. built only with the flag

  • Until a fork answers, the user's further messages in its thread reach it at its next tool boundary, inline, or by pointer when they are too large for the hook, which the fork's own leaf delivery ack records into its turn.
  • A message in a thread whose last answer came from a fork's turn that has since closed, in the session's present generation, goes to that fork again (forks._resumable). Leaf opens the new turn under the fork's agent id and records its pickup, as a first take does, and the hooks module resumes the fork by its agent id. Leaf's message resuming it (forks.resume_prompt) carries the thread's delivery and names what the rest of the session did on the page since the fork's last turn began: the threads it wrote in, the revisions it published and the to-dos it opened or ended, which the fork's transcript lacks. The fork can SendMessage the main thread to ask about them.
  • A thread the main thread answered last gets a new fork, and so does one whose fork's turn still runs, ran in an earlier generation, or can't be resumed. A message the main thread writes in the thread unasked, such as a correction of the fork's answer, answers nothing, so the thread stays the fork's.
  • Messages in different threads start a fork each, side by side.
  • planned fallback If a fork per thread proves wasteful, one standing fork per session would take every small message in turn: cheaper, but slower when messages in several threads arrive together.

The main thread as coordinator

The main thread stays in charge of the session's work. It hears by name as each fork takes a thread, and can steer or stop the fork with SendMessage. It takes its to-dos in the order it judges, and runs work bigger than a message in subagents, as the shipped skill's Stay responsive already asks. A fork changes neither the session's files nor its plan: the line fork gives a fork only work that needs nothing the main thread is changing, and the working fork's task tells it to change nothing the main thread is changing or about to change.

To-dos

built only with the flag A working fork that finds the work bigger than it looked can answer with a to-do, with leaf thread reply --todo as the main thread does. The to-do is the session's and stays open after the fork's turn ends, while the fork's start on it stops counting with the turn. The main thread hears that the fork opened it (the todo outcome above).

planned A message the line fork sorts as significant becomes a to-do on its thread that the agent owes until it ends it, so the main thread takes it in its own order instead of being interrupted by it. Such a message has no working fork, and who opens its to-do is still to be designed.

Where each rule is written

  • Session lifetime, “Turns and generations”: the main thread's turns and generations, the agent turns beside them, and who holds a message.
  • src/leaf/forks.py: its header holds the states a thread moves through and why the line fork runs as it does; holding_turns, refuse_unheld, authorize, pickable, _give and ended hold the rules this page names.
  • src/leaf/state.py: AGENT_TURNS, agent_known and acting_agent_turn, the record of agent turns and the actor a command runs as.
  • src/leaf/hooks.py: agent_command and leaf_commands, the marking and the refusal of a compound command; and src/leaf/hook_transport.py: carry_agent_turn, a fork's tool boundary.
  • hooks/claude-code.ts: forkReply, workFork and the turn.complete hook, which make the forks and report a working fork's end.
  • notes/fork-replies.md: what Claude Code lets a hooks module fork, measured; how well the line fork judges; forks on real pages; and the build steps.
