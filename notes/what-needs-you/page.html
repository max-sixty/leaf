What needs you: tasks

An Ask ends when you answer it. Work the agent owes has had no record of its own: a reply, a Resolve or the end of a session could settle it while nobody had done it. A task is that record. The agent opens one on a thread when it takes on work that outlasts the turn, and only the agent writing its outcome ends it. Tasks, Asks and owed replies together make one queue for you and one for the agent.

Two steps of four are built

Both are on the what-needs-you branch, not yet landed. You picked them on this page's earlier Ask.

  1. A queue for each side (built). leaf page state returns queues.on_you and queues.on_agent, assembled from readings the browser already made. Still to do: a walking all of on_you, not only Asks, and the banner counting on_agent.
  2. Agent tasks in the log (built). leaf task open and leaf task end write task and task_end events.
  3. Done becomes something for you to review (days). A finished task puts its result on your queue, reading it accepts it, and replying to it reopens the same task.
  4. Tasks outlive their session (about a week). A task whose session ended with no outcome reads unobserved and lands on you. A dispatched session can take the task over and write its outcome to this page.

The append door holds the rules. Only the agent opens or ends a task. A task opens only on an open thread, ends once, and nothing else ends it: a reply, a Resolve, a new version and the end of the session all leave it open. Work that finishes inside the turn needs no task, since the turn's status --on claim covers it.

While a task is open, its thread reads Task open, waiting on the agent, and sits under the threads panel's Waiting on: Agent filter; the margin and Page Map carry the same label. The banner names every open task, so one on a thread you resolved stays in view.

Each side has a queue of open items, and what an item is stays open

An item is anything open that one side has to act on. Each names what it is about, its subject and thread, so a surface can take you there. Its kind only says where it came from: today the queues collect open Asks, prose questions waiting on you, failed sends, replies the agent owes, this turn's claimed work and open tasks. That set isn't a contract. New sources join as they turn up, and which kinds deserve their own rules gets decided once we've used the queues.

How they meet today:

  • A task and the message it came from. Your message opens an owed reply. The agent's reply settles it, and a task it opens carries the work on. Nothing records that the task answers that message, beyond both standing on one thread.
  • A task inside an Ask. “Show me a sketch first” in an Ask's thread opens an owed reply, and the agent may open a task there. The Ask still counts as yours, though you are waiting on the sketch.
  • An Ask answered in prose. Your message opens an owed reply, and the Ask stays on you until the agent writes your pick into the page.
  • Resolve. It settles the owed replies in the thread and leaves a task open.

Your point about question and answer holds across the table: the records pair up by who owes them. An Ask and a task are both structured work with an end; a prose question and an owed reply are both a message one side owes the other. Only the owed reply has stages, and they track how far your message has reached the agent, from sent to replying, not the work it asked for.

Pi keeps a message's delivery apart from the work, and has no record for asking you

From Pi Durable:

  • A message is input, not a task. Sent while the agent is busy, it either steers (“joins the running work after the current tool calls”) or queues as a follow-up. A requestId makes the submission exactly-once. Nothing like “picked up” is recorded on it.
  • Work is tasks, and a task's stages are its own. A task type declares named phases, and its state holds a checkpoint naming the current one. Its status is running, waiting on named tasks, or terminal with an outcome (completed, failed or aborted). Code registers one with tx.createTask(Type, input, {ownership}), owned by a task or a conversation.
  • Asking you is not a record. An approval hook asks, and stores your answer with api.memo(), so that “after a restart, the hook finds the stored answer instead of asking again”. The question is the agent's running work, paused on you.

In Leaf's terms: sent and queued are where the message is, picked up through replying is a running task, and an Ask is a task of the agent's waiting on you rather than an item of yours.

On real pages, the agent's work was what went missing

From every thread on this machine's pages with real user text, July to September: Asks drained, with 77 of 104 answered. What the agent took on did not.

threads left open on nobody (median age 28 days) threads you resolved right after the agent promised work of those got the result in the thread

Of those 15 results, 6 landed in a version note or a sibling thread and 9 went to another session by design, which is why a task ends from anywhere and names where its result is.

The model is Pi Durable's: every unit of work is a task with an owner and an outcome. Step 3 adds what review and support tools add to it: whoever did the work reports it, and the one who asked accepts it, with a reply to reopen. Winograd's conversation for action (1986) and Zendesk's ticket lifecycle both work that way. The fuller research is in notes/what-needs-you/research.md.
