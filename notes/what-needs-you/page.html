What needs you: tasks

An Ask ends when you answer it. Work the agent owes has had no record of its own: a reply, a Resolve or the end of a session could settle it while nobody had done it. A task is that record. The agent opens one on a thread when it takes on work that outlasts the turn, and only the agent writing its outcome ends it. Tasks, Asks and owed replies together make one queue for you and one for the agent.

One queue each, and either side puts items on the other's

You set the model in a thread: an Ask is parallel to a task, each side has a queue, either side can put items on the other's, and a pages through yours. An item says whose queue it is on, who put it there, what it is about (a thread, an Ask, the page) and whether it is open. Which kinds of item exist stays open.

the agent An Ask; a question in a thread; later, a result to review A task it takes on

  1. A queue for each side (built). leaf page state returns queues.on_you and queues.on_agent.
  2. Agent tasks in the log (built). leaf task open and leaf task end.
  3. a pages through your queue (built, not yet landed; try it here). Each press goes to the next item on you in page order: an open Ask, a thread with a question for you, or a send to retry. The banner's status row ends with "N on you · M on Claude". t keeps walking every open thread.
  4. Working is a task (built, not yet landed). leaf status working --on folds into the task commands: leaf task start ID "line" takes an item in hand, your move by its event id or a task, for the turn; leaf task open takes a thread, a widget or page; claims move from the status file into the log, and leaf status keeps only waiting and idle. A start left after its turn still reads stalled; merging that with unobserved is step 7. See Working on something means working on a task and What the agent can be working on.
  5. Asks and tasks read as one item. The queues give every item the same fields, so an Ask and a task differ only in whose queue they are on, and the question and answer kinds go.
  6. Either side adds to the other's queue. The agent can put a finished result on you to review, and you can put a task on the agent from a thread.
  7. Items outlive their session. A task whose session ended with no outcome lands on you, and a dispatched session can take it over.

The append door holds the rules. Only the agent opens or ends a task. A task opens only on an open thread, ends once, and nothing else ends it: a reply, a Resolve, a new version and the end of the session all leave it open. Work that finishes inside the turn needs no task, since the turn's status --on claim covers it.

While a task is open, its thread reads Task open, waiting on the agent, and sits under the threads panel's Waiting on: Agent filter; the margin and Page Map carry the same label. The banner names every open task, so one on a thread you resolved stays in view.

Its kind only says where it came from: today the queues collect open Asks, prose questions waiting on you, failed sends, replies the agent owes, this turn's claimed work and open tasks. How they meet today:

  • A task and the message it came from. Your message opens an owed reply. The agent's reply settles it, and a task it opens carries the work on. Nothing records that the task answers that message, beyond both standing on one thread.
  • A task inside an Ask. “Show me a sketch first” in an Ask's thread opens an owed reply, and the agent may open a task there. The Ask still counts as yours, though you are waiting on the sketch.
  • An Ask answered in prose. Your message opens an owed reply, and the Ask stays on you until the agent writes your pick into the page.
  • Resolve. It settles the owed replies in the thread and leaves a task open.

Your point about question and answer holds across the table: the records pair up by who owes them. An Ask and a task are both structured work with an end; a prose question and an owed reply are both a message one side owes the other. Only the owed reply has stages, and they track how far your message has reached the agent, from sent to replying, not the work it asked for.

Working on something means working on a task

Today leaf status working --on SUBJECT "…" writes a claim into the page's status file, outside the log, and a task is a separate record in the log. They hold the same fact: the agent has taken on this subject. Pi Durable splits that fact by lifetime, not by record: a foreground task belongs to the current turn, and a background task outlives it. Leaf can do the same with one record.

Today As a task
status working --on X "sentence" A task on X that lasts the turn, titled with the sentence. The banner's Working line is that task's title.
task open X "title" A task on X that lasts until it is ended, as now.
A claim ends at the agent's next reply in the thread A turn task ends done when the reply that answers it is written.
A widget claim ends with page stamp --completes W The same stamp ends the task on W, done, citing the version.
A claim left after its turn reads stalled A turn task whose turn ended without an ending lands on your queue as unobserved. This is step 7's rule for a background task whose session ends, so stalled and unobserved become one state.
A move reads Working while a claim holds it A move reads Working while an open task on its thread or widget holds it.
status waiting "question" An item on your queue: the page-level question it already is, shown where the banner shows it now.
status idle Stays: the agent is done with the page, refused while it still owes you anything, as now.

What has to move for that to work:

  • Claims move into the log. Each status --on becomes a task event carrying its turn, in place of an entry in status.json's work list. The status file keeps only what the host observes (Codex's live steps and reply bindings), which is not a commitment.
  • Tasks take widgets as well as threads. A widget claim needs a widget that declares work or holds an unanswered press; a task takes the same rule, and --completes becomes the task's ending.
  • The readers of claims read tasks. Workflows (which move is Working, and the standalone claim workflows), admission's record of which moves a gesture affects, the activity fold (declared work, renewal, stalled), the Stop hook's rule that a claim in this turn lets the turn end, the banner, the margin and Page Map "Working" labels, neighbour rows, and the stamp and re-vendor guards for claimed widgets.
  • The instructions change. The registry's answering clauses, conversation-loop.md, event-batches.md, threads.md and SKILL.md tell the agent to claim with status --on; they would tell it to open a task, with an eval before and after.

Decided: leaf status working --on folds into the task commands, so one command takes work on, and status keeps only waiting and idle. This is step 4, before Asks and tasks share one item shape.

What the agent can be working on

If Working always names an item on the agent's queue, the line in the banner points at something you can open. These are the cases:

Case Today The item Working would name
You comment or reply in a thread status working --on the thread Your message. It is already an item you put on the agent's queue, and its id is the item's id.
You press an option, or move a card status working --on the widget; a stamp ends it Your press, the same way.
Work that outlasts the turn: a subagent, CI, a dispatched session task open That task.
One turn answers five threads One claim per thread; the banner shows the latest sentence Each of the five, running. The agent picks what the banner says; until it does, the banner names the item in hand.
You asked in the terminal, not on the page (“build step 3”) status working "…" with no subject Nothing yet. The agent puts a page-level task on its own queue, so the page shows the work and its outcome.
The agent's own initiative: writing the page, revising a section status working "…", or "Writing the page" at init A task the agent opens, on the page or the section.
Housekeeping: re-vendoring, restarting the server, merging main status working "…" or nothing None. It owes you nothing, so it isn't Working; the banner can show the observed step, as it does for Codex.
Waiting for your answer status waiting "…" None on the agent's queue: the item is on yours.

So every case but housekeeping already has an item, or gets one the agent opens. Your moves are items you put on the agent's queue; tasks are items it puts there itself. Working then becomes a state of an item, not a separate claim: leaf task start ID "what I'm doing", where ID is your move's id or a task's, and the subject comes from the item. A reply or stamp that answers a move ends it; a task still ends with task end.

Later: the banner line is a field the agent sees and sets. Leaf fills it from the item in hand when the agent is answering something quickly, and the agent can replace it, for example with one line covering five threads at once.

How Pi Durable models the same ground

The two work at different levels. In Pi, every model turn, tool call and tool result is a message in the user–assistant conversation, and each is a task. In Leaf, a message is your comment or the agent's reply, and one reply is the outcome of a whole run of those: dozens of model and tool steps work towards answering you.

Pi Durable Leaf
A message Every model turn, tool call and tool result Your comment, or the agent's reply to it
A task One step: a model request, a tool call, a compaction, a subagent One thing owed between you and the agent: an answer to your comment, a rebuild, a review
How long it runs Usually seconds; a subagent or reminder longer A turn, or hours to days across sessions
What the record is for Resuming exactly where a crash left off Knowing what is owed, by whom, and whether it was done

So a Leaf item is not one of Pi's tasks but one high in the tree: in Pi's terms, a task the conversation owns, whose children are the steps that work towards it. Leaf sees those steps only as the banner's Working line.

At its own level, Pi Durable works like this:

  • A message is input, not a task. Sent while the agent is busy, it either steers (“joins the running work after the current tool calls”) or queues as a follow-up. A requestId makes the submission exactly-once. Nothing like “picked up” is recorded on it.
  • Work is tasks, and a task's stages are its own. A task type declares named phases, and its state holds a checkpoint naming the current one. Its status is running, waiting on named tasks, or terminal with an outcome (completed, failed or aborted). Code registers one with tx.createTask(Type, input, {ownership}), owned by a task or a conversation.
  • Asking you is not a record. An approval hook asks, and stores your answer with api.memo(), so that “after a restart, the hook finds the stored answer instead of asking again”. The question is the agent's running work, paused on you.

Your model fits Pi's. A Pi task has an owner and waits on whatever it needs, so an Ask is the agent's task waiting on you, and your queue is every task waiting on you. Pi differs in two places, neither a conflict. A message is input that starts or steers the agent's work rather than an item of its own, so putting an item on the agent's queue is your message creating work there. And Pi records nothing about delivery, so Leaf's stages from sent to replying belong to the message, not to the task.

On real pages, the agent's work was what went missing

From every thread on this machine's pages with real user text, July to September: Asks drained, with 77 of 104 answered. What the agent took on did not.

threads left open on nobody (median age 28 days) threads you resolved right after the agent promised work of those got the result in the thread

Of those 15 results, 6 landed in a version note or a sibling thread and 9 went to another session by design, which is why a task ends from anywhere and names where its result is.

The model is Pi Durable's: every unit of work is a task with an owner and an outcome. Step 6 adds what review and support tools add to it: whoever did the work reports it, and the one who asked accepts it, with a reply to reopen. Winograd's conversation for action (1986) and Zendesk's ticket lifecycle both work that way. The fuller research is in notes/what-needs-you/research.md.
