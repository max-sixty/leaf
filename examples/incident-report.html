Export queue backlog, 12 June

A retry storm from one malformed workspace held the export queue for 94 minutes. No exports were lost; the oldest was delayed 81 minutes.

Detected

Resolved
10:48, poison job quarantined

Timeline

Queue-depth alert fires Depth crosses 500; normal peak is 60. On-call confirms a single hot job The same export id retrying at the head of the queue, every 45 seconds. Adjacent deploy ruled out The 09:00 deploy touched imports only; the queue code last shipped in May. First fix doesn't hold Raising worker count clears depth briefly; the retry storm refills it because the head job still fails first. Poison job quarantined The workspace's export is parked in a dead-letter table; the queue drains at normal rate. Backlog cleared Depth back under 60; delayed exports delivered.

Root cause

The export worker treats any failure as retryable. One workspace carried an attachment with a declared size of −1, which fails serialization every time; with retries capped by attempt count but not by queue position, the job returned to the head on each attempt and starved everything behind it. 

graph LR
  Q[queue head] --> W[worker]
  W -->|serialize fails| R[retry in 45s]
  R --> Q
  Q -.->|starved| B[1,204 jobs behind]
The fix is one classification: serialization errors are permanent, not retryable. Retryable failures also now re-enqueue at the tail, so no single job can hold the head again.

Follow-ups

  1. Classify worker failures as permanent vs. retryable; dead-letter permanents on first failure.
  2. Re-enqueue retries at the tail.
  3. Alert on a single job id exceeding five attempts, not only on queue depth.
